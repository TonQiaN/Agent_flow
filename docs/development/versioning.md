# 版本维护指南

当前具备 Roadmap、CHANGELOG 和手工发布约定，尚无产品发布、打包实现或发布自动化。本指南描述如何维护这些文档；没有执行发布演练。取舍见 [版本管理决定](../../.agents/decisions/development/README.md#d-20260908-version-management)。

## 内容放在哪里

| 位置 | 唯一维护的内容 |
| --- | --- |
| [Roadmap 总览](../roadmap/README.md) | 阶段边界、版本目标摘要、版本状态和计划 / 发布入口 |
| `docs/roadmap/<version>.md`（按需创建） | 单版目标、范围与非目标、版本整体验收、关联工作 |
| Issue | 主负责人、详细任务验收、执行进展、讨论与确认 |
| [.agents/decisions](../../.agents/decisions/README.md) | 方案取舍和必要确认摘要 |
| [CHANGELOG.md](../../CHANGELOG.md) | 已实现的变化、待发布条目及历次发布结果 |
| Git tag `vX.Y.Z` | 某次正式发布对应的确切提交 |

Roadmap 不复制 Issue 的详细任务状态或决策正文，CHANGELOG 不收录尚未实现的愿望。操作指南继续说明已实现能力。

## 规划版本

主负责开发者先在相关 Issue 中明确目标与范围，再更新 roadmap 总表。开始该版实际实现的 PR 同步总表为进行中；stack 各层按自己的 base 核对总表、计划和交付说明，不能依靠后续层修正本层的状态。初期只使用计划中、进行中、已发布三种版本状态，状态集中放在总表；它们不替代 Issue 就绪确认或决策生命周期。

远期方向各写一句话即可。开始具体规划某版时，再按下面四项建立版本文件，并从总表链接；不提前创建系列目录、空版本文件或归档副本。

```markdown
# <version>：版本目标

## 目标

这个版本交付后，使用者能够解决什么问题。

## 范围与非目标

包含哪些结果，哪些内容明确留待后续。

## 版本验收

能检查的整体交付结果及验证方式；详细任务验收引用 Issue。

## 关联工作

实际存在的 Issue 与决策索引链接。
```

一个 Issue 已完整覆盖的小补丁，直接从总表关联 Issue，不必新建版本文件。编号采用 X.Y.Z 三段非负整数，各段除 0 外不带前导零，tag 在前面加 v，例如 v0.1.0。当前只约定格式；首发编号、升版边界和兼容性承诺在相关版本规划中明确，不照搬参考项目的版本历史。不因示例文件名就开始发布，也暂不增加 VERSION 或包版本文件。

## 调整范围

负责该改动的开发者同步相关版本计划和总表，保留简短原因；延期事项注明目标版本或待重新安排，取消事项明确标注取消而非完成。需要改变方案取舍时，按既有流程修订同一决策。

已发布计划保留；新的目标写入后续计划。历史事实的纠正注明原因，不改写过去实际交付的范围来冒充当时已经完成。Git 保存修订历史，重要调整原因在当前正文中仍可理解。

## 随 PR 记录实际变化

产生值得告知使用者的实际变化时，在同一 PR 中补充 CHANGELOG 的 Unreleased。条目说明结果、行为变化或限制，可以链接相关 Issue；不逐条复制 commit，也不把计划任务列为新增能力。分支上的条目是本 PR 的交付内容，合入默认分支后才成为已合入的待发布记录。

已有明确目标版本时，在 Unreleased 下使用 `### X.Y.Z（目标版本，未发布）`，其下以四级标题按需分类。只归入已实现的变化，不为仅有规划、尚无实际变化的版本创建空组；没有产品版本归属的协作变化单列。目标版本分组不表示整版验收通过或进入发布准备，不能直接补预计发布日期。

同一未发布功能继续交付后，将条目整理为当前用户行为和仍有效的限制，合并重复分类及相同功能的切片描述。历史过程、失败及对应版本的验证记录保留原事实；已经正式发布的条目不因后续功能实现而改写。版本计划保留当前范围、剩余验收和证据入口，不累积完整执行日志。

分类按需采用新增、修复、重要变更或已知限制，空分类省略。没有使用者可感知变化的 PR，可以在 [PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md) 中说明 CHANGELOG 不适用，不制造空条目。版本目标或范围未变时，roadmap 也不必更新。

## 手工发布

当次发布负责人在对应 Issue / PR 中明确，沿用 [开发工作指南](workflow.md) 的评审和合并步骤。当前没有可直接执行的产品发布任务；首次发布先在对应工作项明确编号、验收和实际交付范围。

1. **准备发布记录。** 核对版本整体验收和相关 Issue，通过 PR 将本次 Unreleased 中已核对的目标版本条目移到二级 `X.Y.Z — 待发布` 标题下，将其分类升为三级，保留 Unreleased；roadmap 保持进行中并关联版本计划。同步必要使用说明和验证证据，未交付事项不算入本版，其他尚未发布的实际变化留在 Unreleased。
2. **确认发布提交。** 发布准备合并到 main 后，记录要发布的完整 commit SHA，核对它包含本版内容和当前适用的验证结果。代码或基线变化时补做受影响的验证；未配置、未执行的检查不算通过。
3. **固定并推送 tag。** 为该确切提交创建 annotated tag `vX.Y.Z`，只推送该 tag。读取远端 tag 指向的 commit（annotated tag 的 peeled commit），核对其与记录的 SHA 一致。同名 tag 已存在时先核对，不能移动、覆盖或强推；推送失败后重试前也先读取远端状态。
4. **记录实际发布事实。** 确认远端 tag 后，通过文档 PR 将 CHANGELOG 标题补为 `X.Y.Z — YYYY-MM-DD`（实际发布日）并链接 tag，将 roadmap 更新为已发布并链接对应变更记录。步骤中断或跨日时保留待发布标记直至核对完成，不把预计日期写成实际日期。tag 固定交付源码，后续文档提交补齐发布事实，无需移动 tag。
5. **完成交接。** 在发布工作项记录 tag、确切提交、验证结果及限制。以后使用 GitHub Release 时复用 CHANGELOG 对应条目，不维护独立 release-notes 正文；只有相关验收完整满足时才关闭工作项。

上述步骤是手工操作，更新 Markdown 不会自动创建 tag 或 GitHub Release。源代码修正使用新版本；发布记录的事实纠错可通过文档 PR 完成，历史 tag 不变。每个 PR 的实质决策正文要求继续适用：发布准备和事实回填可与同问题的相关改动一起提交，有意义的验证边界或落实情况进入原决定，不为发布凑一个新决定。

## 谁在什么时候维护

| 时机 | 主负责开发者 / 发布负责人要做的事 |
| --- | --- |
| 开始规划 | 主负责开发者更新总表，按需建立版本计划并关联 Issue 与决定 |
| 调整范围 | 改动负责人修改受影响计划，说明延期、取消或转移的原因与去向 |
| PR 合入 | PR 作者同步实际变化至 Unreleased，并填写 roadmap / CHANGELOG 的更新或不适用说明 |
| 正式发布 | 当次发布负责人核对验收、记录、提交和远端 tag，补齐日期及已发布状态 |

不增加专职文档角色，也不要求所有普通 PR 执行发布步骤。
