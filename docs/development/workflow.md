# 开发工作指南

当前仓库具备开发流程决定、Issue / PR 模板、确定性 Component 与基础工程检查。已配置 Node 24/26 基础 CI，自动预检、部署和完整产品验收仍未实现；阶段与取舍见 [开发流程决定](../../.agents/decisions/development/README.md#d-20260907-development-workflow)。

## 建立和整理 Issue

主 Issue 描述整体需求：当前情况、问题、期望结果、必要边界与完成标准，使用功能、缺陷、研究、决策、维护五类模板。领域、九项共同字段及缺陷事实的用法见 [Issue 指南](issue-templates.md)。制定者不必在创建时知道具体实现方式。

Sub-issue 关联主 Issue，由对应负责人自主组织其承担的具体工作，对执行方案与交付负责。内容与形式完全自定，当前没有子项模板、写作要求、推荐格式或示范正文；主表及本指南的记录示例不套用到子项。足够多的实际方案完成实施验证后，再提炼共性。通过 GitHub 父子关系、Assignees 与交付 PR 确认工作归属；不按每个 PR 或 AI 会话机械拆项。

人参与整理时，AI 和工具可以归纳讨论、协助澄清和起草主 Issue，人确认责任、范围与完成标准。明确的用户指令可以作为已有确认依据，不增加重复审批；暂时未知的必要条件如实记录，不能冒充就绪。

主 Issue 可在整理与续接字段保留如下短记录，便于核对当前范围。这是主表的使用说明，不是子项写作推荐，也不是新增自动状态：

```text
整理：待补充 / 可开工
主负责开发者与实际参与分工：
确认人、日期与依据：
本次验收范围：引用主 Issue 中的明确条目
当前阻塞：无 / 具体未解决条件
```

## 预检与文档准备

### Blackbox 参考入口与调查边界

开发或测试遇到问题时，优先按症状查阅 [Blackbox Agent Flow（xiaoxuanli-a/Agent_workflow）](https://github.com/xiaoxuanli-a/Agent_workflow) 的对应实现、测试和修复历史，核对是否已有解决方案，再选择复用或补充调查。此项不作为纯文字、链接或 Issue 整理的前置步骤。

确认无相关内容、无法访问或未找到对应结果时，说明依据或限制，继续本项目的复现与调查；若缺失资料确实影响必要的兼容性判断或验收，则记录具体阻塞及所缺依据，继续不依赖该资料的工作。无需穷尽旧仓库，查无结果也不证明旧系统没有该问题。

查阅时记录实际参考的 commit 或版本及环境差异，区分已提交与本地未提交内容；团队入口不依赖相同的本地 checkout 路径。借鉴已有修复后仍运行本项目受影响的回归测试，旧系统的通过结果不能替代当前验证。

### 开工预检与文档

负责人或协助工具在开工前核对当前实现、相关决定及已有 alternatives / rejected，识别重复工作、冲突与必要依赖。Bug 尝试复现并保留实际版本、条件和观察；无法复现不等于没有问题。当前没有后台自动预检，结果可留在 PR 或验证记录。

预检结论为“可继续 / 有阻塞 / 证据不足”，说明依据与负责人采取的处理。范围和验收需要实质调整时回到人参与整理；已有确认不因补充记录而重复审批。

Issue 保存实际讨论和确认，正式决定保留自足的取舍、必要摘要与对应 Issue 定位。已有文档完整覆盖本次工作时，确认适用范围即可，无需重写；需要补充或修订时，负责人先写清本次决定及影响，再实现、测试。实现中出现新取舍时先修订对应正文；决定、实现与指南可以同一 PR 提交。已有问题修改唯一正文，未全部落实仍在 proposed；目录或 Issue 开关状态不能代替对具体方案的确认。

负责人对实际采用的执行方案负责，先按确认的方案推进，AI 不自行改变关键方案。更好方案或偏差可以在 PR 审查中讨论；统一的方案调整判断、确认及回退细则尚未制定，不以本指南新增固定操作流程。

## PR 的交接与审查

[PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md) 记录问题与结果、主 Issue 及实际存在的 Sub-issue、验收覆盖、发生实质改动的决定和验证证据。CLI/API 创建 PR 同样补齐这些交接内容；勾选本身不执行检查。这些是 PR 说明要求，不约束子项正文。

每个 PR 相对实际 base 至少包含一份正式决策正文的实质改动。复用既有 ID 不等于只加引用；轻量改动若不存在有意义的决策变更，应并入同一问题下包含实质决策变更的相关 PR，不为凑数建立决定或制造空修改。已有文档无需重写不豁免该 PR 门槛。作者先自查相关差异与验证，实际审阅方式如实记录，不能把 AI 或作者自查写成多人审查。

审阅者可以先理解主 Issue 的问题、要求和完成标准，在查看实现前独立思考解决方式，再对照 PR 交付、实际采用的方案和证据给出意见。除代码问题外，也核对结果是否满足需求、决定与文档是否一致。更好方案的建议不自动成为已确认变更，阻塞反馈由负责人处理；修正后补做受影响的验证。

涉及版本目标或范围时同步 [Roadmap](../roadmap/README.md)；影响使用者的实际变化写入 [CHANGELOG](../../CHANGELOG.md) 的 Unreleased。适用时点见 [版本维护指南](versioning.md)，普通 PR 不执行发布步骤。当前基础检查命令为 `npm run check`，包含依赖边界、构建、测试类型检查及 Node 测试；测试文件并发数为宿主可用并行度与 4 的较小值，文件内部的并发场景保持原样；更完整的集成验证按改动和验收范围确定，未运行或未配置的项目如实列出，实际结果留在 PR 或需要长期保存的 [验证记录](../validation/README.md)。

## 关联、合并与关闭

父子关系描述具体工作的归属，依赖描述阻塞，PR 引用描述本次交付，stacked PR 的 base 表达代码依赖；这些关系各自核对，不以一种代替另一种。主 Issue、子项、Assignees 与 PR 的关联演练见 Issue 指南。

PR 引用本次覆盖的主 Issue 和实际存在的 Sub-issue。一个子项可以由多个 PR 交付；没有独立拆分价值时，无须为了 PR 创建子项。部分交付使用 `Refs #编号`，仅当某个工作项的完整验收已满足且最终 PR 面向默认分支时使用关闭关键字。[GitHub PR 关联说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)，2026-09-10 核对。

合并前检查非 Draft、目标分支、冲突、阻塞反馈、实际要求的审阅及仓库已配置的必需检查。同步 base 或修改内容后重新核对受影响部分；不借用此前版本的通过结果。合并后确认进入默认分支的实际成果，子项按承担的工作核对，主 Issue 另验整体需求。子项全部关闭或一项 PR 合并都不能代替整体验收；取消与未实现如实区分。

只有存在实际代码依赖且有独立审阅价值时才使用 stacked PR。每层检查自己的 base、范围、决策增量与证据；下层合并后同步上层和 base，重新检查差异，处理衔接后再清理分支。父子 Issue 关系不会自动要求叠放 PR。
