# 开发工作指南

当前仓库具备开发流程决定、本地 Issue / PR 模板及协作操作说明，尚无可运行产品。自动预检、CI/CD、测试矩阵和开发 Skill 尚未配置，真实产品流程尚未验证；阶段与取舍见 [开发流程决定](../../.agents/decisions/development/README.md#d-20260907-development-workflow)。本指南说明目前怎样使用这些文档和模板，不表示自动流程已经存在。

## 建立和整理 Issue

本地已有 [功能模板](../../.github/ISSUE_TEMPLATE/feature.yml)、[缺陷模板](../../.github/ISSUE_TEMPLATE/bug.yml) 和 [维护模板](../../.github/ISSUE_TEMPLATE/maintenance.yml)。模板进入默认分支后才能供 GitHub 对应入口使用；尚未进行线上表单验收。通过 CLI 或 API 建立的 Issue 也需补齐同样的信息。

负责开发者在 Assignees 中明确归属；正文有多名协作者时指出主责。创建时写明问题与目标、范围与非目标、验收标准、依赖和已知疑问；Bug 增加行为差异、步骤及版本/环境。候选决策可以稍后经预检补齐，不能用原始资料链接代替这些内容。

当前采用人参与整理的方式：AI 和工具可归纳讨论、建议拆分、补齐字段及起草验收标准，人参与澄清、纠正并确认关键边界，再登记整理结果。可直接在 Issue 正文维护如下短记录；这不是新增 GitHub 状态、标签或自动触发器：

```text
整理：待补充 / 可开工
整理参与：实际参与的人、AI 或工具及分工
主负责开发者：
确认人、日期与依据：
本次验收范围：引用正文中的明确条目
依赖与阻塞：无 / 列出并说明处理方式
```

明确用户指令可以作为已有确认依据；记录实际参与者，不补造另一轮审批。需要拆分时，子 Issue 各自写可验收的结果、主责和依赖，父 Issue 负责汇总。

## 记录预检与文档准备

目前可由负责开发者或协助工具按任务检查并把结论留在 Issue；没有后台自动预检。推荐记录：

```text
预检基线：提交 / 版本、相关环境
实现对照：当前已具备什么，本次还缺什么
决策对照：相关 ID、已知 alternatives / rejected、冲突与依据
Bug 复现：步骤、结果与证据 / 非 Bug 不适用
预检结论：可继续 / 有阻塞 / 证据不足
主负责开发者的处理：继续 / 补证据 / 调整范围，及理由
决策处理：复用哪些 ID，修订哪些问题，是否新增独立问题
审阅与确认：具体决策 ID、修订范围、实际参与者、日期和明确依据
阻塞意见处理：无 / 处理结论及依据
```

无法复现时填写尝试和缺少的证据，不写“没有 Bug”。结论有阻塞或证据不足时，由主负责开发者明确下一步；影响已确认范围时更新整理记录。

Issue 同时保存决策讨论、分工和审核过程，负责开发者把已经敲定的取舍同步到唯一决策正文，只留下必要确认摘要和 Issue 定位。未全部落实的决定统一位于 proposed；判断能否实施时核对具体方案的确认依据，不能把 Issue 可开工、已关闭或目录位置当作所有建议已被采纳。共同审查及启动期安排见开发流程决定，当前没有固定人数门槛。

然后按 [文档维护指南](documentation.md) 先写相应决定和开发约定，再开展实现和测试。决定可以与代码、测试、指南一起提交。当前没有统一测试命令或矩阵，验证方法按改动和验收范围确定，实际结果留在 PR 或需要长期保存的 [验证记录](../validation/README.md)。

## 使用 PR 模板

版本目标或范围变化时，同步对应 [Roadmap](../roadmap/README.md)；产生值得告知使用者的实际变化时，同一 PR 更新 [CHANGELOG](../../CHANGELOG.md) 的 Unreleased。模板记录更新位置或不适用原因，具体维护时点与发布步骤见 [版本维护指南](versioning.md)。普通 PR 不需要执行发布步骤。

[PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md) 提供问题与结果、Issue 验收映射、决策改动、验证评审、依赖合并几项交接信息。CLI / API 创建 PR 时同样补齐这些内容；模板勾选不执行自动检查。

提交前查看本 PR 相对实际 base 的差异，填写真正发生变动的决策 ID 及内容。已有决定覆盖时复用原文件；轻量任务的处理按流程决定执行，不能只补一个引用就视为满足要求。没有固定要求把决策分成独立 commit。

作者先自查，记录真实测试范围、对象和结果；有人或工具审查时记录实际方式。修正意见后更新验证信息，实质变化重新请求相关审阅。合并前再次核对目标分支、验收证据、冲突、阻塞反馈和仓库当时配置的必需检查，不能以此前版本的结果代替当前状态。

stacked PR 在模板中填写前后依赖、目标分支和各层验收。下层合并后先同步上层和 base，再检查该层 diff、决策增量及受影响的验证。仅引用工作项时可写 `Refs #编号`；最终完整交付才使用关闭关键字。GitHub 对 PR 正文关闭关键字的处理依赖默认目标分支，详见 [官方说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)。

## 当前能力边界

| 项目 | 当前具备 | 尚未完成 |
| --- | --- | --- |
| Issue 整理与审查 | 三类本地表单、字段、人参与整理及决策确认说明 | 线上表单验收、自动状态流转 |
| 预检 | 输入、结果及人处理的约定 | 自动运行器与 Bug 复现能力 |
| 决策及 PR | 正式决定、PR 模板、人工审查步骤 | 决策增量自动检查、完整产品流程验证 |
| 工程验证 | 文档与模板的局部静态校验 | 产品 CI/CD、测试矩阵、部署流程及 Skill 选择 |

Issue 表单的 `required` 字段不能代替人参与整理与关键确认。当前仓库是私有仓库；GitHub 官方对该校验标注了公开仓库限制，CLI / API 和提交后的正文编辑也不能仅靠表单约束。负责人输入不会自动设置 Assignees。当前通过人参与的就绪核对保证必填内容，AI 和工具可协助检查；未来如接自动门禁再另行落实。[表单结构说明](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema)、[Issue 表单说明](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)，2026-09-07 核对。
