先查 Blackbox v0.1.22 / 5610d1b 的 parallel-execution.md、Map/Fork 定义、test_parallel_runtime.py 及并行修复历史。采用稳定 ID、Map 原索引、Fork 字典序、共享容量及部分结果保留；只实施用户确认的单层 JSON、单 Component 与 wait-all，不迁移旧配置、fail-fast 或旧预算重置行为。旧 Python 测试没有在本次运行。

新增 ParallelWorkflowCatalog 与纯展开/汇合模块；每项关联普通单节点检查点，在同一 RunRecordStore 中经现有 Worker 执行。父展开、子项初始记录和队列引用共用一笔条件事务。父等待释放占用，子项全部结束后由队列唤醒父节点；正常输出契约、路由、接纳和 CAS 继续生效。结构层不依赖 Docker、Harness、秘密来源或业务评分代码。

最大 62 项来自现有原子记录接口的 64 条条件限制；空 Map 合法，Fork 至少两个分支。队列索引更新至 v3，不支持开发 v1/v2 自动迁移。对业务而言没有嵌套子流程接口；内部单节点计划是复用现有恢复与调度接口的执行记录。

## 恢复后凭据等待的整组取消

在本地 89b5af4 复核 #16 时发现：#14 已允许取消清理完成后重新等待凭据的串行任务，但整组取消仍只检查子记录的历史 currentIdentity。先核对 Blackbox 5610d1b 的 runtime.cancel_run 和 storage.cancel_dispatch：待调度取消与活动执行的协作取消分别处理，记录与调度变更共同提交。这里复用本项目既有恢复完成事实及条件事务，不复制旧整 Run 调度或单凭租约到期认定停止。

用真实 Worker 子进程执行 Map：A 已接纳，B 执行期间 SIGKILL，恢复确认旧执行清理后通过合成准入端口返回凭据繁忙，C 尚未执行。修复前两个用例均在取消父组时抛出 QUEUE_TASK_ACTIVE。修复将串行和组内未领取项的停止判断归入同一私有函数；不新增状态、配置或授权接口。

修复后两个回归通过、零跳过（6.08 秒）：

- 清理完成的 B 可取消，严格加载保留原一个 Attempt，父组结束为 cancelled；不执行 C 或正常后继。补充将清理证明置为未完成的端口负对照，仍拒绝取消且原记录不变。
- 在取消事务提交前允许另一个 Worker 重新领取 B；原提交因版本冲突重新核对，保留新领取令牌及原检查点，仅设置协作取消，父组继续等待。

构建、测试类型、依赖边界及完整普通套件已执行：407 项中 403 通过，4 项既有 CONNECT 测试因执行沙箱禁止监听 127.0.0.1 报 listen EPERM，无跳过。随后在允许回环监听的环境只复核该代理文件，5 项全部通过（含上述 4 项），未改测试或产品逻辑来放宽检查。原失败日志保留，不能称首轮 npm run check 全绿。默认 E2E 为 17 通过、188 跳过；本次没有启用 Docker、官方模型或私有消费端验收，未将跳过计为通过。
