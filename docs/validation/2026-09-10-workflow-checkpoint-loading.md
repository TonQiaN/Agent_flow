## 实现与针对性检查

engine 严格加载存储信封、Workflow 状态与历史，正常执行和加载共用路由计算；实际执行定义匹配后，经一次性请求调用安装好的文件适配器。integrations 核对实际归档与脚本收据，使用新的临时存储 ID 保留原逻辑清单、token 和前序关联。加载和释放均不写 Run 状态、不调用 executor.execute 或 Runner query/stop。

最终针对性检查 31 项通过，包括 20 项已有检查点/串行流程回归与 11 项加载检查：覆盖正常、取消、失败、停止不明、路由与全局上限的实际写入历史，16 种非法字段/身份/值/路由/定义变更，JSON 值不一致、缺少恢复端口、getter 不执行、一次性请求、逆序回滚及清理失败后保留资源并重试。

新增的归档完成时取消测试先在旧写入实现上确定性失败：异步 saveValue 已把新值加入 writer，但对应接纳步骤尚未登记；此时取消可能保存不一致的检查点。对照 Blackbox 完整更新后提交的顺序，将异步归档准备和同步接纳登记分开，值与步骤在同一不含 await 的阶段登记。修复后实际产生的每个版本均通过严格加载；不以放宽加载校验处理不一致记录。

真实 Docker 的六项场景包含三项已有正常/中断/归档失败回归，以及三项新增加载检查：

- 新进程加载正常 A → B 的 SQLite 检查点。删除原输入和全部临时目录后，实际恢复 seed、seedA、seedAB；原逻辑清单、收据及前序保持一致，修改物化副本后再物化仍为原内容，重新保存也保留逻辑来源。释放后引用失效、临时目录为空，重新加载可成功。
- A 接纳、B 实际运行后 SIGKILL 宿主。保持捕获到的 B 容器运行，再由新进程恢复初始输入和 A 的已接纳文件；加载前后 Docker inspect 都显示该 B 仍运行，未启动额外节点，数据库内容和 revision 不变。只在测试结束时移除这个已捕获 ID 的测试容器。
- 对实际 A 收据与归档注入前序、镜像、Attempt、输入清单、文件大小、归档摘要及额外字段变更；随后注入真实文件等长篡改和丢失。每次新进程加载拒绝、不调用节点、不写数据库，并撤销此前已经恢复的初始引用。修复测试数据后重新加载成功。

第一次完整检查在依赖边界检查阶段停止：局部断言函数命名为 require，被现有静态检查器按动态模块加载识别。Blackbox 为 Python 项目，没有对应 TypeScript 检查器；本项目将局部函数改名为 valid 后边界检查通过，未放宽包依赖规则。
