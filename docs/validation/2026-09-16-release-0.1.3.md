## CI 暴露的容量测试时序问题

首个 head `123cf27bf24b87a809539484cbe1cc59a382d8e4`：push 检查 [35069750197](https://github.com/TonQiaN/Agent_flow/actions/runs/35069750197) 的 Node 24/26 均通过；PR 检查 [35069827008](https://github.com/TonQiaN/Agent_flow/actions/runs/35069827008) 的 Node 26 在 `independent real Worker processes respect the parallel node cap` 出现 `QUEUE_CLAIM_LOST`，普通测试 414 通过、1 失败，Docker E2E 118 通过、87 跳过、0 失败。Node 24 被矩阵 fail-fast 取消，不能记为另一个测试失败或通过。

先限定查阅 Blackbox `5610d1b` 的 `tests/test_scheduler.py` 和 `tests/test_parallel_runtime.py`：正常多 Worker 容量使用 barrier/正常租约，专门过期恢复用例显式缩短租约。该项目为 Python whole-workflow Worker，本项目为 TypeScript NodeTask Worker，借鉴测试职责分开，不复制实现或通过结论。

本项目并行容量测试复用了 SIGKILL 夹具的 900ms 租约。在两个已通过 IPC 确认进入业务的 Worker 收到继续信号后，加入 1100ms 同步停顿，旧 900ms 配置确定复现同一 `QUEUE_CLAIM_LOST`（1 项失败）。仅该容量用例改为正常 30000ms 租约，保留停顿；容量、第三个 Worker 不可领取、完成结果等原断言保留。共享夹具默认仍是 900ms，SIGKILL 和恢复用例不变；生产 Worker、heartbeat、领取归属和过期拒绝全部不变。

修正后独立并行进程测试 5 项全部通过（含两种 SIGKILL 恢复和两种取消竞争）；完整 `npm run check` 再次退出 0，普通测试 415 通过、默认 E2E 17 通过/188 跳过、0 失败。最终 head CI 回执继续在 PR 维护，提交后重跑远端 Docker 矩阵。元数据、外部依赖及本地链接重新核对通过。不以简单重跑得到绿色代替定位。
