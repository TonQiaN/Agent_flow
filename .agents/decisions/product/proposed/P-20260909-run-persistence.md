# 运行状态持久化与恢复协调分离

创建于 2026-09-09。

## 结论与边界

按 #13 已确认范围，首期支持相同定义和环境下的节点边界恢复。存储保存事实，恢复模块读取事实后经 Runner 的共同接口核对/停止旧执行，再进入正常执行及路由；二者不解析 Harness 日志，也不各自建立业务状态机。已接纳结果复用，同一 NodeTask 中断后用新 Attempt，用户路由再入节点才产生新 NodeTask。失败/取消不是自动恢复请求。

单机状态使用 SQLite 事务，WAL、FULL 同步和有限忙等待，参考旧实现的事务边界；具体 SQLite 类型只在 integrations，engine 依赖 RunRecordStore 端口。第一切片提供带 revision 的 Run JSON 记录及 compare-and-swap，作为引擎后续快照的保存基础，不单独定义第二套 NodeTask 状态机或通用事件溯源。每次写入只做有限本地事务，事务内没有执行、网络或文件产物复制。冲突拒绝旧版本更新，未知 schema/损坏记录拒绝读取；不自动迁移、静默重建或删除错误记录。

存储记录的内部结构由引擎快照版本负责；存储只检查 JSON、大小、标识和完整性。CAS 防止覆盖较新的记录，不证明旧容器已经停止，也不能代替执行占用和恢复协调。保存引擎快照时必须保留 Attempt 历史，不能把 CAS 更新解释为允许覆盖历史身份。输入/产物须先复制到耐久位置并核对摘要，之后才提交结果接纳和后续路由事实；结果接纳与下一任务创建要有同一事务或可幂等完成的阶段记录。文件存储与数据库的组合仍须故障注入验证，不能以单一 JSON 行提交成功宣称产物耐久已完成。

耐久产物采用独立 ArtifactArchive 端口；临时 ArtifactStore 的 release 仍只清理临时快照，二者不能作为可互换实现注入。归档先复用同一套文件复制与 contract 校验，再同步文件、树目录和带版本清单，原子发布到唯一目录，最后同步归档根。返回绑定清单摘要的引用后，调用者才可提交 Run 状态；归档成功而数据库提交失败可以留下未引用数据，首期不自动 GC，避免误删并发恢复仍需要的产物。宿主受信目录下发生进程崩溃时，未发布 staging 不可由正式引用读取；已发布目录不可由临时句柄释放。读取校验引用、清单结构/层级和摘要，物化逐文件核对摘要，输出为独立可写副本。此接口不接纳节点结果、不自动恢复任务，也不提供跨磁盘事务或控制宿主者的防篡改保证。

Run 保存定义、Component/contract、用户说明、行为配置及输入快照。认证只保存 Profile 引用和非秘密连接身份，不存 token/key；存储不能靠猜测任意 JSON 文本识别秘密，这一边界由受信快照构造与认证端口落实。正常刷新不使定义失效；关键定义、实现/镜像身份或资源变化则明确阻塞。首期不重建历史环境或迁移旧流程。

恢复定义分成结构/契约与执行绑定两部分核对：结构从已编译的受信计划提取，contract 从实际注册表复制，包含文件 contract 引用的 JSON schema；不能由调用者另交一份声称相同的配置替代。编译时保留这些定义，后续替换 catalog 方法不应改变该计划的快照。支持旧自定义 executor 不提供结构快照，但持久化检查遇到缺失定义必须拒绝，不把缺失内容当作匹配。相同类型与 ID 在同一流程中必须对应一致定义，JSON 对象键顺序不构成变化，数组和具体约束保守按实际内容核对。结构匹配只证明拓扑、Component 元数据及契约一致，不证明任意函数闭包、模型、镜像或认证身份一致；执行绑定描述与恢复协调仍需后续单独接入，不因结构快照可保存而开放任务恢复。

执行绑定先贯通确定性、断网脚本路径：描述从 ScriptExecutor 的实际 argv/期限/出口与 DockerBackend 的已校验选项取得，解析并冻结实际镜像 ID 后，后续执行必须使用同一 ID。恢复安装重新解析得到的描述与保存内容比较，变化拒绝；不能仅记录可变 tag 再让执行重新选择。快照获取不启动容器或分配工作目录；已有资源时不追认冻结，缺失描述的旧 backend 仍可普通执行，但不能提供持久化证据。首个实现对带私有绑定、交互或联网的 backend 明确不可用，不用空描述冒充其认证/代理身份；这些路径与函数版本描述后续继续贯通。

正常执行先接入共享 Workflow 检查点写入路径：初始输入归档并创建 Run 记录后才返回持久运行句柄；节点调用前保存当前身份，已校验输出经实际 executor 的值保存端口归档后，接纳结果、路由计数和后续位置一起通过 CAS 提交，再执行后继。快照中的文件引用只作为进程内关联 token，必须同时保存对应耐久文件记录与可信来源收据，不能单独保存引用字符串。异步归档准备不能提前把值放入可提交的 Run 记录；值与对应接纳步骤在同一同步阶段登记，避免取消在两者之间持久化不完整关系。存储错误或版本冲突停止后续调度，不能把仅内存中成功当成持久成功。持久运行的取消提供异步确认，取消意图提交完成后才返回成功；普通进程内句柄保留原行为。此阶段允许写出可检查的记录，但在 Runner 资源身份恢复与完整快照校验接通前不开放重启执行入口。

检查点加载先读取受信 RunRecordStore，严格核对版本、字段、Run/步骤身份、当前值及值记录的对应关系，并复用正常路由计算校验历史和后续位置，再与实际安装的执行定义比较。文件恢复请求由通过上述核对的引擎加载器签发一次性进程内能力；Catalog 不接受任意 JSON 作为可信收据导入。文件归档逐项重新验证并复制到新的临时快照，原逻辑清单与前序收据保持关联，临时存储句柄单独管理。加载失败撤销本次已建立的引用，清理未完成须保留可重试收尾能力；加载完成也只提供可检查数据和释放句柄，不替代恢复执行所有权、旧资源停止或 Run 状态 CAS。

Runner 的持久资源端口在 allocate 后、prepare/create/start 前保存由实际 backend 生成的资源描述及完整执行身份；保存失败不能创建或启动容器。恢复只使用受信存储记录并核对实际环境，通过共同 Runner 句柄查询、停止和移除旧资源，不重新启动旧会话，也不把旧输出直接接纳。Docker 资源描述须绑定唯一容器名、完整 Run/NodeTask/Attempt、固定镜像和私有工作目录；存在目录的清理由本次资源标记证明归属，目录已丢失不等于容器停止。created 状态也可能仍有未完成启动命令，恢复收尾必须确认旧容器移除后才能报告完成。停止或归属不明时保留记录和目录以便重试；资源恢复能力不替代 Workflow 的 CAS 恢复所有权和新 Attempt 调度。

正常 Workflow 调用通过每次调用独立的宿主端口，把实际 Runner 资源保存到该 Attempt 的同一 CAS 检查点；端口不进入任务 JSON、不使用可跨 Run 覆盖的全局回调。Attempt 开始即登记身份，资源保存绑定当前节点和完整身份，接纳或明确失败后以步骤索引关联既有结果，不重复存储业务输出。保存端口在调用结束后失效，重复或跨身份资源拒绝，写入失败继续阻止创建与后继执行。检查点格式随 Attempt 记录升级，加载器同步严格校验；未发布的旧试验格式不自动升级为具备新资源证据的记录。此记录仍不证明恢复取得所有权或旧宿主已被隔离，完整中断恢复继续通过共同 Runner 和正常路由完成。

Runner 的准备、创建和启动还须分别先提交 pending；准备/创建调用成功后提交 completed，启动还必须经共同 observe 首次确认 running 或 exited 后才提交 completed，不能以异步 start 返回代替，状态随当前 Attempt 保存并按固定顺序推进；回调失败阻止尚未调用的操作，操作抛错或完成事实未提交时保留 pending，不能由一次 absent 查询、宿主退出或时间推算其完成。该有限操作记录是后续恢复争用的前提，不是另一个调度器或租约：恢复取得 CAS 所有权之前不能操作，pending 也不能自动视为可接管。它刻意不照搬 Blackbox 的整 Run flock；文件锁释放与远端 Docker 命令结束是两类事实。当前先落实正常执行的记录与故障语义，恢复协调及未知操作的核对仍需独立验证。

恢复协调先复用严格加载器校验原检查点与产物，再以同一 Run 行的 CAS 写入独立恢复封套，保留原业务快照，记录 claim revision 和旧资源移除确认；普通旧写入者不能覆盖新 revision。恢复封套不是新的业务状态机，恢复尚未执行新 Attempt 时也不改写其结果。原严格加载器同时只读检查普通快照和恢复封套，并返回独立的恢复进度；读取不隐含新认领或容器操作。首期拒绝取消/失败/终态及 pending 启动操作的自动接管，缺少资源恢复能力时拒绝；正常 Script 在资源保存前尚不能发出 Docker 操作，资源保存后的非 pending 状态才进入共同 Runner 核对/停止/移除。两个恢复者按各自读取的同一 revision 竞争，后续接管可产生新 claim；旧句柄的迟到写入拒绝，不能恢复其调度权。共同清理只针对旧不可复用资源身份，完成确认通过 CAS 提交后才可作为后续新 Attempt 的前提；清理不明保留 pending 恢复记录并允许重试，不删除记录或自动重发任务。新 Attempt 调度继续使用正常执行路径，单独完成恢复准备不代表全流程恢复已验收。

恢复执行只消费恢复协调器签发的一次性进程内交接能力，绑定实际 compiled、存储、最后已确认 revision 和已恢复文件引用；query 副本、模型 JSON、复制或重复句柄均不能启动。交接之后由共享 WorkflowRuntime 和 CheckpointWriter 先 CAS 恢复运行记录，再进入原检查、执行、接纳与路由路径；CAS 失效不调用节点。旧活动 Attempt 在确认资源移除后标记 interrupted，原身份、资源和 launch 事实保留；同一 NodeTask 新 Attempt 编号递增，已接纳步骤/用户路由计数不因中断而增加。路由再入节点仍产生新的 NodeTask。已接纳值沿原收据与文件能力复用，不重跑前序节点；交接释放责任转到恢复运行句柄，结束前不能撤销仍在使用的输入引用。检查点版本与严格历史校验同步更新，不自动迁移旧试验记录；新 Attempt 执行验证与全部 #13 绑定/未知操作的验收仍分别记录。

Agent 执行定义由实际 AgentExecutor/Driver 与认证执行组合逐层导出，包含用户说明、实际 Harness 计划和版本、注入的运行资产、期限、非秘密 Profile 与认证传输方式，以及同一 Docker 配置和固定的执行/代理镜像 ID。读取定义不获取凭据租约、不读 token/key、不运行版本探针或容器；镜像解析成功后，后续实际版本探针和执行使用该固定镜像，代理也使用同一固定 ID。正常凭据内容刷新不进入定义比较；Profile 服务、endpoint、引用或行为配置改变须不匹配。缺少实际描述能力的旧自定义 Driver 仍可普通执行，但不能提供持久化定义；定义可比较不等于私有凭据占用或 Agent 资源已可恢复，不能提前开放其 Run 恢复。

联网 Script 的资源恢复把任务容器、出口代理和内外两张网络视为同一不可复用 Runner 资源的组成部分，名称由该资源 ID 确定，并在创建时标注完整 Run/NodeTask/Attempt 身份。恢复从实际网络配置、固定代理镜像与代理程序摘要取得一致性证据；查询错误不能当作缺失，同名异属资源不操作。旧任务容器不存在也须核对并移除其代理和网络；只有共同 remove 逐项确认缺失后才允许释放工作目录和记录恢复清理完成。恢复句柄只重建管理关系，不重建或启动网络/代理。准备阶段冻结的代理程序字节实际用于创建，避免描述与执行换用不同文件；私有认证绑定与交互仍需独立证据，不因网络可恢复就自动开放 Agent 恢复。

Agent 版本探针作为认证获取前独立的 Runner 调用，资源证据不能被后续模型执行资源覆盖。认证组合提供独立的探针资源记录端口，复用 Runner 的保存及启动日志；记录拒绝不得继续获取凭据。探针实际版本、固定镜像、命令和期限由当前组合导出；恢复只取得同一断网环境的管理句柄，不重新运行探针或读取凭据。确认版本成功且资源释放后，须等待调用者的阶段完成记录再获取凭据；完成记录拒绝保持失败，不将探针成功当作整个 Agent 可恢复。此端口本身不授予跨进程认领权，Workflow 的多资源阶段与认证占用仍需后续接入。

不可变环境凭据的执行资源可在源存储短租约已释放后保存。资源定义只包含凭据引用/服务/方式及环境变量名称，不保存密钥、内容摘要或存储版本；恢复使用宿主安装的只管理绑定，不读取源存储、不恢复秘密环境、不写回旧密钥，轮换或删除不会被撤销。实际绑定与只管理绑定须产生一致定义，后者拒绝 prepare/secretEnvironment，只在共同 Runner 确认资源移除后参与释放。资源身份、固定执行/代理镜像、代理代码摘要和完整网络清理仍沿已有规则核对。探针与模型执行使用分开的记录端口；获取凭据期间尚无已保存执行资源时不能推断短租约已释放，订阅独占占用及未知操作仍拒绝自动接管。该阶段先验证不可变 API key 的资源恢复，不提前开放完整 Agent 的 Workflow 恢复。

一个 Attempt 可以按安装时声明的有限顺序拥有多个资源阶段，中间也可包含无 Runner 资源的宿主操作阶段。阶段计划作为实际执行快照的一部分保存；引擎只认识资源/操作及顺序，不认识凭据或 Harness。进入阶段、保存资源、启动日志和阶段完成都须等待同一 Run CAS；前一阶段未完成不能进入后一阶段，迟到或重复回调不能继续执行。资源阶段仍复用共同 Runner 记录；操作阶段未完成或启动 pending 时拒绝自动恢复。恢复先严格校验阶段计划/身份/历史，再在原认领范围内逆序确认全部旧资源已移除，才交给正常新 Attempt；已完成业务节点不重跑，阶段不消耗业务路由次数。接纳要求声明阶段全部完成，不能把未完成的资源操作包装为业务成功。旧单资源路径保留，检查点和执行快照随新增事实升版，旧试验记录不自动迁移。

实际 Agent 接入通用阶段时，由 Driver 声明版本资源、凭据获取操作和执行资源，Engine 不引入认证字段。认证运行器在获取前等待 enter，在不可变环境快照的源短租约释放后等待 complete；任一记录失败阻止执行，已获得的内存绑定须放弃。订阅占用没有对应恢复证据时不声明资源计划，仍可描述实际安装，但不能持久启动。版本阶段确认成功并释放后完成；执行阶段由正常输出接纳后的执行释放完成，不能在输出扫描前删除其目录。恢复通过各阶段实际共同 Runner 清理，不获取凭据或重新解释旧模型记录。

探针和 Driver 的输入物化应优先复用已登记的 Runner 工作目录，避免新建无法随资源恢复定位的外部 scratch。Runner 的 null 输入在 Docker 下表示空输入或显式安装的宿主物化能力；能力不进入请求 JSON/资源记录，不从检查点反序列化，也不改变固定容器路径。资源保存及 prepare pending 提交后，物化先在该资源目录内生成副本，再经原输入复制校验得到可写 input；部分物化、原子改名暂存和失败残留都归共同资源释放所有。文件路径输入与物化能力不能同时指定；方法在运行前固定，旧资源恢复不需要原物化能力。Driver 因此只接收 timeoutMs，移除无职责的 inputRoot；版本探针直接使用已拥有的空 input。实际物化、资源确认与恢复清理须验证来源/相邻目录不受影响，不通过扫描前缀推断所有权。Catalog 与 ArtifactStore 在 Runner 外的其他临时目录、分配但尚未写入记录的窗口仍需独立处理。

同一实际 ArtifactStore 由 Catalog 与 AgentExecutor 共同安装时，可通过存储可选的 inspect 能力借用已存在的进程内快照，跳过 Catalog 的 node 输入物化和 Agent 的重复输入捕获。描述只能由实际存储私有登记返回副本，执行重新核对快照 ID 与契约，Driver 物化仍校验文件摘要；不接受外部清单导入，也不从 JSON 路径推断快照。恢复后使用当前存储的物理 ID，历史逻辑清单与收据内容关系不变。不同存储或无此能力仍走独立物化/捕获路径。借用输入不归 Agent releaseExecution 删除，Catalog 在调用期间保留引用；若停止尚未确认，保留到共同清理成功，禁止调用方提前释放。此优化消除同存储 Agent 执行的冗余目录和输入快照，不声称解决 checkpoint/restore 暂存、旧进程初始/已接纳临时快照或资源分配未登记窗口。

检查点与恢复的文件交接优先使用目标存储可选的 captureMaterialized 端口：受信宿主安装的物化方法在异步操作前固定，只把独立副本写入目标存储本次分配的私有暂存范围，方法与路径不进入持久记录。目标存储复用相同的大小、摘要、媒体/JSON、contract 和读取稳定性检查，对已物化文件原位读取校验及同步，不再复制一遍；目录/文件还须满足当前用户和私有权限。临时存储私有句柄同时记住整个暂存范围，release 统一清理文件与相邻暂存；归档仍按原同步/原子发布顺序提交数据，再返回耐久引用。Catalog 不需要另建 checkpoint/restore 目录，但仍比较清单内容并维护逻辑收据。旧端口实现保留原路径回退；同存储重叠物化仍拒绝。该能力只消除中间副本，不证明 SIGKILL 后未发布暂存或旧进程快照可自动回收；这些资源不通过路径前缀或进程消失认领。

Agent 文件收据只可随严格加载器的一次性文件恢复能力验证，不提供进程内 Agent receipt 导入。先沿 Workflow 前序文件引用核对归档/清单，再核对完整执行身份、组件、outcome、实际 Driver 给出的 Harness/版本/固定镜像及 Agent 输入/输出清单；File Catalog 以源文件或实际存储快照调用 Agent，因此内层 predecessor 必须为空，外层前序关系仍完整保存。来源收据不替代输出 contract 检查，不把旧输出重新走接纳流程。阶段资源已停止的证据也不证明探针、Driver 或 Catalog 的宿主临时目录已经清理；这些目录的崩溃收尾另行落实并如实保留验收缺口。

Effect 的逻辑操作记录独立于 Run/Attempt 行：键绑定 Component/实现、业务身份、目标和规范化完整输入，不能因新 Attempt 更换逻辑键。可选 EffectRecordStore 只负责版本化 JSON 与 create/CAS，不调用外部服务；本机实现复用既有 SQLite 耐久与并发机制，以持久命名空间身份区分不同存储。执行器消费本次明确授权后先提交唯一 pending 记录，成功确认后才调用 apply；收据和输出 contract 校验通过，再 CAS 保存 applied，提交确认后才向调用方接纳。已有 applied 经身份、请求、输入及契约重查后可在新进程复用；pending 不证明未执行，缺少结果核对能力时返回 unknown 并拒绝再次 apply。提交回执丢失时也不以当前内存替代持久事实。dry-run 不读取或占用日志；重启不会复活旧授权。操作日志不提供解除未知、删除占位或任意回执导入接口，不能用于宣称任意外部服务 exactly-once。此切片先验证真实宿主中断后的独立 Effect 执行器，Workflow 执行定义、恢复认领和操作接线另行完成。

Effect Workflow 的首个恢复组合使用明确的固定 target/key 描述与 apply 模式，实际服务适配器提供版本化执行描述，快照同时绑定持久操作命名空间身份；任意宿主映射函数仍可普通执行，但缺少可比较描述时拒绝持久启动，不把函数源码或旧授权序列化为执行依据。加载已接纳 Effect 时沿严格加载器的一次性请求，把前序输入、实际操作映射、outcome 和完整回执与操作日志的 applied 事实核对。活动 Effect 恢复在 Run CAS 认领前只读核对日志，pending 明确阻塞；无占位或已有可靠回执才允许共享正常新 Attempt 路径，最终仍由唯一占位防止旧宿主和恢复者重复调用。恢复核对不签发授权，正常调用仍要求当前宿主明确授权，旧 Run 迟到结果继续被 CAS 拒绝。此组合不增加外部服务查询平台或隐式重试未知操作。

恢复并发必须通过事务状态和执行所有权约束协调；在资源未核对/停止前不启动第二份，不以 PID 消失或超时作为执行停止证明。旧 Blackbox 整 Run 锁不直接固定为将来的 Worker 独占模型，NodeTask 级调度留给 #14。Effect 缺少可靠回执时保持 unknown，按其核对能力处理，不能直接重发。

确定性 JSON 函数的恢复以安装时明确的实现版本与可重算约定为前提。FunctionRegistry 另提供确定性登记：实现包自身声明版本，宿主传入实际行为配置，登记时复制配置并捕获执行函数；该函数只接收独立 JSON 输入及独立配置，不接收 Attempt 身份。版本和配置进入实际执行快照，版本须随实现及依赖的行为变化更新。这是受信代码安装者承担的约定，不是对任意闭包、依赖或纯度的自动证明；普通函数、依赖可变外部状态或具有副作用的函数不能据此恢复，外部写入仍走 Effect。禁止以函数名、toString 或从保存 JSON 重建函数代替安装绑定。

无资源的确定性 JSON 调用通过显式只读恢复检查接入共同恢复协调；不存在旧 Runner 资源或操作阶段才允许继续，未知启动仍拒绝。恢复重算尚未接纳的节点，使用同一 NodeTask 的新 Attempt；先前已接纳步骤不重算。旧宿主函数可能仍在计算，因此此模式只适用于无外部写入的纯计算；Run CAS 拒绝其迟到结果，不能把 CAS 当作停止任意宿主代码。文件函数及其写入目录不能直接套用该无资源约定，需另行满足实际绑定与资源边界。

批卷文件 Script 的应用代码来自当前安装的同一份评分实现，生成后的实际程序字节、固定参数和期限沿 ScriptDefinition 进入执行快照；不复制另一份评分规则，也不通过函数 toString 获取闭包。原始来源摘要在构造调用前校验并复制，作为独立 argv 数据参数传入，不插入 shell 或当作代码执行。恢复仍重新安装当前程序并比较完整 Script 定义，源码变化不得静默混用；保存命令不是从历史记录自动执行代码的授权。输入文件只供业务处理，不能覆盖独立传入的原始摘要。该切片仅提供文件节点的实际 Script 绑定，整条批卷的启动/重开与来源事实取得仍须联合验收。

持久化批卷验收优先采用已有可恢复的 Script/Runner 实现文件 intake 与 Gate，不把所有普通宿主文件回调的自动恢复作为第一版前置。宿主文件回调仍可普通执行；不能仅添加 revision 就视为可以核对或停止旧执行。这个实现选择保持 #9 的 Component/contract 与路由接口，不新增通用宿主进程管理器。确定性 JSON 的明确无副作用约定不能直接扩大到文件写入回调。

应用验收组合还须消除仅存在内存的恢复依赖：原始来源清单在 Run 启动前形成耐久、可核对事实，恢复不能从已变化的原始宿主文件重算；文件到 JSON 的接纳输出须保留并核对其前序文件、outcome、身份和转换收据，不能靠重跑已接纳转换重新造凭证。发布审批仍是当前宿主策略，由可信恢复后的来源链提供依据，不恢复旧授权。固定 target/key 与独立 Effect 日志沿已有接口接入；批卷应用的业务评分和审批判断不进入引擎。具体接线与故障验证完成前，应用组合继续标为未支持持久恢复。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| SQLite 事务 + 文件产物 + 引擎恢复端口 | 参考项目已有单机事务经验；支持并发 CAS 与多记录提交 | 文件/数据库提交仍需明确顺序；同步接口会短暂占用宿主线程 | 首期采用，先验证状态保存，再接产物与恢复 |
| 仅原子替换 JSON 文件 | 简单，单文件读写直观 | 多进程版本更新、接纳/调度的原子性需另造协议 | 不作为主运行状态存储 |
| 直接搬运旧整 Run 恢复锁 | 旧例子可限制同 Run 并发 | 不等价于新 NodeTask/Attempt 与后续队列边界 | 参考校验点，不直接固定执行所有权模型 |
| 通用事件溯源、跨版本环境迁移 | 可保留更丰富历史和重建环境 | 超出已确认首期场景及复杂度要求 | 不采用 |

## 影响与验证

存储实现和 SQLite 依赖留在 integrations，engine 只导出端口、记录版本和标准错误。私有状态目录由宿主显式指定，不搜索桌面配置；POSIX 根目录与数据库/已有 sidecar 要满足当前用户、私有权限、普通文件及非链接条件，根外祖先由宿主管理。数据摘要只检出意外损坏，不是对控制宿主者的真实性证明。

先验证完整写入、重开、重复创建、两个进程争用同一版本、写入前后 SIGKILL 的原子性、损坏/未知格式拒绝。随后联合引擎和 Runner 验证已完成 A 不重跑、旧 B 状态不明时阻塞、确认停止再执行、产物丢失/损坏、定义变化、取消/失败与 Effect unknown。单独存储检查不证明整个 #13 可恢复，机器重启和硬件断电需按实际证据记录。

## 重开条件

单机范围变化、必须跨版本恢复、事务耗时不适合当前宿主、文件/状态提交边界无法满足验收，或新证据表明存储/恢复边界不足时重新评估；普通字段布局和错误码不另起重大架构讨论。
