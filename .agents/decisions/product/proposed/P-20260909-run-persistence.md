# 运行状态持久化与恢复协调分离

创建于 2026-09-09。

## 结论与边界

按 #13 已确认范围，首期支持相同定义和环境下的节点边界恢复。存储保存事实，恢复模块读取事实后经 Runner 的共同接口核对/停止旧执行，再进入正常执行及路由；二者不解析 Harness 日志，也不各自建立业务状态机。已接纳结果复用，同一 NodeTask 中断后用新 Attempt，用户路由再入节点才产生新 NodeTask。失败/取消不是自动恢复请求。

单机状态使用 SQLite 事务，WAL、FULL 同步和有限忙等待，参考旧实现的事务边界；具体 SQLite 类型只在 integrations，engine 依赖 RunRecordStore 端口。第一切片提供带 revision 的 Run JSON 记录及 compare-and-swap，作为引擎后续快照的保存基础，不单独定义第二套 NodeTask 状态机或通用事件溯源。每次写入只做有限本地事务，事务内没有执行、网络或文件产物复制。冲突拒绝旧版本更新，未知 schema/损坏记录拒绝读取；不自动迁移、静默重建或删除错误记录。

存储记录的内部结构由引擎快照版本负责；存储只检查 JSON、大小、标识和完整性。CAS 防止覆盖较新的记录，不证明旧容器已经停止，也不能代替执行占用和恢复协调。保存引擎快照时必须保留 Attempt 历史，不能把 CAS 更新解释为允许覆盖历史身份。输入/产物须先复制到耐久位置并核对摘要，之后才提交结果接纳和后续路由事实；结果接纳与下一任务创建要有同一事务或可幂等完成的阶段记录。文件存储与数据库的组合仍须故障注入验证，不能以单一 JSON 行提交成功宣称产物耐久已完成。

耐久产物采用独立 ArtifactArchive 端口；临时 ArtifactStore 的 release 仍只清理临时快照，二者不能作为可互换实现注入。归档先复用同一套文件复制与 contract 校验，再同步文件、树目录和带版本清单，原子发布到唯一目录，最后同步归档根。返回绑定清单摘要的引用后，调用者才可提交 Run 状态；归档成功而数据库提交失败可以留下未引用数据，首期不自动 GC，避免误删并发恢复仍需要的产物。宿主受信目录下发生进程崩溃时，未发布 staging 不可由正式引用读取；已发布目录不可由临时句柄释放。读取校验引用、清单结构/层级和摘要，物化逐文件核对摘要，输出为独立可写副本。此接口不接纳节点结果、不自动恢复任务，也不提供跨磁盘事务或控制宿主者的防篡改保证。

Run 保存定义、Component/contract、用户说明、行为配置及输入快照。认证只保存 Profile 引用和非秘密连接身份，不存 token/key；存储不能靠猜测任意 JSON 文本识别秘密，这一边界由受信快照构造与认证端口落实。正常刷新不使定义失效；关键定义、实现/镜像身份或资源变化则明确阻塞。首期不重建历史环境或迁移旧流程。

恢复定义分成结构/契约与执行绑定两部分核对：结构从已编译的受信计划提取，contract 从实际注册表复制，包含文件 contract 引用的 JSON schema；不能由调用者另交一份声称相同的配置替代。编译时保留这些定义，后续替换 catalog 方法不应改变该计划的快照。支持旧自定义 executor 不提供结构快照，但持久化检查遇到缺失定义必须拒绝，不把缺失内容当作匹配。相同类型与 ID 在同一流程中必须对应一致定义，JSON 对象键顺序不构成变化，数组和具体约束保守按实际内容核对。结构匹配只证明拓扑、Component 元数据及契约一致，不证明任意函数闭包、模型、镜像或认证身份一致；执行绑定描述与恢复协调仍需后续单独接入，不因结构快照可保存而开放任务恢复。

执行绑定先贯通确定性、断网脚本路径：描述从 ScriptExecutor 的实际 argv/期限/出口与 DockerBackend 的已校验选项取得，解析并冻结实际镜像 ID 后，后续执行必须使用同一 ID。恢复安装重新解析得到的描述与保存内容比较，变化拒绝；不能仅记录可变 tag 再让执行重新选择。快照获取不启动容器或分配工作目录；已有资源时不追认冻结，缺失描述的旧 backend 仍可普通执行，但不能提供持久化证据。首个实现对带私有绑定、交互或联网的 backend 明确不可用，不用空描述冒充其认证/代理身份；这些路径与函数版本描述后续继续贯通。

正常执行先接入共享 Workflow 检查点写入路径：初始输入归档并创建 Run 记录后才返回持久运行句柄；节点调用前保存当前身份，已校验输出经实际 executor 的值保存端口归档后，接纳结果、路由计数和后续位置一起通过 CAS 提交，再执行后继。快照中的文件引用只作为进程内关联 token，必须同时保存对应耐久文件记录与可信来源收据，不能单独保存引用字符串。异步归档准备不能提前把值放入可提交的 Run 记录；值与对应接纳步骤在同一同步阶段登记，避免取消在两者之间持久化不完整关系。存储错误或版本冲突停止后续调度，不能把仅内存中成功当成持久成功。持久运行的取消提供异步确认，取消意图提交完成后才返回成功；普通进程内句柄保留原行为。此阶段允许写出可检查的记录，但在 Runner 资源身份恢复与完整快照校验接通前不开放重启执行入口。

检查点加载先读取受信 RunRecordStore，严格核对版本、字段、Run/步骤身份、当前值及值记录的对应关系，并复用正常路由计算校验历史和后续位置，再与实际安装的执行定义比较。文件恢复请求由通过上述核对的引擎加载器签发一次性进程内能力；Catalog 不接受任意 JSON 作为可信收据导入。文件归档逐项重新验证并复制到新的临时快照，原逻辑清单与前序收据保持关联，临时存储句柄单独管理。加载失败撤销本次已建立的引用，清理未完成须保留可重试收尾能力；加载完成也只提供可检查数据和释放句柄，不替代恢复执行所有权、旧资源停止或 Run 状态 CAS。

Runner 的持久资源端口在 allocate 后、prepare/create/start 前保存由实际 backend 生成的资源描述及完整执行身份；保存失败不能创建或启动容器。恢复只使用受信存储记录并核对实际环境，通过共同 Runner 句柄查询、停止和移除旧资源，不重新启动旧会话，也不把旧输出直接接纳。Docker 资源描述须绑定唯一容器名、完整 Run/NodeTask/Attempt、固定镜像和私有工作目录；存在目录的清理由本次资源标记证明归属，目录已丢失不等于容器停止。created 状态也可能仍有未完成启动命令，恢复收尾必须确认旧容器移除后才能报告完成。停止或归属不明时保留记录和目录以便重试；资源恢复能力不替代 Workflow 的 CAS 恢复所有权和新 Attempt 调度。

正常 Workflow 调用通过每次调用独立的宿主端口，把实际 Runner 资源保存到该 Attempt 的同一 CAS 检查点；端口不进入任务 JSON、不使用可跨 Run 覆盖的全局回调。Attempt 开始即登记身份，资源保存绑定当前节点和完整身份，接纳或明确失败后以步骤索引关联既有结果，不重复存储业务输出。保存端口在调用结束后失效，重复或跨身份资源拒绝，写入失败继续阻止创建与后继执行。检查点格式随 Attempt 记录升级，加载器同步严格校验；未发布的旧试验格式不自动升级为具备新资源证据的记录。此记录仍不证明恢复取得所有权或旧宿主已被隔离，完整中断恢复继续通过共同 Runner 和正常路由完成。

Runner 的准备、创建和启动还须分别先提交 pending；准备/创建调用成功后提交 completed，启动还必须经共同 observe 首次确认 running 或 exited 后才提交 completed，不能以异步 start 返回代替，状态随当前 Attempt 保存并按固定顺序推进；回调失败阻止尚未调用的操作，操作抛错或完成事实未提交时保留 pending，不能由一次 absent 查询、宿主退出或时间推算其完成。该有限操作记录是后续恢复争用的前提，不是另一个调度器或租约：恢复取得 CAS 所有权之前不能操作，pending 也不能自动视为可接管。它刻意不照搬 Blackbox 的整 Run flock；文件锁释放与远端 Docker 命令结束是两类事实。当前先落实正常执行的记录与故障语义，恢复协调及未知操作的核对仍需独立验证。

恢复协调先复用严格加载器校验原检查点与产物，再以同一 Run 行的 CAS 写入独立恢复封套，保留原业务快照，记录 claim revision 和旧资源移除确认；普通旧写入者不能覆盖新 revision。恢复封套不是新的业务状态机，恢复尚未执行新 Attempt 时也不改写其结果。原严格加载器同时只读检查普通快照和恢复封套，并返回独立的恢复进度；读取不隐含新认领或容器操作。首期拒绝取消/失败/终态及 pending 启动操作的自动接管，缺少资源恢复能力时拒绝；正常 Script 在资源保存前尚不能发出 Docker 操作，资源保存后的非 pending 状态才进入共同 Runner 核对/停止/移除。两个恢复者按各自读取的同一 revision 竞争，后续接管可产生新 claim；旧句柄的迟到写入拒绝，不能恢复其调度权。共同清理只针对旧不可复用资源身份，完成确认通过 CAS 提交后才可作为后续新 Attempt 的前提；清理不明保留 pending 恢复记录并允许重试，不删除记录或自动重发任务。新 Attempt 调度继续使用正常执行路径，单独完成恢复准备不代表全流程恢复已验收。

恢复并发必须通过事务状态和执行所有权约束协调；在资源未核对/停止前不启动第二份，不以 PID 消失或超时作为执行停止证明。旧 Blackbox 整 Run 锁不直接固定为将来的 Worker 独占模型，NodeTask 级调度留给 #14。Effect 缺少可靠回执时保持 unknown，按其核对能力处理，不能直接重发。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| SQLite 事务 + 文件产物 + 引擎恢复端口 | 参考项目已有单机事务经验；支持并发 CAS 与多记录提交 | 文件/数据库提交仍需明确顺序；同步接口会短暂占用宿主线程 | 首期采用，先验证状态保存，再接产物与恢复 |
| 仅原子替换 JSON 文件 | 简单，单文件读写直观 | 多进程版本更新、接纳/调度的原子性需另造协议 | 不作为主运行状态存储 |
| 直接搬运旧整 Run 恢复锁 | 旧例子可限制同 Run 并发 | 不等价于新 NodeTask/Attempt 与后续队列边界 | 参考校验点，不直接固定执行所有权模型 |
| 通用事件溯源、跨版本环境迁移 | 可保留更丰富历史和重建环境 | 超出已确认首期场景及复杂度要求 | 不采用 |

## 影响与验证

存储实现和 SQLite 依赖留在 integrations，engine 只导出端口、记录版本和标准错误。私有状态目录由宿主显式指定，不搜索桌面配置；POSIX 根目录与数据库/已有 sidecar 要满足当前用户、私有权限、普通文件及非链接条件，根外祖先由宿主管理。数据摘要只检出意外损坏，不是对控制宿主者的真实性证明。

先验证完整写入、重开、重复创建、两个进程争用同一版本、写入前后 SIGKILL 的原子性、损坏/未知格式拒绝。随后联合引擎和 Runner 验证已完成 A 不重跑、旧 B 状态不明时阻塞、确认停止再执行、产物丢失/损坏、定义变化、取消/失败与 Effect unknown。单独存储检查不证明整个 #13 可恢复，机器重启和硬件断电需按实际证据记录。

## 重开条件

单机范围变化、必须跨版本恢复、事务耗时不适合当前宿主、文件/状态提交边界无法满足验收，或新证据表明存储/恢复边界不足时重新评估；普通字段布局和错误码不另起重大架构讨论。

## 确认与变更留痕

- 用户在 #13 整理前确认保存事实与恢复解耦、节点边界恢复、必要定义一致性和不做低频过度设计；明确授权八项依序实现及验证，并要求常规细节参考 Blackbox。依据 [Issue #13](https://github.com/TonQiaN/Agent_flow/issues/13) 的行为契约、依赖与整理记录。
- 2026-09-09，Codex 核对已有最小执行接口与 Blackbox SQLite/租约/定义快照实现后，按上述授权选择首期本地存储细节。主负责开发者 @xiaoxuanli-a；本记录不冒充另一轮独立审阅或用户逐字段确认。
- 开始实施时基础矩阵仍有真实调用与发布等待；#13 已明确不要求基础事项整项互等。当前先实现存储端口，后续接引擎、产物和 Runner 恢复；尚未整体验收。
