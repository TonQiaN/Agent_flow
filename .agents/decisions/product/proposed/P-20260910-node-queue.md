# 单机按 NodeTask 调度，归属与结果提交共同校验

创建于 2026-09-10。

## 结论与边界

队列只保存已就绪 NodeTask 的引用、调度要求、领取归属和共享容量占用，Run/Attempt/接纳/路由仍以既有持久检查点为唯一业务事实。正常引擎新增持久准备及单节点交还入口，Worker 执行一个 Attempt 后交还控制，后继由正常路由生成再排队；不把旧 Worker 整 Run 调度搬入新结构。

领取同时检查用户角色上限、认证模块身份对应的容量与 Worker 能力，简单按就绪次序扫描，可以跳过暂时无法领取的项，不改变用户选定 Harness、认证或 endpoint。等待不创建 Attempt，也不消耗重试预算。共享认证按 credentialRef/service/method 计数，Profile 别名不能各自增加容量。

首版本地队列复用 RunRecordStore 的事务持久边界，增加有限多记录条件提交端口。部署使用独立命名空间存储 Run 和一份有限队列索引；索引不复制业务结果。并发领取、容量占用、引擎结果写入与后继引用登记受同一条件提交约束。绑定某次领取的 Store 在写入前检查当前令牌及期限，并把所观察到的队列索引版本与 Run 版本共同作为实际事务条件。接管与旧写入因索引版本冲突确定唯一先后顺序，不能只检查归属后进行不带条件的写入；不声称数据库在提交瞬间另行检查时钟。普通引擎和其他存储仍可继续使用原单记录端口，不依赖 SQLite 类型。

过期归属保留容量。新的恢复者先替换领取令牌以阻止旧 Worker 写入，再通过 #13 的共同恢复接口确认旧资源停止/移除，之后同一 NodeTask 新 Attempt；未知状态进入阻塞并保留占用，不凭时钟解除。失败与取消沿用既有终止意图，不引入业务重试。正常停止不再领取，默认排空当前 Attempt；显式取消由运行句柄执行。

旧资源已确认清理、预占令牌已封存而因凭据繁忙重新就绪时，历史 Attempt 仍须保留，但不能把其身份误当作当前活动执行。未领取任务的取消核对恢复封套的清理确认，并将取消与索引状态放在同一条件事务；新的领取先提交时取消须失败。此路径不新增 Attempt、不伪造其结果，也不绕过未确认清理或活动领取。

第一版简单扫描与有限索引接受单机规模约束，不建设公平调度、抢占、动态扩缩容、多主机共识、驻留 Agent 池或历史迁移。凭据源实际占用仍由认证模块管理，调度容量不冒充远端额度或替代源存储互斥。源预占已接通调度前的真实互斥，繁忙任务归还领取并短暂等待；实际 Driver 的 Harness、凭据身份、容量与预占令牌在 Attempt 前核对。普通非队列接口继续兼容。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 条件提交协调 Run 与队列索引 | 复用既有存储及校验，过期归属不能实际写入 | 单机索引更新和扫描会产生竞争，有明确容量上限 | 首期采用，按真实多进程结果验证 |
| 直接搬用旧整 Run Worker | 旧工具入口和心跳经验可参考 | 长期持有 Run，不符合 NodeTask 调度要求 | 只参考生命周期与事务取舍 |
| 独立消息系统并异步复制运行事实 | 可独立扩容 | 首期增加双重状态、提交窗口和运维要求 | 不采用 |

## 影响与验证

引擎交还节点边界不改变正常契约校验、路由、接纳或身份；队列持久实现位于 integrations，Worker 协调依赖端口。验证多 Run/真实多进程的共享角色和认证限制、跳过不可执行项、事务冲突、重开、停止/取消、失联旧资源核对及迟到提交。未验证环节如实留在指南与验证记录，不能以领取单测证明完整 Worker 恢复。

## 重开条件

实际单机容量或吞吐超出有限索引、用户需要多主机调度/公平策略、原子提交无法满足真实故障边界，或新调度单位与 NodeTask 不符时重新评估。

## 认证占用交接的实施细节

#14 联合验收采用同一凭据源的预占：Worker 通过既有源互斥在新 Attempt 前尝试预占，忙时释放队列领取并短暂等待，不产生失败 Attempt。订阅的预占在 Runner 资源已经保存后交给该资源，确认停止后的正常收尾与恢复收尾共用原接口；不可变 API key 读取快照后释放源。

队列记录领取令牌的有限历史；新 Worker 先完成共同旧资源恢复，再封存旧预占令牌，拒绝旧进程在接管后迟到获取凭据。未知占用继续阻塞，不以 PID 消失为解锁依据。源实现负责持久预占与互斥，Worker 仅消费 admission 端口；本次令牌不进入 Workflow 执行定义，正常恢复仍比较同一来源身份。

调度绑定从实际安装的 Driver/Profile 暴露非秘密元数据，经 Agent/Catalog 端口传到 Worker，核对声明 Harness、认证身份及认证容量上限。角色仍由用户配置；调度不重写实际 Profile 或 endpoint。以上是已确认范围内的接口落实，已通过本项目三种 Driver 的真实容器组合及中断验证，不构成新的用户范围确认。

- 2026-09-10，源预占、当前 Driver/Profile 与实际预占源的一致性、旧令牌封存以及三种 Driver 的队列联合测试已完成作者验收。队列索引 v2 保存最多 64 个未收束领取令牌，不提供开发版 v1 迁移；源事务有界等待 1 秒，未知锁保持阻塞，预占尝试不等待繁忙来源。首版实现可以作为 #15 的本地依赖，完整 PR 交付仍单独跟踪。

### 凭据繁忙调度测试的租约边界

验证繁忙来源不生成 Attempt、能够选择另一来源时，使用 NodeWorker 的正常租约；该测试不把宿主300毫秒内完成文件I/O作为正确性的前提。真实过期与失联测试继续显式使用短租约并验证过期拒绝，不放宽生产领取检查或 heartbeat。通过在可用来源的宿主 open 阶段同步停顿350毫秒复现旧测试混入租约过期，再保留这个前置条件验证正常调度。此项依据 #14 既有容量/来源占用验收，以及用户继续完成联合验收的授权；参考 Blackbox 5610d1b 在专门过期用例缩短租约的区分，不把旧系统结果当作当前验证。

同一队列测试文件的普通取消、drain、启动失败、重复接纳与绑定拒绝也使用正常 Worker 租约；这些测试不依赖租约到期。实际过期/失联与旧写入反例仍显式保持短租约。取消测试在业务进入后同步停顿350毫秒，再发取消，以区分有效领取下的取消和已失去领取后的拒绝；生产取消的归属检查不变。

并行容量的独立 Worker 进程也区分正常调度与过期恢复：容量用例使用正常 30 秒租约，并在业务结束前同步停顿 1100 毫秒，验证容量约束不依赖事件循环在旧 900 毫秒租约内完成。SIGKILL/过期恢复用例仍显式保留 900 毫秒短租约及真实过期等待；不放宽生产归属检查。此补充来自 [Issue #44](https://github.com/TonQiaN/Agent_flow/issues/44) 发布准备 CI 暴露的既有测试时序问题，参考 Blackbox 5610d1b 的容量 barrier 与专门过期用例缩短租约的分工，当前项目仍独立复现和验证。
