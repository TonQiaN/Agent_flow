# 单岗位、多简历的证据招聘工作流

创建于 2026-09-15。

## 结论与边界

一次提交一个岗位及最多 12 位候选人的简历和补充材料，文件归属在启动前确认。单文件 20 MiB、合计 128 MiB、最多 64 个文件，每份文档最多 60 页；接纳 PDF、DOCX、TXT、Markdown、PNG/JPEG。限制同时用于前后端；模型上下文仍有上限，超限时明确失败，扩容再设计分批持久化。

工作流合并为四个实际执行节点：读取材料、匹配与推荐、独立复核、生成报告。匹配节点的一次 Harness 执行处理整个批次，完成岗位拆解、各候选人的岗位条件/技能/项目经验/职责核对和二元推荐；独立复核由另一次 Harness 执行，检查全部结果与原文。分配、汇总和确定性校验属于节点内部逻辑，不再为它们创建额外节点。解析与报告节点为断网脚本，页面如实区分脚本和 Agent。

所有候选人依据同一版本岗位要求评审；批次中保留明确身份和材料归属，引用必须对应该候选人或岗位原文。缺失内容为未证实，冲突不等同于造假；只按岗位相关事实分析。每个最终报告的推荐严格二选一：推荐通过/推荐不通过；不设总分、加权评分或排名，未知和冲突必须解释对最终推荐的影响。面试问题是补充，不能代替二元结论。

材料解析在固定断网容器内完成，文本/页码保留原文定位，扫描资料采用 OCR 并标明来源。模型执行通过现有 Harness/凭据适配器及 AgentExecutor。独立复核节点的宿主映射校验完整人数、岗位项、原文/归属、二元结论和复核记录，然后选择通过、返工或拒绝路线；模型不能自行决定宿主是否放行。最多两轮返工，每轮重新检查整个批次以保持岗位要求一致。临时输出在释放前归档，技术失败不能生成候选人不通过结论。旧运行继续按保存的十四节点定义读取，不迁移或改写历史。

代表性验证使用 1 个岗位和 3 份合成简历，覆盖两种二元推荐和未证实/冲突。真实模型完成正常路径；明确标记的确定性测试情景通过实际引擎产生失败、返工、重试、排队、并行和取消，不能在前端伪造状态。故障注入仅在本机测试模式启用。

## 方案考量（alternatives）

用户实际查看十四节点版本后，认为匹配任务拆分过细，一个 Harness 可以承担较完整的逻辑，明确要求合并非必要节点。此前按分配、四维评审、收集、复核、裁决、校验拆分的方案因此改为四节点；独立复核保留其独立执行边界。用户曾暂选多岗位后明确改为单岗位，未给出比较理由，不补造。

## 影响与验证

复用 engine 的 Workflow、NodeWorker、retry 和路由上限；文件与 JSON Agent 支持宿主按校验结果选择已登记 outcome。招聘不再用 Map 拆候选人和维度；并行展示继续以现有 Map/Fork 示例验收。引用逐条核验岗位/候选人归属、原文片段和定位。最终汇总确认所有候选人无漏项、两种允许结论、无评分字段；页面与 JSON/可读报告使用同一已验证结果。

## 重开条件

增加多岗位、更多候选人、人工审批或共享部署时重新评估容量和状态模型。

## 确认与变更留痕

2026-09-15 用户确认单岗位、多简历、逐项结论与证据、不设总分，并要求二元绝对推荐；随后明确授权完整实现及 stacked PR。设计参考 onto-flow 已提交结构与证据规则，未采用其评分阈值。用户另外授权创建 DeepSeek 专用测试 key。实施安排由 Codex 在授权范围内决定，@TonQiaN 主责，尚未其他开发者独立审阅。

实现约束补充：Agent 通过 JSON-to-files 适配直接使用现有执行链；宿主核对原始文件/页码引用后再判定返工。每次招聘启动固定文档、Agent、代理镜像的不可变摘要，防止镜像标签重建改变中途定义。批次中的候选人 ID 由用户上传材料确定；模型必须逐人返回相同 ID，漏人、重复、未知 ID 或串用材料都不能通过。报告同时保存决定性岗位项、未知/冲突影响说明和二元推荐。

招聘宿主沿用 NodeWorker 默认 30 秒任务租约和最长 1 秒心跳间隔。恢复校验和图展开会进行同步数据处理，不能把租约缩短到 3 秒，否则浏览器查询与执行同时进行时，繁忙机器可能把仍存活的 Worker 误判为失去归属。到期拒绝迟到结果的引擎规则保持不变。

2026-09-16，用户进一步明确要求合并非必要节点，运行精简版本并展示真实输入/输出。按上述四节点结构实施，验证按新定义重新进行，首版结果只代表旧版本。
