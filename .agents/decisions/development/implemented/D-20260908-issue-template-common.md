# 主 Issue 的共通字段与 Sub-issue 的自主表达

创建于 2026-09-08。

## 结论与边界

主 Issue 由需求制定者说明当前情况、问题、期望结果、必要边界与完成标准，帮助负责人理解到底要完成什么。制定者不必在建项时给出技术设计、实现步骤、研究方法或测试方案。真实的用户约束保留其依据，已有问题事实与执行方法分开。

Sub-issue 与主 Issue 建立关联，由对应负责人自主组织其承担的具体工作，对执行方案与交付负责。当前接受任意内容组织和表达形式；不提供模板、固定字段、标题样式、段落顺序、写作建议、提示词或示范正文，主 Issue 的字段及填写指导不延伸到子项。实际父子关系、负责人和交付关联属于工作归属，由 [开发流程决定](../README.md#d-20260907-development-workflow) 说明，不变成对子项正文的要求。

这项分工直接使用自然语言描述，不以某个单词等同主 Issue 或 Sub-issue。待足够多的方案经过实施验证后，再从实际工作提炼共性形成子项模板；目前不预设数量门槛、候选写法或自动启用时点。

### 主 Issue 的共同基线

五类各提供一份可独立填写的完整 YAML，手工同步共同内容；分类归 [分类决定](../README.md#d-20260908-issue-classification)，各类只解释差异。共同基线为九字段，下表“必填”是主 Issue 就绪信息及表单 required 的设计意图，不能替代人的确认或真实 Assignees。

| ID · 标题 | 控件 / 创建必填 | 职责 |
| --- | --- | --- |
| `domain` · 所属领域 | dropdown，单选 / 是 | 开发流程、项目内容；YAML 不指定 default，由填写者确认选择 |
| `owner` · 主负责开发者 | input / 是 | 一名人类主责的 GitHub 用户名，另设置真实 Assignees |
| `problem` · 各类当前情况与期望 | textarea / 是 | 谁在什么情况下遇到什么问题、想要什么结果；各类改写提示 |
| `scope` · 范围与边界 | textarea / 是 | 包含、不包含及必须满足的真实约束与依据 |
| `deliverables` · 预期交付物 | dropdown，多选 / 是 | 正式决策正文、实现文件（代码 / 配置 / 模板）、当前说明或使用指南、研究 / 验证记录 |
| `acceptance` · 完成后应看到的结果 | textarea / 是 | 可观察的成果或结论质量；不要求建项者先决定检查方法 |
| `dependencies` · 依赖与阻塞 | textarea / 是 | 无，或影响开工／交付的外部条件、所需结果及关联工作 |
| `decision_context` · 已知约束与相关决定 | textarea / 否 | 已确认要求及依据、已有决定；可保留待澄清问题，不要求先完成方案选择 |
| `handoff` · 整理与续接记录 | textarea / 否 | 后续确认、已完成／未完成及实际关联位置的短摘要；创建时可空 |

交付物可组合。只交正式决定的研究或决策仍需自足的结论、理由与证据；若承诺模板、代码或指南，也须完成相应交付。取消选项不自动撤销验收范围。原始资料、整段聊天、全量工具清单和内部 agent 轨迹不是通用必填项，原始来源仍沿用 [既有拒绝边界](../README.md#d-20260907-mandatory-source-traceability)。

字段顺序为 domain → owner → problem → 类别专用字段 → scope → deliverables → acceptance → dependencies → decision_context → handoff。除 problem 外八项共同字段的完整对象一致；缺陷另保留 reproduction、environment，其他四类不增加专用块。输入使用 placeholder，不预填“已确认／已通过”，验收不用 render 包为代码。领域的 YAML 不指定 default，不等于平台界面保证无初始选择：2026-09-10 实际界面预选“开发流程”，且可切换为“项目内容”。保留两个真实领域选项，在指南中提醒填写者确认，不把平台初始值当作已确认事实。

### 存放、入口与同步

沿用 `.github/ISSUE_TEMPLATE/` 的五份 YAML 和 config.yml；入口标明主 Issue，开放 Blank issue，使子项可以直接自由创建。该开关向有权访问仓库的用户提供空白入口，不能区分主／子项；主 Issue 使用五类模板的约定由人参与整理落实，不能宣称平台自动强制。子项也可使用 GitHub 原生创建／关联入口。

`.agents/decisions/development/` 保留分类、共通和五类差异的七个唯一 ID；`docs/development/issue-templates.md` 说明主表用法与子项自主表达边界，`docs/validation/` 记录真实核对。共同规范不是第六种提交类型，不新增 common.yml、子项表单、第二套正式 Markdown 模板、YAML 继承或生成器。

共同修改同步五表、指南与相应决定；类内差异回到原决定。不为凑数新增正文。同义字段保持 ID；删去的方法块，其职责去向由各类决定说明。既有 Issue 不批量迁移，本轮仅按 #21 范围核对 #20。过去的 Bug behavior→problem 迁移保持不变，若有消费旧字段的工具再显式兼容。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 各类独立定义全部规则 | 局部修改直接 | 共同职责易漂移 | 共通决定集中理由 |
| 共通规范＋差异决定，手工同步完整表单 | 无构建依赖，可直接阅读和填写 | 需核对五份 YAML | 继续采用 |
| 共通数据＋覆盖生成表单 | 可展开到多平台 | 覆盖规则与生成检查增加成本，收益未证实 | 有频繁漏同步证据再评估 |
| 只存片段，提交时拼接 | 文件重复少 | 提交者需重建字段，易遗漏 | 保留完整表单 |
| 一张表包含所有类型字段 | 单入口 | 大量不适用字段增加判断 | 保留五类 |
| 建项时同时要求目标和实现方法 | 看似能直接交给工具执行 | 提前锁定路径，把执行方案责任转给需求制定者 | 主表改为需求与结果表达 |
| 所有 Issue 都不记录方法 | 统一简单 | 妨碍负责人组织实际执行工作 | 主表约束不延伸到 Sub-issue |
| 子项采用统一模板或可选推荐写法 | 便于横向比较 | 未有充分实践，推荐也可能成为隐性要求 | 当前均不提供，由负责人自主决定 |
| 用单个术语定义主／子项 | 简短 | 不同人员和工具对词义理解不同 | 使用自然语言说明用途与责任 |
| 关闭常规空白入口 | 鼓励使用原五表 | 不便落实子项任意形式 | 开放空白入口，明确主表适用范围 |
| 省略 default 即保证界面未选择领域 | 希望让填写者主动判断 | 实际 GitHub 仍预选第一项，配置缺省不能证明界面行为 | 保留两个领域选项，记录平台行为并要求核对选择 |

## 影响与验证

检查五表 YAML、字段唯一性、八项完整对象一致性、领域单选及实际初始选择、旧方法字段去除及缺陷事实保留。主表填写和关联关系可演练，子项不编写示范正文。核对所有当前说明，避免“所有 Issue 必须套表”或对子项换名保留写作建议。#6 历史结果继续有效于旧版本，本轮实际核对与未覆盖范围见 [本轮验证](../../../../docs/validation/2026-09-10-main-issue-templates.md)。

## 重开条件

主表反复漏项、无用字段或同步失败时以实例调整。子项积累足够多的方案实施验证后再提炼共性；不能把本次预留方向直接当作已有模板依据。
