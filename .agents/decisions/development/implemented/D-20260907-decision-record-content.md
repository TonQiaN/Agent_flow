# 一份自足的决定保存选择、比较与否决理由

创建于 2026-09-07。

## 结论与边界

非平凡、非轻量改动必须有一个或多个对应决策记录。已有决定完整覆盖时复用该 ID；出现新取舍时更新该问题正文，或为独立问题新建记录。“必须有记录”不等于“每次必须新建”。每个 PR 的实际决策文件变更门槛及轻量工作的处理归 [开发流程决定](../README.md#d-20260907-development-workflow) 管理，复用记录不豁免该门槛。

非平凡包括影响可观察行为、目标用户、架构或接口契约、数据与安全边界、依赖策略、开发流程及文档治理的改动，不能按行数判定。Issue 模板的增删改属于非平凡改动。错字、排版、机械同步且不改变上述取舍的工作可简化，不因此免除 PR 规则。Bug 修复若恢复已记录行为可沿用原决定；若改变行为或引入新取舍，则需补充记录。

正文至少保存问题、结论与范围、影响与验证、重开条件、简短确认与实际审阅摘要，以及重要变更摘要。当前选择及已有理由在结论中说明；alternatives 仅在满足下述条件时记录，不是每份决定必须填满的比较表。完整讨论和审阅过程保留在对应 Issue，正文定位该工作项并保持关键取舍自足，不另维护审批状态；审查政策见 [开发流程决定](../README.md#d-20260907-development-workflow)。区分事实、待验证假设和建议，原始资料消失后，决定仍应可理解、可评审。

每个问题只有一个稳定 ID 和权威正文。唯一性指完整事实和取舍的归属；索引、短入口提示和从正文生成的阅读视图可以存在，但不能各自维护另一套结论。不同决定间引用，不复制；运行指南描述当前行为，不再复制决策论证。原始讨论副本不属于正式决定。

### alternatives 的记录条件

新增或实质修订 alternatives 条目时，必须同时具备真实用户确实考虑过该方案、用户已给出取舍理由这两项依据，并能定位对应 Issue 中的讨论或确认摘要。AI 自行提出或比较的方案、从最终选择反推的候选及理由，不能冒充用户考量。用户仅要求作出某项决定，或虽提到替代方案但未给出理由时，不补写相应条目。

没有符合条件的内容时，明确写“暂无符合记录条件的替代方案。”，无需为了填满模板另行追问或补造比较。有依据时可用短段落或表格，只提炼用户实际给出的考量、取舍与理由，不为凑齐优点、代价或否决原因补写推测。尚未由用户考虑并说明理由的 AI 建议可留在 Issue 讨论，明确标为建议。

改选后的旧方案也遵守同一条件；生命周期与操作规则中“并入 alternatives”说明记录归属，不豁免真实用户考量和理由要求。缺少依据时，在变更留痕中保留已确认的改选事实并注明理由未提供，不虚构选用或放弃理由。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 短而自足的比较与结论 | AI 和人快速确认为什么选、为什么不选 | 需要主动提炼 | 采用 |
| 只留最后结论 | 文本最短 | 相似观点及否决理由丢失，易反复优化和研究 | 不采用 |
| 完整讨论搬进决策 | 细节齐全 | 噪声破坏信息密度和审批阅读 | 原始内容留在资料区 |
| 每次非平凡改动新建一份 | 容易形式化检查 | 同事实重复登记，产生竞争版本 | 复用对应记录，新问题才新建；PR 门槛由流程决定管理 |
| 每个未选方案复制进 rejected | 目录可枚举 | 理由重复，无法保持唯一 | 同问题在 alternatives，独立拒绝另立记录 |

## 影响与验证

使用 [共同模板](../../TEMPLATE.md) 和 [维护流程](../../../../docs/development/documentation.md)。核对问题是否有唯一记录，新增或实质修订的比较是否有真实用户考量及理由依据，无符合条件内容时是否明确写暂无，说明是否符合当前行为。初始结果见 [验证记录](../../../../docs/validation/2026-09-07-documentation-foundation.md)；本次模板与文字条件的核对留在 [Issue #37](https://github.com/TonQiaN/Agent_flow/issues/37) 及其 PR，不作为真实开发任务行为效果的证明。

## 重开条件

实际任务显示“非平凡”边界有歧义时，以实例修订；不以材料长度、模板字数或是否有 Issue 代替判断。
