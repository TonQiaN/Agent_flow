# 用轻量 Roadmap、变更记录和 Tag 管理版本

创建于 2026-09-08。

## 结论与边界

版本管理先解决三个问题：roadmap 表达当前交付安排，CHANGELOG 记录实际变化，Git tag 固定正式发布的提交。当前只建设手工管理骨架，不实现发布自动化，不确定首发版本或产品功能清单，也不因文档落地而立即发布。

Roadmap 放在 docs/roadmap：README.md 展示阶段边界、版本、核心目标、状态和计划或发布记录入口；远期方向先留在总表。某个版本开始具体规划时，再建立 `<version>.md`，包含目标、范围与非目标、版本整体验收、关联 Issue 和决策。简单补丁已由一个 Issue 完整覆盖时，直接关联 Issue，不强制建立版本文件。初期不建立版本系列和具体版本的多层目录。

版本状态在总表集中维护，初期用“计划中 / 进行中 / 已发布”；延期或取消时说明原因和后续去向，不据此扩展 Issue 状态体系。只有已有对应发布 tag 和记录时才标为已发布。未落实的目标与当前能力说明分开；版本计划不替代 Issue 中的开工确认，也不复制任务状态和设计正文。已发布计划保留，后续安排进入新计划，修订历史由 Git 保存。

根目录 CHANGELOG.md 是唯一人工维护的变更记录正文。Unreleased 只接收实际变化；PR 同步起草本 PR 已实现的条目，合入默认分支后成为已合入、待发布记录，不把分支上的条目当作已发布事实。条目面向使用者说明结果，按需分为新增、修复、重要变更或已知限制，省略空分类，不逐条搬运 commit。发布时将本次条目归入版本及发布日期，保留 Unreleased。以后使用 GitHub Release 时复用对应条目，不再手工维护平行正文。

已有明确目标版本时，Unreleased 内按 `X.Y.Z（目标版本，未发布）` 分组，组内记录已实现的功能变化。这个编号表达交付归属，不表示整版完成或进入发布准备；尚无实际条目的版本不建空组，计划仍在 roadmap。没有产品版本归属的开发协作变化单列，不擅自分配产品版本。各版本及协作组内同类条目合并；同一未发布功能继续实现后，将旧条目收敛为当前行为和仍有效的限制，不能保留相互矛盾的阶段待办。已发布历史和对应版本的验证事实不因后续实现而改写。

版本目标、当前分支交付和发布事实分别核对。开始该版实际实现的 PR 同步总表为进行中，stack 每层按自身 base 保持总表、版本计划和交付说明一致，不依赖更高一层纠正本层的状态。版本计划只保留当前范围、剩余整体验收及证据入口，具体执行次数、失败过程和旧提交结果留在验证记录与 Issue / PR。

版本使用三段非负整数编号 X.Y.Z，发布 tag 使用 vX.Y.Z；这里约定编号格式，不声称已确定兼容性承诺。首发编号和升版边界在实际版本规划中按交付范围明确。未开始打包产品前不增加 VERSION 或包元数据的重复来源；开始打包时再确定产品版本的唯一来源及一致性检查。新项目不自动继承参考项目的版本号或发布历史。

正式发布由当次负责人核对验收和实际范围，通过 PR 整理变更记录、对应计划和必要使用说明，合并后检查确切提交，再为该提交创建并推送 annotated tag。准备中的版本条目标明待发布，roadmap 保持进行中；只有确认远端 tag 和实际发布日期后，才通过 PR 补齐发布事实。发布 tag 不移动、不覆盖；源代码修正通过新版本交付。推送失败时先检查远端是否已有同名 tag，指向不一致时停止处理，不强推替换。

改动的主负责开发者在规划、范围调整和相关 PR 中维护受影响内容，当次发布负责人完成交付核对。不增加专职文档角色。当前所有核对均为手工流程，未来真实发布验证与本次文档骨架验证分别记录。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 单文件 Roadmap | 初期集中易读 | 具体版本与历史计划增长后会挤占总览 | 保留总览，具体计划按需拆出 |
| 总览加按需版本文件 | 总览短，各版可独立讨论 | 需要避免重复状态、Issue 和决策内容 | 采用，明确各自唯一职责 |
| 系列目录、版本目录及多份材料 | 可承载大型版本研究与验证 | 当前无对应内容，增加空目录和导航成本 | 当前不采用，实际增长后再评估 |
| 根目录单文件 CHANGELOG | 易发现，手工维护入口唯一 | 发布时需要核对实际交付范围 | 采用，GitHub Release 复用内容 |
| Unreleased 按目标版本归类已经实现的变化 | 发布前也能查到版本号与功能归属 | 需明确编号不是发布事实，并避免空版本与阶段日志 | 采用；无产品归属的协作变化单列 |
| 每个开发切片追加条目，保留旧待办 | 保留实现过程直观 | 同版读者会同时看到已完成和未完成的相反描述 | 当前未发布记录收敛到最终行为，过程留在验证记录和 Git |
| 自动发布、冻结每版手册和多包版本 | 可支撑复杂发行流程 | 当前尚无产品实现或打包需求 | 暂不建设 |

## 影响与验证

新增 roadmap、CHANGELOG 和 [版本维护指南](../../../../docs/development/versioning.md)，同步开发流程、PR 模板和文档入口。规划的存放边界由 [分层决定](../README.md#d-20260907-documentation-layers) 管理；根指令的入口书写沿用 [唯一书写决定](../README.md#d-20260907-agents-writing)。本决定不共同负责 AGENTS.md。

本决定的落实范围仅为管理文档骨架。目录与入口、计划和现实的区分、维护时点、发布提交与 tag 的对应关系、链接及事实一致性已核对，见 [版本管理骨架验证](../../../../docs/validation/2026-09-08-version-management.md)。实际发布尚未演练，不以静态检查冒充发布成功；未来首次发布另行记录验证。

## 重开条件

版本计划确实需要多份独立材料、手工维护反复漂移、开始分发多个软件包，或需要兼容性承诺和自动发布时，基于实际需求扩展本决定。不能仅因参考项目具备这些能力就照搬。
