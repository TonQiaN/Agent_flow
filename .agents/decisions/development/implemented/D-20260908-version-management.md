# 用轻量 Roadmap、变更记录和 Tag 管理版本

创建于 2026-09-08。

## 结论与边界

版本管理先解决三个问题：roadmap 表达当前交付安排，CHANGELOG 记录实际变化，Git tag 固定正式发布的提交。手工流程已用于 Issue #44 的核心 0.1.3 与完整项目 0.1.4 首次交接；前端与本机工作台按用户确认归入 0.1.4，不实现发布自动化。准备 PR 与实际 tag 分开记录，文档或元数据变更本身不等于发布。

Roadmap 放在 docs/roadmap：README.md 展示阶段边界、版本、核心目标、状态和计划或发布记录入口；远期方向先留在总表。某个版本开始具体规划时，再建立 `<version>.md`，包含目标、范围与非目标、版本整体验收、关联 Issue 和决策。简单补丁已由一个 Issue 完整覆盖时，直接关联 Issue，不强制建立版本文件。初期不建立版本系列和具体版本的多层目录。

版本状态在总表集中维护，初期用“计划中 / 进行中 / 已发布”；延期或取消时说明原因和后续去向，不据此扩展 Issue 状态体系。只有已有对应发布 tag 和记录时才标为已发布。未落实的目标与当前能力说明分开；版本计划不替代 Issue 中的开工确认，也不复制任务状态和设计正文。已发布计划保留，后续安排进入新计划，修订历史由 Git 保存。

根目录 CHANGELOG.md 是唯一人工维护的变更记录正文。Unreleased 只接收实际变化；PR 同步起草本 PR 已实现的条目，合入默认分支后成为已合入、待发布记录，不把分支上的条目当作已发布事实。条目面向使用者说明结果，按需分为新增、修复、重要变更或已知限制，省略空分类，不逐条搬运 commit。发布时将本次条目归入版本及发布日期，保留 Unreleased。以后使用 GitHub Release 时复用对应条目，不再手工维护平行正文。

已有明确目标版本时，Unreleased 内按 `X.Y.Z（目标版本，未发布）` 分组，组内记录已实现的功能变化。这个编号表达交付归属，不表示整版完成或进入发布准备；尚无实际条目的版本不建空组，计划仍在 roadmap。没有产品版本归属的开发协作变化单列，不擅自分配产品版本。各版本及协作组内同类条目合并；同一未发布功能继续实现后，将旧条目收敛为当前行为和仍有效的限制，不能保留相互矛盾的阶段待办。已发布历史和对应版本的验证事实不因后续实现而改写。

版本目标、当前分支交付和发布事实分别核对。开始该版实际实现的 PR 同步总表为进行中，stack 每层按自身 base 保持总表、版本计划和交付说明一致，不依赖更高一层纠正本层的状态。版本计划只保留当前范围、剩余整体验收及证据入口，具体执行次数、失败过程和旧提交结果留在验证记录与 Issue / PR。

版本使用三段非负整数编号 X.Y.Z，发布 tag 使用 vX.Y.Z；这里约定编号格式，不声称已确定兼容性承诺。首发编号和升版边界在实际版本规划中按交付范围明确。根 package.json.version 是核心版本输入，CLI、DeepSeek 工具、domain、engine、integrations 五个工作区跟随核心 0.1.3；用户明确指定的 Studio 使用其 package.json.version 记录前端 0.1.4。内部精确依赖始终指向被依赖包的实际版本，因此 Studio 0.1.4 依赖核心 0.1.3，不把调用方版本复制到依赖上。package-lock.json 同步全部 manifest，不另建 VERSION。新增包默认跟随核心，其他例外须在对应 Issue 和本决定明确。核对每个包的目标版本、内部引用及锁条目，确认外部依赖解析未漂移，再执行干净安装和工程检查。所有包继续 private，不以源码 tag 表示 npm 分发已实现。新项目不继承参考项目的版本号或发布历史。

首次 0.1.3 是累计源码发布，包含原 0.1.1、0.1.2、0.1.3 已验收的交付批次；原批次计划保留以追溯设计，不制造从未发布的 0.1.1/0.1.2 tag。Roadmap 将原批次纳入 0.1.3 一行，tag 核实后再更新为已发布。未合并的后续功能不自动纳入；准备期间默认分支变化时，先复核新增内容与验证适用性再确定发布提交。

前端、运行历史、本机服务与招聘工作流按 0.1.4 单独归属。一个 Git tag 固定整个提交，不能按 CHANGELOG 分组排除其中的文件。首次交接使用两个已经合入主干历史的源码快照：v0.1.3 固定 PR #45 原核心准备提交 `461159cd4a680fbb791ad830b8b250f431f28898`，其中没有 Studio；v0.1.4 固定该 PR 的合并提交 `2e44cf2d27f39475e27fe7c44cdcd098ebadbe22`，交付包含核心、前端及同期修复的完整项目。前者重验该提交自己的 Node 24/26 与 Docker CI，后者核对文件树与已通过完整 CI 的 PR head 一致。各标签的记录按实际源码归属，后续修复不能补写进较早快照。

源码 tag 表达整个项目在该提交的交付，不等于给所有包统一升版；v0.1.4 快照仍保留核心包 0.1.3 和 Studio 0.1.4 的既定元数据。包版本、实际快照与验证身份分别记录，不宣称两个快照中的核心文件完全相同，也不增加独立包发布自动化。后续发布事实通过文档 PR 补齐，tag 不随这类文档提交移动。

正式发布由当次负责人核对验收和实际范围，通过 PR 整理变更记录、对应计划和必要使用说明，合并后检查确切提交，再为该提交创建并推送 annotated tag。准备中的版本条目标明待发布，roadmap 保持进行中；只有确认远端 tag 和实际发布日期后，才通过 PR 补齐发布事实。发布 tag 不移动、不覆盖；源代码修正通过新版本交付。推送失败时先检查远端是否已有同名 tag，指向不一致时停止处理，不强推替换。

改动的主负责开发者在规划、范围调整和相关 PR 中维护受影响内容，当次发布负责人完成交付核对。不增加专职文档角色。当前所有核对均为手工流程，真实发布验证与原文档骨架验证分别记录。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 单文件 Roadmap | 初期集中易读 | 具体版本与历史计划增长后会挤占总览 | 保留总览，具体计划按需拆出 |
| 总览加按需版本文件 | 总览短，各版可独立讨论 | 需要避免重复状态、Issue 和决策内容 | 采用，明确各自唯一职责 |
| 系列目录、版本目录及多份材料 | 可承载大型版本研究与验证 | 当前无对应内容，增加空目录和导航成本 | 当前不采用，实际增长后再评估 |
| 根目录单文件 CHANGELOG | 易发现，手工维护入口唯一 | 发布时需要核对实际交付范围 | 采用，GitHub Release 复用内容 |
| 自动发布、冻结每版手册和多包版本 | 可支撑复杂发行流程 | 原骨架阶段尚无产品实现或打包需求 | 不建设发行自动化；2026-09-18 的 Studio 显式版本例外见结论 |

## 影响与验证

新增 roadmap、CHANGELOG 和 [版本维护指南](../../../../docs/development/versioning.md)，同步开发流程、PR 模板和文档入口。规划的存放边界由 [分层决定](../README.md#d-20260907-documentation-layers) 管理；根指令的入口书写沿用 [根入口书写决定](../README.md#d-20260910-root-agents-writing)。本决定不共同负责 AGENTS.md。

原始落实范围为管理文档骨架。目录与入口、计划和现实的区分、维护时点、发布提交与 tag 的对应关系、链接及事实一致性已核对，见 [版本管理骨架验证](../../../../docs/validation/2026-09-08-version-management.md)。2026-09-18 首次交接另行核对两个实际源码快照、各自 CI、annotated tag 和远端 peeled commit，并补齐日期与发布状态，见 [源码发布交接验证](../../../../docs/validation/2026-09-18-source-release.md)；不以原静态骨架检查冒充发布成功。

## 重开条件

版本计划确实需要多份独立材料、手工维护反复漂移、开始分发多个软件包，或需要兼容性承诺和自动发布时，基于实际需求扩展本决定。不能仅因参考项目具备这些能力就照搬。
