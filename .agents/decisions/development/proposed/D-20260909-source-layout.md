# 根 src 下区分应用、业务定义、引擎与具体适配

创建于 2026-09-09。

## 结论与边界

实现源码、测试、示例和开发脚本集中到根 src。src/apps 放可启动入口；src/packages 放内部代码包。根目录保留包管理、共享编译配置和 GitHub 配置，文档及决策沿用现有目录。包内不再重复嵌套 src。

共同业务类型放 domain；engine 包按功能组织并定义其需要的接口；具体文件、进程、数据库、认证和 Harness 适配进入 integrations。依赖为 apps → engine/integrations/domain、integrations → engine/domain、engine → domain。domain 不依赖运行环境。engine 可依赖纯校验库，不读取文件、网络或启动进程。跨包通过包导出入口，不引用内部源文件；应用不互相导入。

首个切片只创建 CLI、domain、engine；尚无真实适配时不创建空 integrations 包。后续按实际交付创建 integrations、Worker、Server、Web、API contracts 和 Client。前端以后通过版本化 API 和客户端消费运行状态，不读取数据库或引擎内部状态；画布坐标和展示配置与执行定义分离。

内部包统一使用 ESM、显式依赖、严格 TypeScript 配置，公开入口集中在 index.ts。npm workspaces 管理 src/apps/*、src/packages/*。先用 TypeScript 构建和 Node 测试入口，不引入额外任务调度平台。单元测试跟随模块，跨模块测试和样例分别位于 src/tests、src/examples。

导入检查拒绝跨包相对路径、未声明包依赖、反向依赖和 domain/engine 的环境依赖。它是可检查的静态边界，不声称阻止恶意代码；执行隔离由后续 Runner 提供。

基础 CI 运行同一 npm run check，使用 Linux 上的 Node 24 与 26；源码构建与测试类型检查分开，便携包不加载 Node 全局类型，测试可以使用 Node 测试 API。每次本地验证与远端矩阵分别记录，配置存在不代表远端已经通过；发布、部署与流程预检自动化不随此配置隐含启用。

## 容器内工具程序

DeepSeek 的隔离文件服务属于容器内应用，放在 src/apps/deepseek-tools，宿主 integrations 只负责后续按执行身份装配，不导入其程序为库。它使用原生 Node ESM 启动脚本和固定镜像提供的 SDK；SDK 在应用 manifest 中声明精确版本的可选 peer dependency，并明确由镜像提供，避免给所有宿主执行组合安装另一套 Harness。缺少或版本不符须在执行模型任务前失败，不能把 optional 理解为功能降级许可。

依赖检查同样扫描该应用，接纳显式 peer 声明，并追踪 node:module createRequire 产生的静态加载函数；动态模块名、未声明 SDK 及应用作为库导入仍拒绝。固定安装根用于该容器程序的模块解析，不来自用户输入。本次使用原生 JavaScript 是独立程序与镜像 SDK 的装载边界；业务与宿主内部包继续保持严格 TypeScript。实际原生工具测试验证程序行为，不能用宿主编译通过代替容器兼容性。

## 方案考量（alternatives）

| 方案 | 收益 | 代价 | 取舍 |
| --- | --- | --- | --- |
| src/apps 与 src/packages，少量包内按功能分目录 | 源码入口统一，应用与复用模块有依赖边界 | 需要工作区构建配置 | 用户确认采用 |
| 根 apps/packages | 常见工作区布局 | 根目录实现入口分散 | 用户要求所有实现集中到 src |
| 每个 Issue 独立包 | 包级隔离明确 | 初期接口易变化，增加配置和拆包成本 | 先保持少量包，真实边界需要时再拆 |
| 所有内容单包、单编译配置 | 配置最少 | 前端与服务端边界更难约束 | 不采用；保留应用和包配置 |
