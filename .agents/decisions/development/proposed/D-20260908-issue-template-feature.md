# 功能模板说明使用场景与期望行为

创建于 2026-09-08。

## 结论与边界

功能模板说明新增或改变什么产品能力，目标文件为 `.github/ISSUE_TEMPLATE/feature.yml`，前缀为 `[功能]`。相对 [共通规范](../README.md#d-20260908-issue-template-common)，重点改写 problem，帮助制定者说清谁在什么场景遇到限制、希望发生什么变化。选类与拆分归 [分类决定](../README.md#d-20260908-issue-classification)。

### 相对共同基线的差异

| 字段 | 处理与内容归属 |
| --- | --- |
| `problem` | 标题为“当前场景与期望能力”；说明当前做不到什么、为什么需要、期望使用者能完成什么 |
| `behavior_contract` | 移除独立必填块。用户可见的正常、边界或失败行为在 problem/acceptance 表达；已有兼容、权限等真实要求写入 scope，不预先设计内部接口 |
| 其余共通字段 | 沿用共通规范，不增加技术方案或可选实现建议栏；共九个输入块 |

例如外围时间回放的需求可以是：“审阅者想看某时点当时已经知道的信息；停在结果返回前时不能显示未来输出，浏览不产生新运行。”这些是期望行为，能够进入验收；不需要在 Issue 中选择存储结构、事件模型或界面实现。

验收以约定场景下的行为和必要兼容结果为准。实现者选择方案及实际验证方法，相关取舍与结果按项目文档约定记录。独立研究或选择结论按主要交付目标另判断类型。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 独立的行为与接口契约块 | 提醒补充输入输出及边界 | 与目标和验收重复，也容易把建项变成提前接口设计 | 原方案曾采用；本次把期望行为归回目标和验收 |
| 在目标和验收中描述用户可见行为 | 制定者能直接说明想要什么，保留实现空间 | 仍需写具体场景，不能只说“做一个功能” | 采用 |
| 所有功能预填技术设计、权限与接口细项 | 大项目可提前暴露部分影响 | 小事项填大量不适用项，未经探索的选型容易变成限制 | 真实约束按需写入 scope，方法不作为 Issue 字段 |

## 影响与验证

核对九项共通职责及旧 behavior_contract 的需求部分去向。用外围回放和配置带来的行为改进检验：只描述情境、期望及边界即可填写，不需要内部结构或实现步骤。旧链接预填应人工整理到对应需求字段，不能整段搬入方法文字。

此前版本的字段与线上检查见 [2026-09-08 实施验证](../../../../docs/validation/2026-09-08-issue-templates.md)。本次改版由 [Issue #21](https://github.com/TonQiaN/Agent_flow/issues/21) 跟进，当前待完成新版交付与默认分支核对，移回 proposed；旧验证不作为新版本已生效的证据。

## 重开条件

真实填写仍需反复追问当前情况或期望结果、方法约束转移到其他字段、必要事实丢失，或无法判断完成边界时，带具体例子修订。不能为恢复旧字段数量重新添加方法栏。
