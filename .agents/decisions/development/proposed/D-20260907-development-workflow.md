# 以 Issue 为起点的开发与 PR 闭环

创建于 2026-09-07。

## 结论与边界

正式开发以 Issue 为起点：Issue → 人参与整理至可开工 → 初步预检 → 负责开发者敲定决策与文档 → 开发、测试 → PR 评审与修正 → 合并、验收与关闭。研究可在 materials 中自由开展；进入项目开发时，要把可执行范围和验收结果提炼进 Issue，不能要求执行者重新阅读原始资料才能开工。

本次敲定流程、职责和交接条件，准备本地模板。自动预检程序、CI/CD 配置、测试矩阵、开发 Skill、部署策略另议；不运行真实产品场景，不将本决定移入 implemented。模板存在也不代表 GitHub 已启用自动门禁。当前操作及工具限制见 [工作指南](../../../../docs/development/workflow.md)。

### Issue 的责任与开工条件

- 每个工作项归属一名明确的主负责开发者，由 GitHub Assignees 体现；可有协作者，但不能用“团队负责”代替主责。主负责者负责范围确认、决策判断、文档、实现、测试和验收跟进，AI 可协助执行，不替代人的责任归属。
- Issue 按可独立验收的结果拆分，尽量保持模块化；记录必要依赖。父 Issue 可汇总目标，实际开工单元仍要各有负责人和验收标准。不按文件数量或 AI 会话机械拆分。
- Issue 的必要信息与填写时点由 [共通规范](../README.md#d-20260908-issue-template-common) 统一定义，类型选择由 [分类决定](../README.md#d-20260908-issue-classification) 管理，Bug 等专有内容归各类差异决定。建项、预检与交接据此核对信息；暂时未知项如实标记，不用已有表单缺少某字段豁免必要范围与验收。
- 制定 Issue 的职责是说清当前情况、期望结果及真实约束；不知道具体怎样实现不构成建项或可开工的阻塞。实现者与 AI 在目标内选择方法，Issue 不预设技术路线或研究/测试计划。需要沉淀的技术取舍及执行证据按对应决定与文档维护，Issue 只保留必要确认和产物定位；自主实现不改变已确认目标或豁免实际验收。
- 模板细则独立为分类、共通字段及五类差异共七项决定；本决定保留开发阶段和职责。模板的增删改属于非平凡改动，按同一流程修改实际负责该问题的决定、表单与说明；现有文件与待实施的差异见工作指南，不因选择新规范就宣称表单已经更新。
- 建立 Issue 后先进行人参与的整理，达到“可开工”再进入预检。AI 和工具可以协助归纳讨论、拆分工作、补齐信息及起草验收标准；人参与澄清、纠正和关键判断，确认主责、范围与验收边界。由主负责开发者参与并确认即可，不强制增加另一位审批者；已有明确用户指令可作为确认依据，不为登记重复询问。缺少负责人、含糊的验收条件或未解决的必要依赖不能冒充就绪。

### Issue 承接决策讨论与审查

Issue 同时承接决策的讨论、分工、审查和敲定。确认时指明决策 ID、本次修订内容与适用范围，记录实际确认人、日期、依据及阻塞意见的处理；不能只用“Issue 可开工”或“已关闭”推断其中所有建议都已采纳。结论改变后，由主负责开发者同步唯一决策正文；决定浓缩最终取舍和必要确认摘要，Issue 保存完整过程。

鼓励同一决定由多名开发者审阅，以减少个人误判形成长期错误约束，并同步团队对项目的理解和掌控程度。当前仍在启动期，协调成本会减缓构建，因此继续直接设计、直接做，不要求固定人数或等待多人审查；已有用户明确指令可登记为确认依据。仅作者自查或 AI 审查就如实记录，未进行多人审阅不补造记录。未来固定审阅人数、确认权限或启动期结束条件，在本决定中重新讨论。

决策目录不再单独承载审查确认阶段，未全部落实的决定留在 proposed；能否实施按 Issue 中对具体方案与范围的明确确认判断。只有落实并验证后才进入 implemented，具体转换由 [生命周期决定](../README.md#d-20260907-decision-lifecycle) 管理。

### 预检与负责开发者的判断

预检在人参与的整理与关键确认完成后、正式实现前进行，可由工具自动执行：比较当前实现与 Issue 目标，检查相关现行决定、alternatives 和独立拒绝理由，识别重复实现、冲突与依赖；Bug 尝试复现，并记录使用的版本、环境、步骤、结果与证据。预检只报告事实和建议，不自动改写决定或取消验收要求。

预检输出“可继续 / 有阻塞 / 证据不足”，附依据。无法复现不等于没有 Bug：主负责开发者决定补充证据、缩小调查范围或以明确说明的验证方式继续；未解决的决策冲突必须先由主负责开发者敲定处理方式，不能交给实现阶段偷偷改选。范围或验收发生实质变化，回到人参与整理的环节；仅补充细节不强制重走全部步骤。

主负责开发者据此判断要引用、修订或新增哪些决策。非平凡、非轻量改动须由一个或多个对应决定覆盖；同一问题优先修订原文，只有独立问题才新增。内容密度与唯一性判据归 [内容决定](../README.md#d-20260907-decision-record-content) 管理。

### 文档先行与一并提交

负责开发者先在工作分支写清本次决定、影响范围、接口或行为约定及验收方式，再执行开发和测试。已有文档完整覆盖时无需重写，先确认适用范围。实现中发现新取舍，先修订相应文档再继续；影响已确认范围时回到上一步。

“先写”是工作顺序，不要求决策先独立 commit、先开 PR 或先合并。决定、实现、测试和相关文档可以在同一 PR 提交；决定的明确确认也可来自已有授权，不增加形式审批。决定描述期望，使用指南只描述当前现实；准备中的说明标清待实现，合并时按实际结果同步。

### 每个 PR 与决策改动的关系

每个 PR 至少关联一个实际 Issue，并且相对它自己的目标分支，包含至少一份正式决策正文的实质改动。实质改动包括真实的新取舍、对后续开发有用的边界/比较/验证标准补充，或有事实依据的生命周期转换；只改索引、模板、空格，或仅在 PR 中写决策 ID，均不满足。目录转换要保留稳定 ID、同步索引并留下真实依据。

轻量改动不因此强制新建决定。优先在对应旧决定中补足确有价值的内容；若不存在有意义的决策变更，应并入同一问题下有决策变更的相关 PR。不能为了门槛编造取舍、添加无意义“再次确认”、把测试日志搬进决定，或夹带无关决策。由此增加小修复单独提交的成本，是当前明确接受的流程取舍；实际使用若频繁需要凑改动，应重开本条，不能自行放宽。

### PR 的测试、评审、修正与合并

1. 默认短期工作分支和范围集中、可审阅的 PR；未完成可先开 Draft。说明具体问题、结果、关联 Issue、发生改动的决策、验收覆盖与测试证据，不能用文件清单代替行为说明。
2. 作者先自查变更和相关测试，再进入评审。测试针对当前提交及其目标分支，记录实际执行结果、未覆盖内容和原因；已配置的必需检查必须满足。尚未配置 CI、跳过或未运行的检查不能写成通过。具体测试矩阵留待另议。
3. 评审检查行为与验收、决策一致性、回归风险及文档现实性。审阅安排与事实记录沿用本决定中的共同审查及启动期取舍；Issue 中对方案的确认不替代对 PR 实际实现和测试证据的评审。
4. 作者逐项处理反馈：修正、说明依据或将范围外建议转为关联 Issue；不能以转出 Issue 掩盖本次验收缺陷。修正后复测受影响范围，实质变更请求重新评审；未解决的阻塞反馈不能靠勾选“已解决”消失。
5. 合并前确认非 Draft、目标分支正确、无未解决冲突、每项本次验收有证据、必需检查及实际要求的审阅已满足。分支基线、代码或决定发生变化时，重新检查差异并补做受影响的验证；不借用旧提交的通过结果。主负责开发者协调合并，由有权限的人或已获授权的工具执行，不擅自绕过仓库限制。
6. 合并后核对实际进入默认分支的结果和验收证据，再结束工作项。分批实现时，部分 PR 仅引用 Issue；只有满足完整验收且面向默认分支的最终 PR 才使用关闭关键字，否则验收后手动关闭。出现回归，关联原 Issue/PR 记录修复或回退，并按同一决策与 PR 纪律处理；重大事故另在 docs 永久复盘。

涉及版本目标或范围的工作同步对应 roadmap；产生值得告知使用者的实际变化时，同一 PR 补充 CHANGELOG 的 Unreleased，并在模板中交代更新或不适用原因。版本发布的准备与核对沿用该 PR 流程；编号、记录分工和维护时点由 [版本管理决定](../README.md#d-20260908-version-management) 管理，不在每个普通 PR 增加发布审批。

### 有依赖时使用 stacked PR

仅在存在实际依赖、拆开有助于独立审阅和分步验收时叠放 PR；没有依赖的工作用普通独立 PR。底层 PR 面向默认分支，上层面向直接依赖分支。每层说明自己的范围、验收、前后依赖与合并顺序，按自己的 base 检查差异；下层已带有的决策改动，不能替上层满足“本 PR 有决策改动”的要求。

按依赖从底向上合并，每次进入默认分支的阶段都应保持可用和文档一致。下层修正后向上传递，重新检查所有受影响层；下层合并后再调整上层 base、同步分支并检查差异、冲突、决策改动和测试证据。尤其在 squash 或 rebase 改写祖先后，确认没有重复带入已合并内容。上层仍依赖分支时先完成衔接再清理分支。无需把某个 stack 工具或预览功能设为基础依赖。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| Issue 起点，人参与整理，工具预检，主责敲定后实现 | AI 和工具协助提炼，人的参与保障责任、范围及验收判断 | 仍需人参与关键澄清与确认 | 采用 |
| 从聊天直接开工，完成后补 Issue | 启动快 | 开工时缺少共同验收和归属，容易事后补故事 | 正式开发不采用；研究仍可自由进行 |
| Issue 一建立就自动实现 | 减少人工交接 | 未整理目标及冲突可能被自动放大 | 自动化先停留在预检，人负责就绪与取舍 |
| 在 Issue 审查并敲定决定，正文保存浓缩结论 | 讨论、分工和确认在已有工作项中衔接，减少重复状态 | 需要说明确认针对的具体方案与范围，并同步正文 | 采用；目录精简及原取舍由生命周期决定管理 |
| 启动期强制多名开发者先审后做 | 及早纠错并同步项目理解 | 当前管理与产品均刚起步，协调成本会减缓构建 | 当前鼓励审查但不强制等待 |
| 永久只由提出者判断，无共同审查目标 | 协调少、推进快 | 个体失误会沉淀为长期约束，团队掌控程度容易分化 | 不作为长期方向；保留共同审查目标 |
| 每个 PR 都有实质决策改动 | 决定和实现一起进入审查视野 | 轻量修复、stack 每层需有合理的文档增量 | 按用户要求采用，禁止为门槛制造噪声 |
| 已有决定覆盖时 PR 只引用即可 | 轻量、避免重复文字 | 不满足本次明确要求的决策文件改动门槛 | 收紧原规则，保留复用同一决定的原则 |
| 决策必须先独立合并才能实现 | 决策审批与编码分离明显 | 启动期多一次串行等待，原子变更被拆散 | 不要求；先写文档，可在同一 PR 一并提交 |
| 所有变更强制 stacked PR | 层级统一 | 无依赖的小改动也承担分支同步与审阅成本 | 仅按依赖与审阅价值使用 |

## 影响与验证

本决定管理开发阶段与交接条件；决策内容、生命周期、AGENTS.md 书写分别由各自既有决定管理，交叉引用不增加共同负责人。Issue 分类及字段内容归分类、共通与各类模板决定，本正文不另维护一套类型或字段细则。同步 Issue / PR 模板和当前说明；原静态结果留在 [流程验证记录](../../../../docs/validation/2026-09-07-development-workflow.md)，本次细则拆分见 [模板决定设计验证](../../../../docs/validation/2026-09-08-issue-template-decisions.md)。以后进入真实产品开发时，再用实际 Issue 检验交接、预检、评审修正和验收是否可用，不能以模板存在替代。

PR 反馈修正、目标分支变化及 Issue 关闭行为参照 GitHub 官方 [评审修正](https://docs.github.com/en/pull-requests/concepts/resolving-reviews)、[修改 base](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-base-branch-of-a-pull-request) 和 [关联 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) 说明，2026-09-07 核对；本项目的门槛与责任分配是本次设计取舍。

## 重开条件

实际工作反复出现就绪信息不足、单一负责人瓶颈、小修复为满足决策门槛制造噪声、stack 层无法独立验收，或复现结果长期无法支持判断时，带实际例子修订本决定。单人判断错误长期影响开发、团队理解明显分化或协调条件变化时，重新讨论共同审查安排；这些信号不自动启用审批门槛。未来 CI/CD、测试矩阵和 Skill 的选择补充各自具体决定，不因本流程留有阶段就视为已经敲定工具。
