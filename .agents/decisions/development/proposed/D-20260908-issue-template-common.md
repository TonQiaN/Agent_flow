# 共通规范与五份完整 Issue 表单

创建于 2026-09-08。

## 结论与边界

共同字段、存放与同步约定集中维护；五类决定只解释相对基线的差异，每类最终提供一份可独立填写的完整表单。首版手工维护五份 YAML，不另设基础表单或正式生成器。分类选择归 [分类决定](../README.md#d-20260908-issue-classification)，开发阶段与责任归 [开发流程决定](../README.md#d-20260907-development-workflow)。

### Issue 由制定者说明情况与目标

Issue 的核心输入是当前发生什么、谁受到什么影响、为什么值得解决，以及制定者到底想要什么结果。实现者应能据此理解需求，与 AI 一起探索达到目标的方法；建项和可开工不以制定者已经想清技术方案为前提。

Issue 正文不预设技术选型、内部结构、实现步骤、研究路线或测试方案，也不保留一个可选的方法栏继续诱导填入这些内容。方法由执行者在工作中选择；有长期价值的技术取舍进入相应决定，实际验证方法和证据进入 PR 或验证记录。Issue 保留需求澄清、完成事实和相关记录的定位，不复制为另一份执行方案。

必要约束来自已经存在的事实或用户明确要求，并写清依据。例如现有兼容要求、权限限制、必须支持的使用场景或实际预算可以限定目标；从初步技术想法推导出的限制不能冒充需求。缺陷复现描述过去怎样触发问题，属于事实，不是未来怎样修复。

验收写完成后应观察到的结果，研究/决策则写需要回答的问题、结论质量与适用边界。结果需要可核对，但不能把指定工具、试验步骤或测试命令写成建项者必须准备的答案；也不能以执行了某种方法替代目标达成。

### 共通字段

共同基线有九个字段。下表的“创建必填”是就绪信息要求及表单 required 的设计意图，不代替人参与整理、真实 Assignees、确认或验证。暂未知的事实如实填写，并在实施前处理必要阻塞，不用默认文字假装已经确认。

| ID · 基准标题 | 控件 / 创建必填 | 职责与必要内容 |
| --- | --- | --- |
| `domain` · 所属领域 | dropdown，单选 / 是 | 从“开发流程”“项目内容”选择一个主要领域，不设默认值；按分类决定的作用对象判断，跨领域影响写入范围 |
| `owner` · 主负责开发者 | input / 是 | 一名人类主责及 GitHub 用户名；协作者可列分工。另核对真实 Assignees，文本不能替代责任归属 |
| `problem` · 当前情况与期望结果 | textarea / 是 | 谁在什么情况下遇到什么问题、造成什么影响、希望得到什么结果；各类按需要改写提示，不要求实现方案 |
| `scope` · 范围与边界 | textarea / 是 | 包含与非目标、必须满足的真实约束及依据；不预先拆模块、设计内部接口或填写实施路线 |
| `deliverables` · 预期交付物 | dropdown，多选 / 是 | 选择正式决策正文、实现文件（代码 / 配置 / 模板）、当前说明或使用指南、研究 / 验证记录；说明希望收到什么成果，不强制提前指定文件路径或内部结构 |
| `acceptance` · 完成后应看到的结果 | textarea / 是 | 场景下可观察的结果、需要回答的问题或结论质量；不指定实现与测试方法，不以执行步骤替代达成结果 |
| `dependencies` · 依赖与阻塞 | textarea / 是 | 无或所需具体交付、解除条件与处理人；区分阻塞、参考、父子关系，不虚构 Issue 号 |
| `decision_context` · 已知约束与相关决定 | textarea / 否 | 已明确的要求、依据或相关决定；未知需求问题可待澄清，不要求创建者先列候选方案、完成研究或作出技术选择 |
| `handoff` · 整理与续接记录 | textarea / 否 | 创建时可空；按实际记录需求确认、参与者、已完成/未完成结果、待澄清问题及相关产物定位，不填写执行计划 |

交付物可组合，不能靠取消勾选隐形删除既有验收承诺；变更范围时按原流程记录原因和处理。若研究或决策的范围仅包含正式决定，可只选择该交付物；证据与理由仍须在自足正文中足以支持结论。原始资料、整段聊天、所有开发工具版本及产品内部 agent 轨迹不作为通用必填字段；原始资料关联沿用 [既有拒绝边界](../README.md#d-20260907-mandatory-source-traceability)。

### 基线如何形成各类表单

字段顺序为 domain → owner → problem → 类别专用字段 → scope → deliverables → acceptance → dependencies → decision_context → handoff。五类都保留九个字段；八项共享相同控件、标题、提示与必填意图，problem 按类别改写。领域放在第一个输入位置，用简短提示区分团队开发方法与产品本身；提交者须主动选择，不根据表单类型自动推断。文本输入用 placeholder 提示，不用默认 value 填写“无阻塞、已确认、已测试”；验收正文保留正常清单语义，不以 render 包成代码块。

类决定分别定义新增字段、problem 的改写及验收填写解释。增删改不是数量配额：没有合理原因可以写“删除无”。将来某类确需删除、改变控件、必填意图或字段语义时，在其差异决定记录适用边界和原职责去向；共通决定保留默认值，核对时允许有明确依据的例外，不能静默偏离。所有类都需要的变动回到本决定。

同义字段保持稳定 ID；每份表单内 ID 唯一。2026-09-08 的模板保留功能/维护的六个旧 ID，增加 deliverables 与 handoff；Bug 的旧 behavior 合并到共同 problem，具体理由归 [缺陷模板决定](../README.md#d-20260908-issue-template-bug)。该次迁移没有回写历史 Issue；本次 #20 的明确审查修订与其他历史项分别处理。

领域扩展新增 `domain`，网页、CLI/API 都在提交后正文中保存“所属领域”及所选文字；此字段不会自动设置 GitHub Labels、Issue Types 或改变标题前缀。历史 Issue 沿用下述按需补充原则，不以未填写的新字段追溯否定已完成验收。

2026-09-10 的后续反馈进一步调整职责：共同 ID 保留，acceptance 改为结果验收；移除 feature 的 behavior_contract、research 的 evidence_plan/stop_rule、decision 的 options/impact、maintenance 的 change_plan。各类决定说明原有事实、期望行为和必要边界分别由 problem、scope、acceptance 承接，执行方法不迁移为其他必填栏。Bug 的 reproduction/environment 保留。旧链接预填这些被移除的字段时须重新整理需求，不静默把整段方法搬入 scope 或验收。

### 存放与唯一维护入口

| 位置 | 内容及归属 |
| --- | --- |
| `.agents/decisions/development/` | 分类、共通、五类差异共七份决定；正文按生命周期存放，通过分类 README 的稳定 ID 引用。本决定负责目录与同步取舍，不另增第八份存放决定 |
| `.github/ISSUE_TEMPLATE/` | 五份完整 feature.yml、bug.yml、research.yml、decision.yml、maintenance.yml 及 config.yml；保留原三份路径，新增两份 |
| `docs/development/issue-templates.md` | 实施后说明怎样选类、填写、设置主责及使用 CLI/API，保留简短例子和真实限制；工作指南链接该页 |
| `docs/validation/` | 按实际日期记录决定、模板和指南的一致性、填写演练与线上入口结果；只在有真实结果时建立记录 |
| `materials/` | 研究稿、候选表单和详细实验材料，不成为另一份正式字段规范或必读开工依据 |

共通规范不是第六种可提交类型，不在模板入口放 common.yml，也不额外维护一套五类正式 Markdown 模板。CLI/API 按对应完整表单准备正文，并在使用指南说明；研究中的 Markdown 骨架可作为材料，不能整包当作正式入口部署。首版不引入 YAML 跨文件继承、配置合并规则或自动生成流程；复制到五份表单的共同内容由同步核对控制。

config 沿用关闭常规空白入口的设置；模板存在不等于自动门禁。五类入口和标题前缀由分类决定负责，表单不固定指派某一开发者或预置尚不存在的新类别标签。实际平台限制和检查结果放使用指南，不用设计声明代替线上验证。

### 变更与迭代

共同规则变更先改本决定，再同步受影响表单及指南；仅当某类的例外或验收解释变化时修改其差异决定。类内变化只改相应决定、表单和受影响说明。无真实取舍变化的文件不为凑数改动。

每次同步核对共同 ID、控件、标题、提示、必填意图及例外；旧 ID 或职责改变时明确对应关系。已关闭 Issue 保留历史，活跃 Issue 在当前工作需要时补缺口，不批量重写确认与验收。观察真实选类争议、反复追问、无用字段和交接失败来修订，不预设配额、自动过期或固定审阅人数。共同字段频繁变化或实际漏同步时再评估生成器，届时仍由本决定管理来源、合成规则和生成结果的检查。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 五类各自定义全部规则 | 每份完全独立，局部变动直接 | 当前八字段完全相同，重复解释易产生分歧 | 采用共通规范集中理由 |
| 共通规范＋差异决定，手工维护完整表单 | 规则唯一，表单直接可读，无构建依赖 | 修改共同文字仍需核对五份 YAML | 采用首版，明确接受同步成本 |
| 共通数据＋类别覆盖，生成表单 | 共同修改一次可展开各类及多平台格式 | 需维护覆盖语义、工具、来源定位和生成检查；长期收益尚未实测 | 有频繁改动或漏同步证据后重开 |
| 每类只存片段，填写时再拼接 | 物理重复少 | 提交者与审阅者需要重建完整字段，遗漏更难发现 | 交付完整表单 |
| 一张表单包含所有类型字段 | 单入口，公共信息集中 | 大量字段对当前类型不适用，增加填写判断 | 按主类提供完整表单 |
| 领域用自由文本或只留在填表说明中 | 改动少，表达自由 | 用词不一致或未随提交保存，难以稳定阅读归属 | 使用共通单选字段，保存明确答案 |
| 为领域设置默认值或按类型推断 | 少一次选择 | 维护、研究等可属于不同领域，默认答案容易掩盖未判断 | 不预选，所有表单使用同一提示与选项 |
| 建项时要求方法、候选方案及验证计划 | 有助于提前暴露部分不确定性 | 制定者往往尚不了解实现，容易把猜测固化为实现者和 AI 的限制 | 按本次反馈撤下方法输入，重点表达情况、目标与真实约束 |
| 方法字段改为可选或改名为建议 | 创建负担较低，保留早期想法 | 仍会在需求正文中形成隐含执行指令 | 不采用；具体取舍与执行记录在后续相应文档中形成 |
| 可观察结果与必要边界限定交付，执行者选择方法 | 人能确认想要什么，保留实现探索空间 | 制定者仍须把模糊愿望澄清成可理解的结果 | 采用；不把“自由实现”误用为免除验收 |

## 影响与验证

实施需同步五份 YAML、入口配置及使用指南。检查 YAML 结构、共同字段及有依据的差异、稳定 ID 和链接；用五类样例及仅决定、否定结论、未复现例子核对可填写性。CLI/API 正文应能表达同等信息；默认分支实际模板选择与显示需单独核对。静态通过不表示 GitHub 行为或长期维护成本已验证。

五份完整 YAML 与新使用页已落实，共同字段手工同步；默认分支选择器及实际表单展示已核对，结果见实施验证。本轮文本核对见 [设计验证记录](../../../../docs/validation/2026-09-08-issue-template-decisions.md)；本决定不把 research artifact 的生成器转为正式项目工具。

本次核对九项共通职责、领域单选/无默认值、八项相同共通对象及显式字段迁移；用“不知道怎样实现但知道想要什么”的场景核对可填写性，确认没有把方法要求藏入范围或验收。CLI/API 正文读回须能看到领域、当前情况和期望结果。旧版及本轮仅新增领域的检查均不能代表最终改版已在线生效；[Issue #21](https://github.com/TonQiaN/Agent_flow/issues/21) 的修订待完成交付与默认分支验证，保留 proposed。

## 重开条件

出现共同字段频繁漏同步、模板数量或目标平台明显增加、共性下降、必要字段负担过重，或字段同名异义导致错误续接时，以实际例子修订。没有这些依据时，不为减少文件内重复先引入模板框架。
