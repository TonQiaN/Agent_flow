# 维护模板说明当前问题与期望改进

创建于 2026-09-08。

## 结论与边界

维护模板用于落实工程、文档或协作改进，目标文件为 `.github/ISSUE_TEMPLATE/maintenance.yml`，前缀为 `[维护]`。制定者说明当前有什么不便或成本，以及希望改善到什么程度。具体改法、迁移步骤和验证方案由执行者选择。共同职责见 [共通规范](../README.md#d-20260908-issue-template-common)，类型选择见 [分类决定](../README.md#d-20260908-issue-classification)。

### 相对共同基线的差异

| 字段 | 处理与内容归属 |
| --- | --- |
| `problem` | 标题为“当前情况与期望改进”；说明当前影响、维护原因与希望获得的改善 |
| `change_plan` | 删除改动、兼容与验证计划块；既有兼容等真实要求归 scope，期望改善归 problem/acceptance，不要求制定者先选改法、文件拆分或测试方案 |
| 其余共通字段 | 沿用共通规范；共九个输入块 |

例如 #21 可以说清楚“创建者尚不知道怎样实现，却被模板要求填写方法；希望只说明情况和目标也能完整建项”。验收应检查模板是否支持这一结果，而不预先要求选用哪种生成器、字段拼接技术或检查脚本。

如存在已有兼容性、数据保留或服务连续性要求，在范围中写清要求及依据；实现者据此处理迁移和回退。正式版本安排仍按 [版本管理决定](../README.md#d-20260908-version-management) 执行，不为每个维护 Issue 增加发版计划。

维护若实际新增产品行为或恢复既有失效契约，按主要结果判断功能或缺陷。维护也不能只凭写完一份方案结束已承诺的模板、指南或其他工程结果。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 必填改动、兼容与验证计划 | 提前提醒入口影响与迁移风险 | 将制定者尚不清楚的实施路线变成建项要求，易限制 AI 探索 | 原方案曾采用；本次去掉计划字段 |
| 只写“优化”“维护” | 输入很短 | 不知道当前问题和希望改善到什么程度 | 不采用；情况、影响与结果仍须清楚 |
| 现状和期望改进为核心，范围保留真实约束 | 小维护也能完整表达需求，执行者可选择改法 | 约束须说明来源，防止由猜测形成限制 | 采用 |
| 所有维护固定要求迁移、回退及产品测试计划 | 看似覆盖完整 | 小文档事项产生不适用内容，也不能证明真实交付 | 根据实际目标和风险在执行中确定方法 |

## 影响与验证

用模板改进、产品使用说明修订和存在真实兼容要求的维护情形检查：不提供实施步骤也能建项，既有事实和结果责任保留。方法字段的内容不整体移入 scope 或 acceptance。

此前版本的字段与线上检查见 [2026-09-08 实施验证](../../../../docs/validation/2026-09-08-issue-templates.md)。本次改版由 [Issue #21](https://github.com/TonQiaN/Agent_flow/issues/21) 跟进，当前待完成新版交付与默认分支核对，移回 proposed；旧验证不作为新版本已生效的证据。

## 重开条件

真实填写仍需反复追问当前情况或期望结果、方法约束转移到其他字段、必要事实丢失，或无法判断完成边界时，带具体例子修订。不能为恢复旧字段数量重新添加方法栏。
