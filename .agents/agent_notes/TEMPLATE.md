# 要记录的选择或问题

创建于 YYYY-MM-DD。这是 agent_notes 正式笔记模板；文件名作为稳定 ID，放入对应生命周期目录，不另写 status。

## 结论与边界

写清选择、已有理由、适用范围与非目标。尚未敲定的内容使用提议语气；已在 Issue 敲定但尚未全部落实的结论仍可位于 proposed，写清确认适用的范围。拒绝记录写清拒绝什么、在什么范围内不采用。期望与当前实现分开。

## 方案考量（alternatives）

只有真实用户确实考虑过、且已给出取舍理由的方案才写入，并定位对应 Issue 中的讨论或确认摘要。用户只要求作出某项决定、未讨论替代方案，或提到了方案但未给理由时，不补写条目；AI 自行提出、比较或推测的内容不能冒充用户考量。

无符合条件的内容时写“暂无符合记录条件的替代方案。”，无需为填满本节另行追问。有依据时按需用短段落或表格记录，只提炼用户实际给出的考量、取舍和理由，不为凑齐优点、代价或否决原因补写推测。当前选择及已有理由可以只保留在“结论与边界”。

改选后的旧方案也须满足同一记录条件；缺少理由时在变更留痕中注明，不推测补齐。用户理由中尚待验证的判断标明不确定；理由已有独立拒绝记录时，只引用稳定 ID，避免复制正文。具体要求见 [内容决定](development/README.md#d-20260907-decision-record-content)。

## 影响与验证

影响什么行为、文档或模块；怎样确认落实。实现后链接 docs 中相关当前说明或验证结果。原始资料路径不是必填项，不构成生效条件。

## 重开条件

哪些事实、范围或约束变化值得重新评估。拒绝记录尤其要防止换种措辞就重开研究；未约定时如实写明，有新依据后再讨论。

## 确认与变更留痕

- 简述何时、由谁、针对什么方案和范围作出决定，并定位对应 Issue 中的明确依据；未确认就写待讨论。已有用户指令可登记为依据，不重复索取批准。
- 浓缩实际审阅情况；未进行多人审阅就写明，不用目录或 Issue 开关状态推断已经审阅、确认或实现。完整讨论与审阅过程留在 Issue，不再增设审批状态字段。
- 简要记录已确认改选的日期和旧选择；符合条件的比较理由放在 alternatives，不重复长文；未提供理由就如实注明，不推测补齐。
- 实际存在的 Issue/PR、复盘或相关决定可以引用；不虚构编号、批准人或验证结果。

不要复制逐字稿或一次性施工记录。同一问题的待决修订可列在原文末尾，明确它尚未改变当前结论。
