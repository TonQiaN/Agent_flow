# 用目录管理决策生命周期

创建于 2026-09-07。

## 结论与边界

在产品、开发流程两个分类下，分别用以下目录管理决策。生命周期只由路径表达，正文不另写状态；同一决策 ID 同时只有一份正式正文。

| 目录 | 含义与开发效力 |
| --- | --- |
| proposed | 尚未全部落实，包括讨论中和已在 Issue 中敲定、待开发或验证的决定；是否可实施看明确确认依据，不能只看目录 |
| implemented | 在所述范围内已落实并验证，后续相关改动继续遵循 |
| archived | 问题退出当前范围或提案撤回；保留记录，不约束当前工作，不等于明确拒绝 |
| rejected | 独立且被明确拒绝的方向；记录拒绝边界与重开条件，防止重复研究 |

archived 使用该英文拼写。superseded 不作为并列状态：被替代的是同一问题下的旧方案，合并进正文的 alternatives，保留选用与放弃原因。一般未选方案也只在该处维护；独立问题的明确拒绝才建 rejected 记录，不复制完整理由。

## Issue 与 agent_notes 目录的分工

Issue 承载讨论、分工、审查与实施范围的确认；目录表达决定的落实、退出或拒绝情况。取消 accepted，未全部落实的决定统一放在 proposed；不在正文增设等价状态字段或另建子目录。共同审查的目标、启动期取舍和具体确认方式归 [开发流程决定](../README.md#d-20260907-development-workflow) 管理。

proposed 不等于“尚未同意”，也不自动授权实施。正式开发时按对应 Issue 中对具体决定及其修订范围的明确结论执行；已有用户指令可以登记为确认依据，无需重复请求审批。决定正文保留简短确认摘要及对应 Issue 的定位，结论与关键取舍仍须自足，完整讨论和审阅过程不复制进决定。

已有明确确认的目标在待落实阶段仍可约束对应开发，但不能作为功能存在的证明。implemented 只表示所述范围已落实并验证，不证明经过多人审查；Issue 已敲定也不等于实际验收通过。

## 状态转换

| 事件 | 操作 |
| --- | --- |
| 新问题进入正式讨论 | 在 proposed 建立笔记，先查重复问题与已有否决理由 |
| Issue 中对具体决定及范围有明确采纳依据 | 保留 proposed，在正文浓缩确认摘要并定位 Issue；按开发流程继续，不因确认单独移动目录 |
| 所述范围全部落实并验证 | 从 proposed 移入 implemented；部分完成仍留 proposed，进度在 docs 或 Issue 说明 |
| 整个独立提案被明确拒绝 | 移入 rejected，留下拒绝结论、边界与重开条件 |
| 问题不再适用或提案撤回 | 移入 archived，并写明原因；不能用归档代替拒绝理由 |
| 当前方案改选且已确认 | 更新同一正文，旧方案合并进 alternatives；新方案待落实时移入 proposed，记录 Issue 中的确认范围，验证后再移入 implemented |
| rejected 或 archived 出现新依据并重开 | 同一文件移回 proposed，保留既有拒绝或退出背景；重开研究不等于许可采用 |

只是在讨论修订时，保留原文件当前目录和结论，在末尾写清待决修订。不能因未经确认的建议把仍有效的已实现决定整体搬入 proposed，也不能另建同问题正文来竞争效力。改选已经确认时，按 Issue 中的范围和过渡约定更新同一记录；移动目录本身不代表撤销全部既有要求。

归档不用于日常换方案。错字修正不触发状态转换。移动文件同时更新分类索引，其他正式引用通过稳定 ID 定位。已提交版本可用 Git 追溯，但关键理由必须在当前正文自足，不能只靠翻历史找回。

## 方案考量（alternatives）

| 方案 | 可取之处 | 代价或不适用原因 | 本次取舍 |
| --- | --- | --- | --- |
| 生命周期目录，正文专注内容 | 浏览与按范围读取直接 | 转换需移动文件并更新索引 | 采用 |
| 正文写 status，索引再复制状态 | 单文件携带元数据 | 多处事实易漂移，不符合目录管理要求 | 放弃上一版做法 |
| superseded 与生命周期并列 | 易堆积替代历史 | 混淆方案替换和决策生命周期，需拼接多个版本的理由 | 不采用，旧方案并入 alternatives |
| 保留独立 accepted 目录 | 过去用于区分采纳与实施，并为共同审查留出位置 | 现在 Issue 已承担讨论、责任与审查确认，再维护目录会重复同一事实 | 放弃；保留原选用理由，相关职责转入 Issue |
| 未落实统一 proposed，由 Issue 承接审查确认 | 减少重复状态，沿用同一开发交接入口 | 目录无法单独表达是否已敲定，需要看确认摘要和对应 Issue | 按本次用户要求采用 |
| 删除目录后在正文新增等价状态字段 | 单文件可区分采纳与讨论 | 仍重复维护 Issue 已承载的事实 | 不采用，不将旧状态换个位置保存 |
| 每次改选新增整份记录 | 完整版本易留存 | 同问题多份事实，信息密度降低 | 保持一个 ID 与一份正文 |

操作见 [维护指南](../../../../docs/development/documentation.md)，初始骨架依据见 [原验证记录](../../../../docs/validation/2026-09-07-documentation-foundation.md)，本次目录迁移与规则核对见 [开发流程验证](../../../../docs/validation/2026-09-07-development-workflow.md)。本记录落实的是目录、模板与规则，不代表未来产品决定都已实现。

## 重开条件

实际使用证明目录无法表达落实边界、Issue 确认与决定难以对应、索引难维护或单份笔记承载不同问题时，以实例调整；不为分类完整而增加状态。共同审查的门槛与责任变化回到开发流程决定讨论，不由目录变化自动启用审批门槛。
