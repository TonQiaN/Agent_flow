## 01 · 初步 high level 功能

产品方向候选：服务两人实际的大量、重复、对结果稳定性有要求的文书与数据处理任务。使用者主要通过 AI 工具及结构化入口生成、修改、运行工作流，通过前端理解编排与执行结果。TypeScript 重设计，参考旧项目的能力、失败经验和测试场景；不预设旧 Python 代码、配置或运行历史兼容。[C04](#C04) [M09](#M09) [M12](#M12)

建议在领域层把关系说明清楚：**Workflow 定义 → Run → 就绪节点任务 → Attempt → Harness 调用 → 外围结果/产物**。每次 Attempt 分别关联镜像环境快照和节点 Harness 配置快照。逻辑角色用于任务资格和共享额度，执行者只是本次领取者；Prompt、任务边界、skill/MCP 设置和数据契约属于具体调用的输入条件。前端通过这些身份读取当次事实。配置分层与三种 Harness 分模块已明确，具体对象字段仍由 E05 讨论。

共同的第一条候选验收流程沿用聊天：**材料输入 → Agent 提取 → Gate 校验 → 必要时 Fixer 修复并再校验 → Transform 整理 → Effect 模拟发布**。页面可查看流程与路径、外围提交的 Prompt、节点 skill/MCP 配置、镜像环境、返回产物和失败摘要，并回到某个时点查看外围状态。[C02](#C02) [C04](#C04) [U](#U) [U2](#U2)

## 02 · 前端第一版：展示到什么程度

已明确的功能方向是只读展示、外围回放、镜像环境与节点能力分开呈现。下面具体字段和交互仍是细化建议。这里的“编排结果”指已生成或加载的流程定义、节点/边及运行映射，也包含外围执行结果。

| 展示面 | v1 建议包含 | 容易漏掉的验收点 | Issue |
| --- | --- | --- | --- |
| 流程全局 | 输入/输出、节点类型、角色、依赖、outcome、返修边、实际走过路径 | 同一节点多次执行可区分；未走分支不显示成功；布局是定义的展示结果 | E10 |
| 节点、Prompt 与 Harness 能力 | 任务描述/边界、Prompt 模板与外围渲染提交值、变量来源、所选 Harness、节点 skill/MCP/其他支持设置、原生配置摘要 | 当前配置与历史快照、配置声明与生成/校验结果分开；不读取内部 system prompt、会话或工具记录 | E10 |
| 镜像与物理环境 | 声明与实际镜像/模板、系统工具/依赖、Harness 安装版本、挂载权限、网络/资源、物理预检、生命周期 | 与节点 skill/MCP 分区；环境清理后仍能读快照；声明/实测/未知有区分，认证只显示脱敏引用 | E11 |
| 历史入口 | Run ID、流程/版本、起止时间、状态、结果摘要、筛选 | 无历史、服务读取失败、历史不完整都有说明；旧运行不会套上新配置 | E12 |
| 外围时间轨迹 | 播放/暂停、倍速、拖动、逐事件跳转；联动节点状态、Attempt、输入提交、输出/产物返回 | 运行中显示状态与经过时间；不补造内部进度。长空档、同时间、迟到及缺失的外围事件有规则 | E12 |
| 业务结果与产物 | 文本/结构化输出、文件引用/预览、校验结果、生成节点和 Attempt | 产物缺失/清理有状态；路径、摘要和权限足以追溯；预览不执行嵌入脚本 | E13 |
| 失败与运行摘要 | Harness 调用错误摘要、Runner 退出/超时、Gate/outcome、外围耗时、Effect 状态 | “进程成功≠业务通过”；其他汇总指标仅展示外围直接返回值；导出仅含约定外围证据并脱敏 | E13 |
| 调度可见性 | 角色额度、队列、等待原因、实际执行者和接管；随后加并行泳道/重试 | 随 0.1.2/0.1.3 后端交付增量，不在 v1 伪造尚不存在的队列指标 | E14 |

**回放只覆盖工作流外围时间与输入输出，不进入 container 内 agent 的执行记录。** 记录来自编排器、Runner 和 Harness 调用边界，包括任务提交、等待、开始、完成/失败/取消、输入、返回输出与产物引用。Run、NodeTask、Attempt、事件来源、外围时间与稳定顺序用于关联。内部消息、工具调用、会话日志和推理过程均不采集，即使 Harness 开放相应接口也不纳入本范围；不保留包含这些内容的原始输出流。任务结果通过约定的返回协议提取。

例如：`10:00 提交输入 → 10:01 开始 → 10:04 返回输出`。回放停在 10:02 时只显示“执行中、已运行 1 分钟”和已提交输入；10:04 才显示返回结果。内部何时调用工具、何时生成某个文件不属于记录范围。产物以外围接收/登记时点进入回放，无法取得的内部时点不推断。历史回放消费已存外围事件，不发起新 Run 或外部动作，也不等于节点恢复。字段及存储格式由 E05/E08 讨论。

v1 可以有搜索、筛选、展开、切换、缩放、定位、回放及诊断下载，这些服务于读取。启动/取消运行的最小入口仍可由 B04 的 CLI/API 承担；前端 v1 不因后台存在这些接口就加上写入按钮。当前最新用户要求比会议曾讨论的极少量 Prompt 修改更明确。[M08](#M08) [U](#U)

首次端到端验收至少覆盖：正常完成；Gate 失败后返修；进程完成但业务不通过；执行环境启动失败；运行中取消；外围记录部分缺失；收集器排除内部 agent 记录。窄屏、键盘、长 Prompt/返回输出、空态和加载错误随视图验收。并行/重试病例在对应后端交付后加入。

## 03 · 镜像环境、节点能力与 Harness 模块

Container / 环境管理仍是核心内容。本次明确把**镜像提供的物理能力**和**节点通过 Harness 配置的能力**分开管理：物理依赖存在，与某个节点启用 skill、MCP、插件等，是两个不同事实。[U2](#U2) 会议里关于工具依赖、插件差异和共享工作区的讨论继续作为研究参考。[M04](#M04) [M05](#M05)

| 层次 | 管理内容 | 责任与展示 |
| --- | --- | --- |
| **镜像 / 执行环境** | 操作系统、系统工具与库、解释器、Harness 可执行程序及安装版本；实例的工作目录、挂载、网络/资源和生命周期 | B03 负责环境操作；E06/E07 讨论和验证。E11 展示镜像/物理环境声明与当次快照。 |
| **节点任务 / Harness 能力配置** | 任务描述、任务边界、Prompt、输入输出契约、环境引用、所选 Harness；该 Harness 开放的 skill、MCP、插件及其他接口设置 | B04 提供结构化节点配置，B01 按 Harness 校验和转换；E10 只读展示声明、生成/校验结果及当次配置快照。 |
| **Harness 专属模块** | 解释本 Harness 的字段，生成原生指令/配置，声明挂载或注入需求，调用 Harness，转换外围结果与错误 | DSH、Codex、Claude 分模块维护。共享最小调用契约，专属行为留在各自模块；Runner 执行环境操作，不解释三套原生设置。 |

节点能力设置不限于 skill 和 MCP：应有扩展入口容纳所选 Harness 实际开放的功能，具体首期字段通过支持矩阵确认。不同 Harness 不必有完全相同的配置项；不支持项明确显示或拒绝，不能静默忽略。默认值、继承、覆盖顺序以及配置校验仍需 E05/E06 讨论。

**同一镜像可以服务不同能力配置的节点。** 例如提取节点和校对节点引用同一个具备 PDF 工具的镜像，各自设置不同任务边界、skill 集合与 MCP 连接。运行时由所选 Harness 模块分别生成配置，配置互不串用；在物理依赖已满足时，调整节点 skill/MCP 不应要求重建镜像。若新增能力确实需要额外可执行程序或系统库，则单独声明环境依赖并预检，不能只凭节点配置宣称可用。MCP 所需的本地运行依赖与节点的连接/工具设置同样分别归属，凭据通过引用注入。

三种 Harness 已敲定，项目内代码管理按下面的边界拆开；表中模块名是讨论用示意，不代表已经创建代码目录。

| 独立模块 | 本次明确的方向 | 需要继续研究或验证 |
| --- | --- | --- |
| `harnesses/codex` | 独立处理 Codex 的节点能力配置、调用及运行工作区的 `AGENTS.md` 指令组织 | 所选版本的指令发现/覆盖规则，skill/MCP 等接口、配置生成与隔离 |
| `harnesses/claude` | 独立处理 Claude 的节点能力配置、调用及运行工作区的 `CLAUDE.md` 指令组织 | 所选版本的指令发现/覆盖规则，skill/MCP 等接口、配置生成与隔离 |
| `harnesses/dsh` | 独立处理 DSH 的配置与调用，进一步挖掘插件系统 | 插件能承载哪些节点能力、如何装载/组合/禁用，以及与任务边界和配置隔离的关系；不预先承诺与另外两种完全等价 |

这里的 `AGENTS.md` / `CLAUDE.md` 对应用户所举 `agents.md` / `claude.md` 的运行指令文件示例，具体文件名、路径与规则按后续选定 Harness 版本验证。本段讨论的是产品为任务运行准备的文件；仓库根目录现有 `AGENTS.md` 与 `CLAUDE.md` 符号链接的治理关系继续保持。本次只在 artifact 记录模块化方向，不创建模块、修改指令文件或将研究写成已验证支持。

候选任务类型建议用两条轴描述：**工作性质**（功能、缺陷、研究、设计讨论、工程/流程维护）与**交付物**（决定、实验结论、代码/配置、指南/模板）。例如 E01 是产品讨论、仅决定交付；E07 是功能研究、实验与决定交付；E03 是流程改进、决定与模板交付。模板如何实现这两条轴留给 E03，不要求新增五套表单。

若一个 Issue 只负责确认尚未实现的产品方案，完成后相关决定仍可以留在 `proposed`。若一个决定的全部范围只是已落地并验证的流程规则或文档制度，再根据实际验收判断生命周期；不能对“仅文档”统一机械移动到 implemented。独立拒绝与同一问题的未选方案仍按现行规则区分，不重建 `accepted`。[R03](#R03)
