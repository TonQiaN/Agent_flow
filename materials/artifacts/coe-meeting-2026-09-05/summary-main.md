## 1. 最重要的结论

1. **先把任务跑通，再用证据决定是否细拆。**付方圆认可先以较大的稳定任务单元完成 MVP；随后再衡量细粒度拆分是否改善质量、耗时或 Token 成本。细拆不是所有场景的预设答案。〔[42:27–45:28](transcript.html#t-42-27)〕
2. **两人的方案可以按层整合。**付方圆侧重节点或工作区内部的实现、可观测性与精调；李孝轩侧重节点或工作区之间的通信、容器隔离与编排。整个工作流可以成为上层的一个节点。〔[23:28–24:18](transcript.html#t-23-28)、[51:43–53:55](transcript.html#t-51-43)〕
3. **新项目叫 AgentFlow，开发语言选 TypeScript。**优先适配 DeepSeek Harness，同时保留 Codex、Claude 等 Harness 的接入能力；各适配器按实际能力提供审计等字段。〔[01:10:11](transcript.html#t-01-10-11)、[01:14:21](transcript.html#t-01-14-21)、[01:19:19–01:23:15](transcript.html#t-01-19-19)〕
4. **前端主要服务观察与调试。**运行历史、轨迹回放、节点 Prompt 和流向是核心展示内容；主要配置和修改由用户通过 AI 工具完成，仅保留少量人工微调。〔[01:23:20–01:24:41](transcript.html#t-01-23-20)〕
5. **初期聚焦高重复量、要求稳定的文书和数据处理。**先满足自身需求；代码开发工作流、开源、商业化及交付数据处理成果等路径保留为后续探索。〔[01:24:47–01:29:54](transcript.html#t-01-24-47)〕
6. **先定通用开发流程，之后再定产品架构。**以文档为第一公民，用 Issue、独立 worktree、PR 和评审串起工作；初期手动审核合并，逐步探索自动化。会末明确说项目骨架此时不需要先动。〔[01:40:17–01:43:58](transcript.html#t-01-40-17)、[01:50:10–01:54:14](transcript.html#t-01-50-10)〕

## 2. 核心分歧：工作应拆到多细

两人的分歧同时涉及**任务粒度**和**边界约束**，讨论后找到了可兼容的层级，但尚未通过对照实验判定哪种做法在具体场景更好。

| 维度 | 付方圆的出发点 | 李孝轩的出发点 |
| --- | --- | --- |
| 拆分原则 | 找到最小的、有独立意义的动作，逐步执行和调优 | 找到单个 Agent 能稳定完成的最大任务；组合不稳定时再拆 |
| 最看重的收益 | 中间过程透明、局部调试、精调成本、模块化分工 | 先保障端到端稳定，减少不必要的拆分及耦合 |
| 内部上下文 | 同一工作流共享工作区，各 Action 使用独立会话；用 Prompt 告知前序产物路径 | 拆开的节点通过明确的输入输出约束通信 |
| 约束位置 | 对整个工作流的入口、出口做检查；内部主要依靠 Prompt，遇到问题再加约束 | 节点前后设置 Gate，先固定接口，再独立调试 |
| 证据状况 | 有简历多角色评审结果不稳定的实践经历；尚无系统的拆分收益比较 | 提出必须比较拆与不拆的效果，认可不同场景可能需要不同粒度 |

**兼容方式：**一个带明确输入输出边界的任务单元，内部可以先由一个 Agent 完成；确有收益时再拆成多个步骤。其内部工作流又可以封装为上层的一个节点。这样，外部编排与内部精调可以分别推进。〔[11:08–14:23](transcript.html#t-11-08)、[27:18–28:18](transcript.html#t-27-18)、[34:27–39:36](transcript.html#t-34-27)〕

**仍需验证：**付方圆提出可用业务数据集测试，例如简历与岗位匹配；李孝轩进一步要求比较不同设计在质量、速度和 Token 消耗上的差异。会议没有给出既定数据集、验收阈值、重复试验次数或已完成的量化结果。〔[16:34](transcript.html#t-16-34)、[24:18–26:27](transcript.html#t-24-18)、[43:40–44:07](transcript.html#t-43-40)〕

## 3. 产品与架构的落点

### 3.1 Harness 适配：共享接口，能力按实际提供

双方认可设置适配层，不把产品限定在单一 Harness 上。DeepSeek Harness 是优先投入的对象，因为可以深入修改、观察内部过程；Codex 和 Claude 即使不能输出相同的审计信息，也应允许接入。**“能接入运行”和“具备全部精调与审计能力”是两个层次。**具体配置声明、能力字段和接口契约尚待架构讨论。〔[01:19:19–01:23:15](transcript.html#t-01-19-19)〕

付方圆还提出在开发环境保留相关 Harness 的参考源码，并考虑更新检查，帮助 AI 准确理解实现。李孝轩将其归为开发流程议题；会上没有把更新 Hook 或参考目录定成完整规范。〔[01:20:55–01:21:59](transcript.html#t-01-20-55)〕

### 3.2 容器、插件和调度：整合方向明确，方案尚需验证

李孝轩已有为 Agent 启动独立容器并挂载资源的实现思路；付方圆现有隔离更多依赖运行目录和路径限制，希望用容器能力改造。两人讨论了按任务挂载插件、避免不需要的插件激活，以及预制镜像和启动前环境检查的差异。**插件机制本身尚未深入研究，不能视为适配已完成。**〔[41:42–41:58](transcript.html#t-41-42)、[48:41–49:42](transcript.html#t-48-41)、[54:31–57:44](transcript.html#t-54-31)〕

千级并发是期望达到的服务能力。会议举例指出：PDF 切图等任务可能在短时间集中占用大量内存；可考虑监测容器资源、错开峰值。发言中的依据是现有试用观察，**没有千并发压测结果，也未确定调度算法、资源预算或服务指标。**〔[46:14–48:03](transcript.html#t-46-14)、[50:31–51:15](transcript.html#t-50-31)〕

### 3.3 用户体验：让人看清过程，让 AI 承担配置工作

可视化主要用于查看执行历史、回放轨迹、理解节点 Prompt 和流程走向。用户通过 Codex、Claude 等工具创建和调整工作流，前端承接观察、诊断及少量修改。付方圆强调透明的执行上下文也能帮助 AI 继续调试和优化。〔[19:25–19:49](transcript.html#t-19-25)、[44:36](transcript.html#t-44-36)、[01:23:20–01:24:41](transcript.html#t-01-23-20)〕

### 3.4 复用旧项目：带走功能、经验和决策，重新对齐架构

会上“移植”的含义经过澄清：先把现有功能和踩坑经验带入新项目，由 AI 参考已有实现；新架构仍需重新讨论。付方圆原项目中的 Object、端口设计来自 Ontology 背景，脱离该业务前提后需要重审。**本次会议没有最终定下节点定义、数据流转协议和完整目录骨架。**〔[01:44:11–01:48:27](transcript.html#t-01-44-11)〕

## 4. 协作方式与开发流程

项目有两个并行目标：做出有用的 AgentFlow，也摸索一套能支持 AI 编程长期维护的小团队开发方法。两人可用于讨论的时间主要在晚间，平时可能异步推进；流程应适配这种实际情况。〔[01:31:11–01:33:32](transcript.html#t-01-31-11)、[01:43:09–01:43:58](transcript.html#t-01-43-09)〕

会上认可的大框架是：**讨论目标与预期结果 → 形成并分类 Issue → 明确分工 → 必要的研究与决策记录 → 独立 worktree 实现 → 带依据和验证材料的 PR → 评审与合并。**Bug、新功能和方向调整被用作 Issue 分类的例子，具体模板和流程细则仍需初稿讨论。〔[01:32:41–01:35:44](transcript.html#t-01-32-41)、[01:40:17–01:43:04](transcript.html#t-01-40-17)〕

| 原则 | 会议中的含义 | 尚未定下的细节 |
| --- | --- | --- |
| 文档是第一公民 | 用自然语言保存目标、背景、架构、功能和决策；出现遗漏错误时可追溯 | 文档分类、维护责任、更新及复盘规则 |
| Stacked PR | 控制单次改动规模，表示 PR 之间的依赖，支持持续推进 | 栈如何维护、依赖如何表达、合入次序 |
| 人工审核逐步转自动化 | 骨架未稳定时手动合并；后续探索 AI 核验依据、决策冲突和代码 | 自动合并门槛、CI 项目、异常处理机制 |
| 流程从简 | 先以小团队能运行的最小规则起步，遇到遗漏再补充 | 哪些规则必须、哪些可按任务规模简化 |
| 项目说明与 Skill 有边界 | 讨论 AGENTS.md、ADR；项目内优先放针对该项目的 Skill | 最终文件结构和具体 Skill 清单 |
| 沟通可沉淀 | 日常交流倾向用飞书，让 AI 汇总会议与消息 | 是否需要新空间、如何接入、如何复核产物 |

依据：〔[58:43–01:00:00](transcript.html#t-58-43)、[01:34:07–01:36:27](transcript.html#t-01-34-07)、[01:48:38–01:54:14](transcript.html#t-01-48-38)〕

## 7. 读取飞书 AI 总结时应保留的区别

飞书原文在下方保留，便于对照。正文依据逐字稿作了以下区分：

- **“通过调度器错峰即可支撑千级并发”是 AI 纪要的强化表述。**原始发言是目标、可能方案和试用观察，没有给出相应压测证明。
- **节点细拆、嵌套和分工是设计方向。**会议承认细拆收益未验证；接口规范、兼容性和详细职责仍需架构讨论。不能把“完全兼容”“完全解耦”读成已经验证的实现结果。
- **自动合并、自动总结是逐步探索的方向。**当前阶段明确采用人工审核，并由两人复核 AI 生成的流程方案。“无需人工手动整理”不等于无需人工核验。
- **直属的会后任务是流程初稿。**会末在 01:50:22 明确表示骨架暂时不需要先动；不要把早些时候关于骨架的畅想当作最终行动项。
- **AI 待办存在责任表述歧义。**原文写“完成后与付方圆共同核验”，同时又标记付方圆为负责人；逐字稿 01:52:04 明确是“两人看一眼并讨论补充”。下方原文不做改写。
