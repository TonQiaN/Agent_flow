1. 最重要的结论

  1. 先把任务跑通，再用证据决定是否细拆。 付方圆认可先以较大的稳定任务单元完成 MVP；随后再衡量细粒度拆分是否改善质量、耗时或 Token 成本。细拆不是所有场景的预设答案。〔42:27–45:28〕
  2. 两人的方案可以按层整合。 付方圆侧重节点或工作区内部的实现、可观测性与精调；李孝轩侧重节点或工作区之间的通信、容器隔离与编排。整个工作流可以成为上层的一个节点。〔23:28–24:18、51:43–53:55〕
  3. 新项目叫 AgentFlow，开发语言选 TypeScript。 优先适配 DeepSeek Harness，同时保留 Codex、Claude 等 Harness 的接入能力；各适配器按实际能力提供审计等字段。〔01:10:11、01:14:21、01:19:19–01:23:15〕
  4. 前端主要服务观察与调试。 运行历史、轨迹回放、节点 Prompt 和流向是核心展示内容；主要配置和修改由用户通过 AI 工具完成，仅保留少量人工微调。〔01:23:20–01:24:41〕
  5. 初期聚焦高重复量、要求稳定的文书和数据处理。 先满足自身需求；代码开发工作流、开源、商业化及交付数据处理成果等路径保留为后续探索。〔01:24:47–01:29:54〕
  6. 先定通用开发流程，之后再定产品架构。 以文档为第一公民，用 Issue、独立 worktree、PR 和评审串起工作；初期手动审核合并，逐步探索自动化。会末明确说项目骨架此时不需要先动。〔01:40:17–01:43:58、01:50:10–01:54:14〕

2. 核心分歧：工作应拆到多细

两人的分歧同时涉及任务粒度 和边界约束 ，讨论后找到了可兼容的层级，但尚未通过对照实验判定哪种做法在具体场景更好。

维度 付方圆的出发点 李孝轩的出发点
拆分原则 找到最小的、有独立意义的动作，逐步执行和调优 找到单个 Agent 能稳定完成的最大任务；组合不稳定时再拆
最看重的收益 中间过程透明、局部调试、精调成本、模块化分工 先保障端到端稳定，减少不必要的拆分及耦合
内部上下文 同一工作流共享工作区，各 Action 使用独立会话；用 Prompt 告知前序产物路径 拆开的节点通过明确的输入输出约束通信
约束位置 对整个工作流的入口、出口做检查；内部主要依靠 Prompt，遇到问题再加约束 节点前后设置 Gate，先固定接口，再独立调试
证据状况 有简历多角色评审结果不稳定的实践经历；尚无系统的拆分收益比较 提出必须比较拆与不拆的效果，认可不同场景可能需要不同粒度

兼容方式： 一个带明确输入输出边界的任务单元，内部可以先由一个 Agent 完成；确有收益时再拆成多个步骤。其内部工作流又可以封装为上层的一个节点。这样，外部编排与内部精调可以分别推进。〔11:08–14:23、27:18–28:18、34:27–39:36〕

仍需验证： 付方圆提出可用业务数据集测试，例如简历与岗位匹配；李孝轩进一步要求比较不同设计在质量、速度和 Token 消耗上的差异。会议没有给出既定数据集、验收阈值、重复试验次数或已完成的量化结果。〔16:34、24:18–26:27、43:40–44:07〕

3. 产品与架构的落点

3.1 Harness 适配：共享接口，能力按实际提供

双方认可设置适配层，不把产品限定在单一 Harness 上。DeepSeek Harness 是优先投入的对象，因为可以深入修改、观察内部过程；Codex 和 Claude 即使不能输出相同的审计信息，也应允许接入。“能接入运行”和“具备全部精调与审计能力”是两个层次。 具体配置声明、能力字段和接口契约尚待架构讨论。〔01:19:19–01:23:15〕

付方圆还提出在开发环境保留相关 Harness 的参考源码，并考虑更新检查，帮助 AI 准确理解实现。李孝轩将其归为开发流程议题；会上没有把更新 Hook 或参考目录定成完整规范。〔01:20:55–01:21:59〕

3.2 容器、插件和调度：整合方向明确，方案尚需验证

李孝轩已有为 Agent 启动独立容器并挂载资源的实现思路；付方圆现有隔离更多依赖运行目录和路径限制，希望用容器能力改造。两人讨论了按任务挂载插件、避免不需要的插件激活，以及预制镜像和启动前环境检查的差异。插件机制本身尚未深入研究，不能视为适配已完成。 〔41:42–41:58、48:41–49:42、54:31–57:44〕

千级并发是期望达到的服务能力。会议举例指出：PDF 切图等任务可能在短时间集中占用大量内存；可考虑监测容器资源、错开峰值。发言中的依据是现有试用观察，没有千级并发压测结果，也未确定调度算法、资源预算或服务指标。 〔46:14–48:03、50:31–51:15〕

3.3 用户体验：让人看清过程，让 AI 承担配置工作

可视化主要用于查看执行历史、回放轨迹、理解节点 Prompt 和流程走向。用户通过 Codex、Claude 等工具创建和调整工作流，前端承接观察、诊断及少量修改。付方圆强调透明的执行上下文也能帮助 AI 继续调试和优化。〔19:25–19:49、44:36、01:23:20–01:24:41〕

3.4 复用旧项目：带走功能、经验和决策，重新对齐架构

会上“移植”的含义经过澄清：先把现有功能和踩坑经验带入新项目，由 AI 参考已有实现；新架构仍需重新讨论。付方圆原项目中的 Object、端口设计来自 Ontology 背景，脱离该业务前提后需要重审。本次会议没有最终定下节点定义、数据流转协议和完整目录骨架。 〔01:44:11–01:48:27〕

4. 协作方式与开发流程

项目有两个并行目标：做出有用的 AgentFlow，也摸索一套能支持 AI 编程长期维护的小团队开发方法。两人可用于讨论的时间主要在晚间，平时可能异步推进；流程应适配这种实际情况。〔01:31:11–01:33:32、01:43:09–01:43:58〕

会上认可的大框架是：讨论目标与预期结果 → 形成并分类 Issue → 明确分工 → 必要的研究与决策记录 → 独立 worktree 实现 → 带依据和验证材料的 PR → 评审与合并。 Bug、新功能和方向调整被用作 Issue 分类的例子，具体模板和流程细则仍需初稿讨论。〔01:32:41–01:35:44、01:40:17–01:43:04〕

总结

本次会议围绕 AI 工作流编排工具的设计思路、联合开发方案与落地路径展开深度对齐，核心内容如下：

  • AI 工作流设计理念的分歧与共识

    • 付方圆的最小单元拆分思路

      • 拆分逻辑：主张将任务拆解为最小可执行动作单元，每个节点对应不可再拆分的最小任务，参考 RoughLoop 思维保障每一步执行的稳定性。
      • 约束规则：节点间默认仅通过 Prompt 传递上一节点的文件路径作为上下文，不强制设置输入输出强约束，遵循非必要不新增约束的原则。
      • 设计初衷：优先复刻个人使用 CLI 与 AI 交互的工作习惯，追求更强的过程掌控感，支持模块化迭代与团队分工，便于后续精细化调优。
      • 验证背景：此前在简历解析场景中，直接使用单 Agent 完成多角色评审汇总任务时出现结果不稳定问题，是拆分思路的实际触发背景。

    • 李孝轩的最大稳定单元思路

      • 拆分逻辑：优先寻找单 Agent 可端到端稳定完成的最大任务单元，仅在端到端执行出现稳定性问题时，才将任务拆分为多个独立节点。
      • 约束规则：所有拆分后的节点间必须设置 Gate 强约束，对输入输出格式做严格校验，保障节点间完全解耦，可独立调试与优化。
      • 设计初衷：尽可能减少不必要的节点拆分，降低整体工作流的复杂度，在保障稳定性的前提下提升任务执行效率，减少额外的调度开销。

    • 双方共识与兼容方案

      • 思路无本质冲突：两种设计思路不存在根本矛盾，可通过分层架构实现完全兼容，节点内部支持细粒度拆分，节点间通过强约束做边界隔离。
      • 拆分必要性验证约定：李孝轩建议付方圆针对细粒度拆分的实际效果做量化验证，对比不同拆分方式在执行质量、耗时、Token 消耗等维度的差异，明确拆分的适用场景。
      • 节点封装规则：所有完成开发的工作流均可封装为独立原子节点，作为更大规模工作流的组成部分，实现工作流的嵌套调用与复用。
  • 联合开发方案与核心能力规划
    • 项目定位与命名
      • 正式命名：确定项目正式命名为 AgentFlow，区别于传统的通用 Workflow 编排工具，核心面向 AI Agent 的任务编排场景做专属优化。
      • 发展路径：初期以个人使用为核心目标，优先满足两人自身的开发与工作提效需求，后续可探索开源、商业化服务等多种可能性。
      • 边界规划：明确初期暂不将代码开发类场景纳入核心规划，该场景涉及 Git 冲突、高权限容器等潜在坑点较多，待核心能力成熟后再做评估。
    • 技术栈与核心能力
      • 技术选型：确定采用 TypeScript 作为全栈统一开发语言，同时支撑前端可视化与后端调度逻辑的开发，降低跨语言的适配成本。
      • 多 Harness 适配层：设计统一的适配层架构，优先对 DeepSeek Harness 做深度适配，支持精细化改造与全链路审计，对 Codex、Claude 等仅做基础适配。
      • 核心功能：核心能力覆盖工作流运行轨迹回放、可视化调试、节点插件按需挂载、容器化隔离、中央调度器等模块，前端以展示与调试为核心定位。

    • 流程参考框架
      • 核心范式：整体开发流程核心参考 DeepSeek Harness 成熟开发范式，采用 Idea -> Issue 分类 -> 独立分支实现 -> PR 提交 -> 合并的标准链路。

      • 文档优先级：明确文档为项目第一公民，所有决策、架构、功能说明均以自然语言文档为核心载体，代码仅为文档的落地实现，优先级低于文档。
      • PR 规则：确定采用 Stacked PR 模式，支持 PR 之间的依赖关系，避免单次提交的改动量过大，降低审核与回退的成本。
      • 信息沉淀规则：所有会议、日常沟通内容均通过 AI 工具自动总结沉淀，无需人工手动整理，最大程度降低跨时间协作的信息差与沟通摩擦。
    • Vibe Coding 协作共识
      • 协作价值：双方确认当前 AI 已可覆盖绝大多数代码实现工作，协作的核心价值为互补不同视角的设计输入，把控整体方向。
      • 单人开发风险：明确单人使用 AI 开发时，个人的错误会被无限放大，且容易陷入牛角尖，双人协作可快速识别不合理的设计，避免无效投入。
