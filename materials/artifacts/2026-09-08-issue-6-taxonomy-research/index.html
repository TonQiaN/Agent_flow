方案 优点 对本项目的代价 研究判断

03 · 怎么选类：看主要结果，不看正在做哪一步

这是分类辅助，不替代范围判断；混合工作按主结果分类。

主类型 关键问题 典型交付 不能据此自动推断
功能 要新增或改变什么产品能力？ 可用行为/接口、对应决定与验证 写的是 Prompt/配置就不是开发；功能必须一次交付所有未来版本
缺陷 哪个已约定的行为没有成立？ 复现/调查证据、修复、回归验证 无法复现就不是 Bug；看见异常就知道根因
研究 哪个未知事实需要证据？ 有界研究结论与适用限制，可包含决定 必须写产品代码；必须证明原设想可行；证据不足等于已完成
决策 团队现在要选定什么？ 自足的正式决定、确认范围与落实交接 决定被采纳等于功能实现；没有实验证据也能编造比较结果
维护 要落实什么工程、文档或协作改进？ 代码/配置/模板/指南与适当验证 维护只是小改动；可以不受 Issue/决定/PR 规则约束

选择时先核对期望是否为已有契约：如果已承诺行为被破坏，通常是缺陷；如果期望本身尚未选定，先澄清范围。独立工作只需证据回答问题时选研究，只需选择方案与形成规范时选决策；其余按产品行为交付或工程改善选择功能/维护。

文件名、模块名和工具名不决定类型。 修改 Prompt 以满足新业务规则是功能；修复违反既有 schema 的 Prompt 可以是 Bug；优化团队开发用 AGENTS/skill 是维护。新建三 Harness 执行模块在当前“尚无产品实现”的基线下属于功能；未来对已实现适配层进行不改变契约的重构，则通常是维护。性能任务同理：恢复已有时限是 Bug，未知瓶颈定位是研究，既有契约内优化是维护，承诺新的容量/行为边界是功能。

什么时候拆成多个 Issue

满足以下具体条件再考虑拆分：不同主责能独立交付；研究结论会决定是否还有实现工作；某项是其他工作的明确阻塞；各自有不同验收时间且单独交付有价值。父项负责共同结果和整体验收，子项保留自己的主责、范围与证据。

当主目标、主责和验收仍相同，调研、方案选择、实现、评审修正与 AI 会话切换可留在一个 Issue 内。不能为每个 Agent、新分支、文件、PR 或工作阶段机械建项。Issue #6 就是一个例子：当前做研究，最终仍要交付模板与指南，因此无需因研究阶段把整个 Issue 改成“仅研究”，也无需先创建 E04。

容易混淆的维度 推荐表达 为什么不当作主类型
前端、Runner、Harness、环境、流程文档 正文模块范围；确有筛选需求时加少量 area 标签 一个 Bug 可跨前后端，一份决定也可跨模块
决定、代码、模板、指南、验证记录 可多选交付物 + 对应验收 所有主类型都可能需要决定或说明
紧急、阻塞、低优先级 影响/优先级及依赖；具体排序由主责判断 紧急不会改变“修复什么”
0.1.x、某次发布 roadmap / milestone 或已有版本入口 版本目标与任务性质不同，不在表单内复制整份 roadmap
Epic、父项、子项 组成关系；父项仍有主要工作类型 结构层级不能代替交付定义
待整理、研究中、实现中、待审阅 阶段摘要/现有状态 不把阶段变化变成类型变化或决策目录变化
已完成、取消、重复、不采用、延期 关闭/继续处理依据与去向 “研究后不采用”可完成研究；撤回计划不代表功能实现

共通加差异，还是五类各自维护？

本项目更适合“共通规范＋五类差异”，填写入口则保留五份独立完整的模板。 这里要区分三件事：共同规则在哪里解释、填写者拿到什么、文件是否由工具生成。前两项可以分别采用集中规范和完整表单，不必为了共通规范马上引入生成器。

现有候选每类有 9–10 个字段。owner、scope、deliverables、acceptance、dependencies、decision_context、handoff 这七项的字段结构与文字完全相同；problem 有共同职责、按类别改写提示；每类再增加 1–2 项专用字段。这个重合度说明共同规则真实存在，适合集中维护。这只是结构对比，并非填表效率测量。

维护方式 修改一项共同规则 修改一类专有需求 当前成本与判断
五类各自定义，不考虑共性 五份决定和五份表单分别判断，容易漏改或形成不同解释 类内自由，局部修改直接 初期最直观；当前共性很多，长期容易反复讨论同一问题，不推荐
共通决定＋五类差异决定；五份完整表单 在共通决定修改一次理由，再核对并同步受影响表单；只有某类的例外理由变化时才改其差异决定 修改该类决定与该类表单 推荐首版。规则集中、表单可独立阅读；接受手工同步五份表单的成本
共通数据文件＋五类覆盖数据，生成完整表单 改共同数据后重建，减少逐份同步 改该类覆盖数据后重建 改动频繁时有价值；当前会新增合成规则、工具依赖、生成结果与来源定位的维护成本，先保留为升级方案

完全独立的方式也有适用条件：各类别由不同团队负责、共享字段很少，或同名字段的含义实际不同。当前五类属于同一开发流程、共同主责与验收原则，尚不具备这些条件。另一边也不应把所有差异硬塞进共同模板：复现只对 Bug 有用，研究停止条件只对研究有用，它们保持类内定义。

08 · 长期维护：分类之后如何避免信息再次失效

一个 Issue 要能让几天后的另一个人或另一个 AI 找回当前事实，推荐在实质节点更新一段短记录：当前基线 → 已确认范围 → 已完成与证据 → 未完成/阻塞 → 下一步和责任人。优先覆盖过时摘要，并在必要处保留变更原因；不要把每次工具调用都变成评论。外部假设变化、接口范围变更和关键审阅意见需要说明影响，普通进度无需制造审批。
