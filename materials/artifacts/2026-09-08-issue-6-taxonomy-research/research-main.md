## 02 · 分类方案：比较后为什么推荐五类

| 方案 | 优点 | 对本项目的代价 | 研究判断 |
| --- | --- | --- | --- |
| 一张万能模板，正文自选类别 | 入口最少，共通字段只维护一处 | Bug、证据研究、方案取舍差异大；无关问题会塞进所有人的表单，AI 也容易省略差异信息 | 不推荐作为当前主入口；CLI 可共享公共骨架 |
| 保留三类，把研究/讨论全放维护 | 迁移最小，工程事项集中 | “修复/交付文件”和“只回答未知/作选择”混杂；需要靠长说明纠正验收方式 | 可用的保守备选，但正是现有讨论暴露的缺口 |
| 四类：功能、缺陷、研究/决策、维护 | 少一个入口，探索工作集中 | 需要同一表单里区分实验证据和方案选择；纯决策易被要求做实验，纯研究也可能被迫给采纳结论 | 若五类使用中频繁选错，可合并；目前作为主要备选 |
| **五类：功能、缺陷、研究、决策、维护** | 每类有清楚的主要问题和完成条件；三类旧入口保留，只新增两个 | 增加两个文件，需要防止强制把每个阶段拆成新 Issue | **用户已认可方向；按七项决定细化，字段与实际使用仍需验证** |
| 很多专类：Prompt、文档、测试、重构、性能、安全、发布、Epic 等 | 名称看起来细致 | 把实现载体、质量目标、风险和结构关系混到一个层级，交叉选择与重复维护明显增多 | 首期不采用；特定差异用条件字段，真实反复失配再拆 |

五类方向已获确认，上表保留选择时的比较依据；四类方案不再与五类并列为当前待选项，只有出现具体重开理由时再评估。这不是行业唯一标准，也没有两人团队长期运行统计证明“五类最优”。选择依据是本项目已经出现独立研究和独立范围确认需求，并且现有三个入口仍有价值。原 25 项映射中暂得 14 功能、8 决策、2 研究、1 维护、0 Bug，**这是对候选清单的解释，不是未来工作分布预测**。当前无产品实现，也不能把假设 Bug 当作已发生问题。

外部资料提供的是设计参照：

- Rust RFC 模板要求说明动机、具体用例、方案代价、替代方案和未决问题，适合借鉴“决策必须回答什么”；其大型社区治理流程不直接照搬到这里。[Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/master/0000-template.md)
- Rust 的 RFC 采纳和实现追踪分开，提示“方案完成”与“功能完成”应有不同交付事实；AgentFlow 沿用自己的 proposed / implemented 规则，无需复制其生命周期。[Rust RFC 流程](https://github.com/rust-lang/rfcs)
- 本轮读取的 OpenHands 仓库表单面向 Agent Canvas：Bug 收集版本、运行方式、实际/期望、复现和验收；Feature 收集问题、期望行为和验收。可以借鉴字段职责，不照搬其截图门槛、ready-for-dev 标签或全量日志要求。[Bug 表单](https://github.com/OpenHands/OpenHands/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml) · [Feature 表单](https://github.com/OpenHands/OpenHands/blob/main/.github/ISSUE_TEMPLATE/feature_request.yml)
- VS Code 指南强调一个独立问题一个 Issue，复现应包含相关版本与条件；这支持按验收结果拆分。它的自动过期关闭机制不适合未经验证就套到当前异步小团队。[VS Code 贡献指南](https://github.com/microsoft/vscode/blob/main/CONTRIBUTING.md#writing-good-bug-reports-and-feature-requests)

## 03 · 怎么选类：看主要结果，不看正在做哪一步

<!--CHOOSER-->

| 主类型 | 关键问题 | 典型交付 | 不能据此自动推断 |
| --- | --- | --- | --- |
| 功能 | 要新增或改变什么产品能力？ | 可用行为/接口、对应决定与验证 | 写的是 Prompt/配置就不是开发；功能必须一次交付所有未来版本 |
| 缺陷 | 哪个已约定的行为没有成立？ | 复现/调查证据、修复、回归验证 | 无法复现就不是 Bug；看见异常就知道根因 |
| 研究 | 哪个未知事实需要证据？ | 有界研究结论与适用限制，可包含决定 | 必须写产品代码；必须证明原设想可行；证据不足等于已完成 |
| 决策 | 团队现在要选定什么？ | 自足的正式决定、确认范围与落实交接 | 决定被采纳等于功能实现；没有实验证据也能编造比较结果 |
| 维护 | 要落实什么工程、文档或协作改进？ | 代码/配置/模板/指南与适当验证 | 维护只是小改动；可以不受 Issue/决定/PR 规则约束 |

选择时先核对期望是否为已有契约：如果已承诺行为被破坏，通常是缺陷；如果期望本身尚未选定，先澄清范围。独立工作只需证据回答问题时选研究，只需选择方案与形成规范时选决策；其余按产品行为交付或工程改善选择功能/维护。

**文件名、模块名和工具名不决定类型。** 修改 Prompt 以满足新业务规则是功能；修复违反既有 schema 的 Prompt 可以是 Bug；优化团队开发用 AGENTS/skill 是维护。新建三 Harness 执行模块在当前“尚无产品实现”的基线下属于功能；未来对已实现适配层进行不改变契约的重构，则通常是维护。性能任务同理：恢复已有时限是 Bug，未知瓶颈定位是研究，既有契约内优化是维护，承诺新的容量/行为边界是功能。

### 什么时候拆成多个 Issue

满足以下具体条件再考虑拆分：不同主责能独立交付；研究结论会决定是否还有实现工作；某项是其他工作的明确阻塞；各自有不同验收时间且单独交付有价值。父项负责共同结果和整体验收，子项保留自己的主责、范围与证据。

当主目标、主责和验收仍相同，调研、方案选择、实现、评审修正与 AI 会话切换可留在一个 Issue 内。不能为每个 Agent、新分支、文件、PR 或工作阶段机械建项。Issue #6 就是一个例子：当前做研究，最终仍要交付模板与指南，因此无需因研究阶段把整个 Issue 改成“仅研究”，也无需先创建 E04。

| 容易混淆的维度 | 推荐表达 | 为什么不当作主类型 |
| --- | --- | --- |
| 前端、Runner、Harness、环境、流程文档 | 正文模块范围；确有筛选需求时加少量 area 标签 | 一个 Bug 可跨前后端，一份决定也可跨模块 |
| 决定、代码、模板、指南、验证记录 | 可多选交付物 + 对应验收 | 所有主类型都可能需要决定或说明 |
| 紧急、阻塞、低优先级 | 影响/优先级及依赖；具体排序由主责判断 | 紧急不会改变“修复什么” |
| 0.1.x、某次发布 | roadmap / milestone 或已有版本入口 | 版本目标与任务性质不同，不在表单内复制整份 roadmap |
| Epic、父项、子项 | 组成关系；父项仍有主要工作类型 | 结构层级不能代替交付定义 |
| 待整理、研究中、实现中、待审阅 | 阶段摘要/现有状态 | 不把阶段变化变成类型变化或决策目录变化 |
| 已完成、取消、重复、不采用、延期 | 关闭/继续处理依据与去向 | “研究后不采用”可完成研究；撤回计划不代表功能实现 |

## 05 · 共通字段：够用，但不把整套流程塞进创建表单

推荐八个共通信息块（其中问题描述按类型调整），再加一至两个差异块。YAML 中最终为功能 9、缺陷 10、研究 10、决策 10、维护 9 个输入块；其中“相关决定”和“整理与续接”可按阶段补充。不是要求每次创建都填写一篇设计文档。下面的字段数量是草案结构计数，不是填表耗时测量。

| 信息 | 创建时 | 开工 / 实施前 | 交接 / 结题时 |
| --- | --- | --- | --- |
| 主责 | 一名人类主责，设置 Assignees | 范围调整时核对责任 | 接手者与主责变更留简短说明 |
| 问题、目标与该类关键问题 | 足以判断这是哪项工作；未知如实写 | 从宽泛愿望收敛到具体交付切片 | 不用实现结果倒写最初的问题 |
| 范围与保留边界 | 包含/排除、受影响接口或模块 | 明确不可默改的已确认行为 | 遗留范围有去向，不能隐形删除验收 |
| 交付物 | 明确预计交付内容 | 指向所需实际内容/文件，不靠占位路径凑数 | 对照真实进入默认分支或确认的产物 |
| 验收 | 可检查结果与方法 | 补齐基线、反例和适用测试 | 填实际结果、版本、未测部分及原因 |
| 依赖 | 无 / 具体所需交付；参考与阻塞分开 | 阻塞有处理人及解除条件 | 子项结束不自动清除未满足的依赖 |
| 相关决定与待决问题 | 可先列候选 ID 或待查问题 | 查现行正文/alternatives/rejected；必要取舍先写清 | 记录实质改变与具体确认；同问题唯一正文 |
| 整理与续接 | 可空，不填“默认已确认” | 人参与确认范围；已有授权直接登记 | 保留当前基线、已做/未做、阻塞与下一步 |

AI 可以提取材料、拟分类、补字段、对照决定、提出验收和执行检查；人负责主责归属、目标和关键取舍。续接记录不需要保存“每一步 AI 思考”或整段会话。影响判断的证据需要可核对，但原始聊天路径不是必填项。[现行工作指南](../../../docs/development/workflow.md) · [资料关联的拒绝边界](../../../.agents/decisions/development/rejected/D-20260907-mandatory-source-traceability.md)

### 条件信息放在哪一块

| 触发条件 | 在相关字段补充 | 不作为所有 Issue 的必填项 |
| --- | --- | --- |
| 运行错误 / Harness 能力实验 | 提交与 Harness 版本、镜像依赖、节点 skill/MCP 配置分别列出；外围 Run/NodeTask/Attempt、时间与 I/O | 不要求容器内 agent 会话、工具调用轨迹或所有开发工具版本 |
| 修改接口、配置或历史 schema | 调用方、兼容策略、旧数据样例、迁移/失败/回退路径 | 无数据迁移的文字修正不填一套回滚手册 |
| 非确定性结果 | 评分规则、样本/控制条件、实际重复次数与失败次数、外部变化 | 不把一次跑通写成稳定；没有观测时写未知，不造数字 |
| 会造成外部写入或资源消耗 | 哪些动作在本次范围内、dry-run/预算/权限条件（适用时） | 不把建立 Issue 本身视为所有外部动作的无限授权 |
| 影响多个开发者/Agent 的共享契约 | 接口边界、协作分工、并行改动约束、明确交接点 | 不为每名执行 Agent 新增一个主责类型 |
| 敏感数据或凭据问题 | 脱敏证据、影响范围、实际可共享范围 | 不粘贴密钥，也不在本次凭空建立新合规流程 |

字段按实际问题增减。采用 `placeholder` 引导填写，不用默认 `value` 填入“无阻塞 / 已确认 / 已测试”；否则默认文字容易被误作真实判断。后续若有自动化读取字段，稳定的字段 ID 比复杂目录更有用；当前不承诺这种自动化已经存在。

### 共通加差异，还是五类各自维护？

**本项目更适合“共通规范＋五类差异”，填写入口则保留五份独立完整的模板。** 这里要区分三件事：共同规则在哪里解释、填写者拿到什么、文件是否由工具生成。前两项可以分别采用集中规范和完整表单，不必为了共通规范马上引入生成器。

现有候选每类有 9–10 个字段。`owner`、`scope`、`deliverables`、`acceptance`、`dependencies`、`decision_context`、`handoff` 这七项的字段结构与文字完全相同；`problem` 有共同职责、按类别改写提示；每类再增加 1–2 项专用字段。这个重合度说明共同规则真实存在，适合集中维护。这只是结构对比，并非填表效率测量。

| 维护方式 | 修改一项共同规则 | 修改一类专有需求 | 当前成本与判断 |
| --- | --- | --- | --- |
| 五类各自定义，不考虑共性 | 五份决定和五份表单分别判断，容易漏改或形成不同解释 | 类内自由，局部修改直接 | 初期最直观；当前共性很多，长期容易反复讨论同一问题，不推荐 |
| **共通决定＋五类差异决定；五份完整表单** | 在共通决定修改一次理由，再核对并同步受影响表单；只有某类的例外理由变化时才改其差异决定 | 修改该类决定与该类表单 | **推荐首版。规则集中、表单可独立阅读；接受手工同步五份表单的成本** |
| 共通数据文件＋五类覆盖数据，生成完整表单 | 改共同数据后重建，减少逐份同步 | 改该类覆盖数据后重建 | 改动频繁时有价值；当前会新增合成规则、工具依赖、生成结果与来源定位的维护成本，先保留为升级方案 |

完全独立的方式也有适用条件：各类别由不同团队负责、共享字段很少，或同名字段的含义实际不同。当前五类属于同一开发流程、共同主责与验收原则，尚不具备这些条件。另一边也不应把所有差异硬塞进共同模板：复现只对 Bug 有用，研究停止条件只对研究有用，它们保持类内定义。

### 五类相对共同基线的具体变化

共同基线的八个字段是 `owner`、`problem`、`scope`、`deliverables`、`acceptance`、`dependencies`、`decision_context`、`handoff`。`problem` 表达“当前问题与目标”，允许类型调整提示。其余共同字段的统一要求由共通决定负责，类内填写解释与必要例外由类决定说明。

| 类型 | 增加 | 改写 | 删除 | 为什么这样改；本类验收解释 |
| --- | --- | --- | --- | --- |
| 功能 | `behavior_contract` | `problem` 改为用户、场景与新增/改变能力 | 无 | “想做什么”不足以实现；补输入输出、正常/失败与接口边界。`acceptance` 填行为可观察的结果 |
| 缺陷 | `reproduction`、`environment` | `problem` 改为触发、实际/期望及依据 | 无 | 修复需要失败条件和相关基线；允许未知或未复现。`acceptance` 保留恢复契约及回归目标，调查结束不自动等于修复 |
| 研究 | `evidence_plan`、`stop_rule` | `problem` 改为未知问题与结论用途 | 无 | 研究需说明怎样取证、何时结束；支持否定结论。`acceptance` 验有界结论与证据限制，不强制产品实现 |
| 决策 | `options`、`impact` | `problem` 改为需要选定什么、哪些已确认 | 无 | 比较选择与落实后果需要单独交代。`acceptance` 可以只验正式决定，明确已采纳与未实现部分 |
| 维护 | `change_plan` | `problem` 改为当前工程问题与改进目标 | 无 | 保留改动入口、兼容、适用迁移/回退和验证；`acceptance` 核对所承诺文件与行为实际落地 |

**“增删改考量”不要求每类都制造删除。** 当前没有充分理由删除共同字段：例如研究不写产品代码，仍然需要主责、范围、交付物与验收。某类将来确实不适用某字段时，在其差异决定说明为什么、原字段职责如何处理；若五类都不需要，直接修订共同基线。仅更换提示但含义不变，保留原 ID；职责实质改变则评估迁移，不能用同名掩盖含义变化。

### 以后改一次，具体要维护哪里

| 改动 | 需要修改与核对 | 不需顺手改动 |

| Bug 增加一个确有必要的环境提示 | Bug 差异决定、`bug.yml` 和受影响示例/说明 | 共通决定与其他四类表单 |
| 减少全部类型都不必要的字段 | 共通决定、五份 YAML 和引用该字段的说明；查清是否有类内例外 | 分类决定，除非分类本身也变了 |
| 调整研究/决策边界或新增主类 | 分类决定及实际受影响的类决定、模板和指南 | 不机械重写无关决定 |

首版同步核对的最低内容是：共同字段 ID 是否齐全且无重复、类型与必填意图是否一致、共同文字是否偏移、每类新增/改写是否符合自己的差异决定。由实施 PR 留下实际比较结果；本轮尚未新增自动检查或 CI。现有 artifact 生成脚本已复用共通定义，但它只证明候选可以生成，不证明维护正式生成器更省成本。

如果共同字段经常变化、出现真实漏同步，或确实要同时交付多个平台格式，再在共通决定中重开“单一数据源生成五份表单”的方案。届时再敲定源文件位置、允许的覆盖规则和生成检查，避免现在先建立一套尚无持续需求的模板框架。

## 08 · 长期维护：分类之后如何避免信息再次失效

一个 Issue 要能让几天后的另一个人或另一个 AI 找回当前事实，推荐在实质节点更新一段短记录：**当前基线 → 已确认范围 → 已完成与证据 → 未完成/阻塞 → 下一步和责任人**。优先覆盖过时摘要，并在必要处保留变更原因；不要把每次工具调用都变成评论。外部假设变化、接口范围变更和关键审阅意见需要说明影响，普通进度无需制造审批。

| 情况 | 处理建议 | 需要保留的事实 |
| --- | --- | --- |
| 研究发现原设想不可行 | 研究可按预定问题验收；实现目标需要调整时更新原项或后续范围 | 真实证据、适用边界、否定理由与重开条件 |
| 决定采纳，实施另行推进 | 决策类 Issue 可在其文件交付和确认范围满足后结束；产品决定仍可留 proposed | 后续实施去向、明确未实现部分；无需虚构新 Issue 号 |
| 调查仍无法复现 | 保留 Bug 目标，主责选择补证、缩小调查或按证据处理 | 尝试、缺少条件与处理依据，不写“已修复” |
| 多个 PR 分批交付 | 部分 PR 引用工作项；最终对完整验收核对 | 每个 PR 自己的 base、决定增量和验证范围 |
| 一个子项已完成 | 更新组成关系，父项再验共同结果 | 端到端集成、尚未交付子范围，不能只看勾选数 |
| 合并后出现回归 | 关联原项/PR，按具体缺陷重新跟进；重大事故留永久复盘 | 回归版本、触发条件、修复/回退证据 |
| 重复、取消或延期 | 更新原项并说明结果和去向；不创建“重复类 / 延期类”模板 | 没做的范围、替代项/后续安排及重开条件 |

研究/决策的验收与结束边界已在各自正式决定中形成设计，仍需模板和真实使用验证。现行边界包括：每个正式 PR 对自身 base 的实质决策改动、人参与关键确认、同问题唯一决定、proposed 不等于未同意或可自动实施。小改动不为凑规则制造无意义决策；是否合并到相关工作项，应看真实共同问题。[开发流程决定](../../../.agents/decisions/development/README.md#d-20260907-development-workflow) · [生命周期决定](../../../.agents/decisions/development/README.md#d-20260907-decision-lifecycle)

### 模板怎样继续完善

建议先用之后一小批真实工作项检查：选类争议在哪里、哪些必要信息要追问、哪些字段总是不适用、是否有人把决定完成误作实现完成、AI 能否凭短摘要续接。可先观察约 10 项作为讨论起点，**不是当前生效的配额或统计承诺**。若研究/决策常分不清且字段高度重合，可回到四类备选；若某种场景反复需要独特验收，再考虑拆模板。

模板修订本身沿用 Issue → 相关决定 → 模板/指南 → 验证流程。保留既有字段 ID 和文件路径可降低迁移成本；必须变更时明确映射。已关闭 Issue 不批量重写历史；活跃项仅在当前工作需要时补缺口，原始确认和验收不能被新默认值覆盖。功能模板内曾经缺少一个字段，不意味着此前所有工作都自动无效。

| 顶层 `type` | GitHub 的 Issue Types 在组织层定义；本仓库 owner 为 User | 不写组织级 `type:`。先用模板入口及标题前缀表示主类；本项尚未新建类别标签。[表单语法](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms) · [组织类型](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/managing-issue-types-in-an-organization) |
| 必填校验 | 官方 schema 对 input/textarea/dropdown 的 required 注明仅适用于公开仓库 | 保留字段的必填意图，但以人参与的就绪核对保证完整性；不能将私有仓库表单当作门禁。[表单 schema](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema) |

| 默认分支与空白入口 | 模板进入默认分支才可用；blank_issues_enabled=false 也不是禁止所有维护者使用空白入口 | 保持原设置，不将它视为访问或就绪控制；最终必须核对真实入口。[模板配置](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository) |
| 条件分支 | 本次官方 schema 的已列字段没有提供我们所需的动态显隐方案 | 草案使用五份明确表单与条件填写说明，不依赖未经验证的字段联动 |
| CLI/API | CLI 可直接给正文文件并指定主责等信息 | 五份 Markdown 骨架覆盖同等信息，使用 body-file 提交后回读；不假定网页表单会自动补齐 CLI 正文。[GitHub CLI](https://cli.github.com/manual/gh_issue_create) |
| 父子 / 阻塞关系 | GitHub 分别提供 sub-issues 与 blocked-by/blocking | 可作为后续结构表达，正文仍需写清交接条件；本轮未在 #6 创建这些关系或验证本仓库 UI。[子项](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues) · [依赖](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies) |
| 开放式讨论 | Discussions 适合问答与开放对话，需要启用；本仓库未启用 | 沿用飞书/materials 自由讨论；有明确产出与结束条件的决策工作仍放 Issue，不强制启用新入口。[Discussions](https://docs.github.com/en/discussions/collaborating-with-your-community-using-discussions/about-discussions) |

标题前缀是首版轻量选择，也会有被随手改掉的风险。当前用主责整理核对分类；若长期检索/自动化确需稳定机器字段，再比较少量 `kind:*` 标签与平台原生类型，不同时维护三套互相竞争的权威分类。模块标签、优先级标签和交付物标签也不预先铺满仓库。

候选表单优先沿用 `feature.yml` / `bug.yml` / `maintenance.yml`，新增 `research.yml` / `decision.yml`，避免仅为排序重命名旧入口。每份模板内字段 ID 唯一，同一概念在不同模板中复用相同 ID；不使用跨文件 YAML include 或未验证的继承机制。

## 12 · 来源、研究方法与限度

本研究优先使用当前仓库、用户明确要求和真实 Issue / PR；外部仅选官方文档与项目自身模板。检索与取样覆盖了项目材料到当前默认分支的主要流程演变，并定向阅读会议中的异步协作、研究任务、分类与轻量流程段落。没有重新下载飞书聊天或云端逐字稿，没有将旧 AI 纪要作为事实补充。材料源的摘要保存在 [provenance.json](sources/provenance.json)，研究阶段 Issue 正文保存在 [Issue #6 快照](sources/issue-6.json)。

初轮查找 GitHub 表单/类型能力、真实开源模板与 RFC 工作方式；随后针对个人仓库、私有表单校验、主责/标签、父子依赖、CLI 和研究/决策差异做定向核对。停止检索的原因是：当前分类和字段涉及的主要平台假设已经有官方依据，项目场景能够映射，剩余不确定性主要需要本团队真实填写和实施验证，继续搜更多模板难以替代这些证据。

- **事实来源**：当前仓库与远端快照、用户原话、所列会议时间段、官方文档。
- **确认与具体设计**：用户已认可五类、共通规范＋五类差异及七项决定组织方式；据此写出正式设计正文，具体字段与验收解释没有冒充用户逐条独立批准。研究原稿不成为第二套正式规则。
- **推演与演练**：30 场景中已标明未来假设，八份样例不是真实提交或故障；没有采集团队效率指标或运行性能实验。
- **已验证与限度**：GitHub 选择器、五类表单展示、多选与 Markdown 清单预览已实际核对；未试验空白提交拦截、CLI/API 新建样例、长期分类一致性、真实填表负担或多人审阅效果。静态/展示检查不能证明这些结果。
- **时间性**：外部主分支和 GitHub 文档可能变化，访问日为 2026-09-08；页面未给明确更新日时不编造发布日期。当前仓库状态与较早 artifact 快照分别表达。
