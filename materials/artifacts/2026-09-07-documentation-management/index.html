3. 你还没有展开的关键部分

3.1 决策需要保留理由和边界

“支持多个 Harness”是一条结论；“为什么支持、是否要求能力对等、当前适用的场景是什么”才能约束后续实现。过度浓缩成口号，会让 AI 用自己的理解补全关键空白。

建议一份短笔记至少保留：问题、决定、主要替代方案与取舍、适用边界、来源。必要时加一条重看条件。详细研究留在 artifact；无需把讨论逐句搬进决定。

3.2 接受、提议、被替代不能混在一起

多人异步开发最容易出现两种错误：AI 把建议当作共识，或者不同任务各自找到一版“最新决定”。本轮已用状态标签区分材料。更完整的建议是：以明确决议作为生效依据，实质改变新增替代记录，旧决定可追溯，索引指向当前有效项。

尚待讨论的是谁有权决定什么。 单人负责领域能否独立确认、跨边界改动是否需要两人参与，不能由 AI 替团队规定。已明确的用户指令可直接登记，不需要为了记笔记再请求一次确认。详见 生命周期提案。

3.3 决定描述期望，使用指南描述现实

一份接受的决定可能尚未实现。不能因为决定采用某 Harness，就在使用指南写成“已支持”。因此 docs/ 需要标清当前阶段和可验证行为，规划另行标注。

建议以后在同一个变更中维护受影响的决定、当前说明与实现。这样评审时能发现“目标变了但指南没变”或者“指南写好了但功能不存在”。本轮的架构和指南入口如实标为尚无运行实现。

3.4 还需要给验证与事故复盘一个去处

会议 01:53:49 特别提到：即使检查通过，使用时仍出错，也要追溯错误为何被放过。这一点没有在你本次列举中展开。

建议原始日志、复现步骤、实验和复盘过程仍放 artifacts/；从中发现的长期修正进入相应决策笔记，最终运行说明进入 docs/。先复用已有三层，不额外建立第四套知识库。一个单次 Bug 不必自动升级成制度决定。

3.5 Artifact 也需要可编辑源与出处

可视化页面、PDF 或幻灯片是阅读形式；其编辑源、构建方式和原始证据仍应可定位。把同一次会议或研究按主题聚合，比将 TXT、HTML、图片分别散落在不同格式目录里更容易追溯。

建议每个材料包只写一份短索引：来源与日期、原始文件、衍生摘要、阅读入口、提炼去向。原文纠错另存版本，AI 摘要单独标注。当前会议包已按这个方式补上索引。

4. 建议优先讨论的设计取舍

A. 开发必须从 Issue 开始吗

这仍是未决问题。会上认可 Idea → Issue → worktree → PR 的大框架，同时明确需要按小团队实践简化。你本次也把“从 Issue 开始的优缺点”作为需要决策的例子，因此本轮没有写成强制制度。

方案 好处 代价
所有工作必须先建 Issue 工作项、负责人和上下文容易统一定位 初步探索、会议讨论和极小改动也会承担登记成本
所有工作自由推进，最后补记录 启动快 容易丢失背景、分工和先前决议，补记常常滞后
研究可先产出 artifact；形成重要取舍时写决定；进入实现时登记工作项 区分探索、决策与执行，能兼顾追溯与轻量 需要约定何时算进入实现、哪些小改动可以简化

建议采用第三种。 “决策为第一公民”不等于每项任务都要先产生新决策；在已有决定内修错、完善说明可以直接推进。Issue 承载执行范围和负责人，决定承载方向与理由，二者互相引用即可。

B. 哪些材料随 Git 共享

建议把小体积文字稿、可编辑文档源和材料索引随 Git 管理，大体积音视频保留飞书来源与定位信息；可复现的生成文件根据评审和离线阅读需要选择保存。

好处是新成员拿到仓库后可以复核核心文字依据，同时减少大型二进制版本的负担。代价是原始音视频访问仍依赖飞书权限；仅有远程链接的材料还存在链接失效问题。具体取舍待讨论，本轮没有用 .gitignore 排除原始材料，也没有提交或推送材料。

C. AGENTS.md 要不要写成项目百科

建议保持短入口，只放读取顺序、材料效力和必要协作行为；“为什么这样写”进入开发流程决策，详细维护方法放进 docs/development/。

原因是所有任务都可能读这个入口，放入大量历史会提高上下文成本，复制规则也容易不同步。当前 CLAUDE.md → AGENTS.md 的共享方式保留，避免维护两份相同说明。

5. 下一步如何继续

先讨论决策接受与替代的最小机制、以及材料共享范围。随后再用实际一项小工作检验这套结构是否容易找、容易更新、容易追溯；遇到明确问题时再增加模板或检查。

产品的节点契约、Harness 接口、容器方案和页面架构仍应单独形成产品决定。本轮的候选笔记只是把会议方向浓缩出来，避免下一次重新读取整场会议，不代表已经定案。
